## 1. 背景与目标

为 CascadedEngine 探索一套自研编辑器：网页负责编辑器界面，C# 负责编辑器服务，现有 C++ 继续承担窗口、渲染图、GPU 后端和资源管理。

目标不是把引擎改造成浏览器应用，而是让桌面引擎进程承载网页界面与原生视口：

- 网页使用 HTML/CSS 与 TypeScript 实现面板、属性编辑器和命令输入。
- 新增 C# 编辑器服务，向网页提供稳定的命令、结果和事件协议。
- 复用现有 CSharpHost 与生成绑定，不让网页接触 C++ 指针、C ABI 或绑定句柄。
- 保留 Vulkan/D3D12 原生视口，不要求 WebAssembly、WebGPU 或逐帧图像传输。

## 2. 现状核实

### 已有基础

- 引擎是多后端渲染引擎，原生渲染可以继续由 C++ 承担。来源：`docs/project-baseline.md`；逐字引文：“CascadedEngine 是一个多后端渲染引擎，采用可插拔的图形后端架构。”
- CSharpHost 已在引擎进程内加载 CoreCLR，并通过函数表与托管侧双向调用。来源：`CSharpHost/README.md` 的「它做什么」一节；此处是转述、非逐字引文。
- 现有托管入口在引擎主线程执行。来源：`CSharpHost/README.md`；逐字引文：“`Boot` / `Tick` 都在引擎主线程上被调用”。
- 托管侧已经能使用生成的 `IWindow` / `IWindowSystem` 表面建窗、读取尺寸和修改窗口。来源：`Scripting/Managed/UserScript.cs` 与 `openspec/specs/csharp-window-runtime/spec.md`；此处是转述、非逐字引文。
- 原生窗口与渲染后端已有连接点。来源：`Interface/RenderInterface/header/CRenderBackend.h`；逐字引文：“virtual castl::shared_ptr<WindowHandle> GetWindowHandle(castl::shared_ptr<cawindow::IWindow> window) = 0;”

### 当前缺口

- 现有 C# 通路只完成窗口这一条纵向路径，不能把窗口绑定直接等同于编辑器后端。来源：`docs/ROADMAP.md`；逐字引文：“阶段 2 只打通了窗口这一条路”。
- 尚缺编辑器服务、网页静态资源宿主、网页通信协议、选择与撤销模型，以及面向编辑器的对象编号。
- 原生窗口回调（焦点 / 光标 / 鼠标 / 键盘 / 关窗 / 尺寸）已经能经生成绑定投影到 C#（`complete-csharp-window-system-bindings` 于 2026-11-01 实现，见该 change 的 `tasks.md` 5.1–5.2）；编辑器仍缺的是下面这些服务与数据模型，不是窗口回调本身。
- 当前窗口接口没有向 C# 暴露完整的窗口枚举面，因此首个切片只控制由编辑器服务明确登记的窗口，不预先承诺列出所有原生窗口。
- 场景、实体与组件数据模型不属于现有 C# 窗口通路；完整场景编辑器不能仅靠增加网页和通信层得到。

## 3. 推荐架构

```text
网页界面（HTML/CSS + TypeScript）
        │ 命令 / 结果 / 事件
        ▼
新增 C# 编辑器服务
        │ 生成绑定 + 手写适配器
        ▼
现有 CSharpHost → C ABI → C++ 引擎
                              │
                              ▼
                    Vulkan / D3D12 原生视口
```

### 职责划分

- **网页**：布局、控件、临时界面状态，以及向用户展示编辑器状态的投影。
- **C# 编辑器服务**：协议校验、编辑器对象编号、命令分发、选择、撤销、主线程调度和事件聚合。
- **生成绑定层**：继续镜像 C++ 接口，不直接成为网页协议。
- **C++ 引擎**：拥有引擎对象与原生渲染状态，执行真正的窗口、资源和渲染操作。

引擎对象状态以 C++ 为准；编辑器文档、选择与撤销状态以 C# 编辑器服务为准；网页不另维护一份可以反向覆盖引擎的场景副本。

## 4. 关键决策轴与结论

### 4.1 先外部浏览器，后决定是否嵌入

第一步使用外部浏览器连接仅本机访问的 C# 服务，避免同时引入网页容器、原生窗口组合和通信协议三类问题。

协议稳定后，再评估 WebView2 或 Chromium 嵌入。嵌入只替换网页宿主和传输适配器，不重写编辑器服务与命令协议。

### 4.2 通信采用命令、结果、事件三类消息

- **命令**：携带请求编号、命令类型、编辑器对象编号与参数。
- **结果**：携带对应请求编号，以及成功结果或可诊断错误。
- **事件**：通知对象变化、对象失效、选择变化和后台任务进展。

网页只使用编辑器对象编号。编号到引擎句柄的映射由 C# 编辑器服务持有，对象销毁或重绑后必须能让旧编号失效。

首版可以使用 JSON 表达低频编辑命令；只有实测证明文本协议成为瓶颈后，才单独设计高频二进制通道。

### 4.3 网络回调不直接调用引擎

网络接收方只负责解析、校验和入队。引擎调用统一由引擎主线程上的托管入口执行；现有 `Host.Tick` 是可用挂点，正式接入方式留待 proposal 决定。

长时间操作不能借网页请求阻塞引擎主线程。需要等待的任务必须显式建模，并通过事件报告完成或失败。

### 4.4 原生视口不经过网页图像传输

保留 C++ 原生窗口和现有 Vulkan/D3D12 后端。初期允许网页与原生视口分窗；后续若合并到同一编辑器壳，再单独处理视口区域、输入焦点、缩放和尺寸同步。

不把每帧画面读回 CPU 后发送给网页，也不要求为了编辑器界面再实现一套 WebGPU 渲染后端。

**2026-11-22 修订（用户裁定）**：简单分栏合并**纳入首切片**——一个原生窗口，WebView2 以子 HWND 嵌右侧面板条，原生渲染占左侧视口区域（SetViewPort/SetScissor），尺寸回调同步子窗口布局与视口。首切片三角形静态无场景交互，输入路由代价小。**复杂合并（多视口、相机交互、动态布局、焦点路由）仍延后**。逐帧读回传输仍排除；展示证明用一次性 OS 屏幕捕获（测试断言，非显示路径）。

### 4.5 原生事件先轮询，回调后补

在回调投影尚未实现时，编辑器服务可以在主线程轮询已登记对象并发布差异。需要回调时，再补齐保活、注销与失效语义；不能生成只有签名、没有真实通知能力的桩。

**2026-11-22 调查更新**：本节前提已过时——10 类窗口回调（close/size/pos/focus 等）已由 `complete-csharp-window-system-bindings` 绑定到 C#，首切片直接用真回调做对象失效与尺寸/位置同步。**标题没有回调**（`IWindowSystem` 无 `SetWindowNameCallback`）：编辑器自己改的标题服务知道，外部改标题首切片不承诺同步。

### 4.6 2026-11-22 用户裁定与调查结论（首切片路线）

用户裁定（原话："可以不用浏览器吗，用自己的壳或者webview"→ 路线①；"其它按照你推荐的来吧，出一个change"）：

- **宿主路线①：自有窗口 + WebView2，单窗口分栏（2026-11-22 修订）**。编辑器服务用 `NewWindow` 建**一个**原生窗口（即 scene view 目标），WebView2 以**子 HWND** 嵌右侧面板条（宽度可配），原生渲染占左侧视口区域；全程引擎进程内。ImGui 式同窗体验：ImGui 走同一渲染管线，WebView2 走子窗口 + DWM 组合，机制不同效果可达（§4.4 修订）。代价已认：引入第一个 NuGet 包 `Microsoft.Web.WebView2`（微软第一方）+ 系统 WebView2 运行时（本机已装 157.0.4341.60，实测注册表）。
- **前端：纯 TS 无框架**（Vite 构建，node 仅开发期）。理由：首切片界面是薄投影，难点在服务层；与仓库零包依赖风格一致；服务层框架无关，将来面板多了再引框架不返工。
- **本地服务：.NET 内置 HttpListener + WebSocket**（零 NuGet 服务依赖，静态文件同进程托管，运行期不需要 node）。
- **程序集：同 Scripting.Managed.dll 新命名空间**（宿主只加载一个程序集，多程序集不支持——CSharpHost/README 已知限制；加载器零改动）。环境变量门控仿探针模式。**正式线程模型：一个后台监听线程（收包/解析/入队），引擎调用全在主线程 Tick 执行**；csharp-host 主规范无禁线程条款（2026-11-22 grep 核实），README"不建线程"是现状描述，随批更新。
- **协议：手写 v1**（约 6 条命令，C# 记录 + TS 类型镜像，一份 PROTOCOL.md 为准 + 握手版本号）。CodeGen 只做 C++→C#、无 TS 发射器（README 第一节），协议类型是 C# 原生对象，不经 CodeGen；同源生成等协议长大再立批。
- **撤销：命令级单层**（set-title/set-size 记旧值重放；对象失效报失效错误）。完整撤销栈延后。
- **多窗口**：架构自然支持（对象编号 + 事件广播给所有客户端），首切片仍只登记一个目标窗口（§5），协议从第一天带编号，扩展不返工。
- **ImGui 不碰**：IMGUIContext 全仓唯一消费方是 GPUBackendTester（TestIMGUI，渲染回归载荷，历史抓出字体白块/副窗偏移两 bug）；web 替代的是编辑器 UI 角色，不是测试角色。退役 ImGui 是独立决策，须先补等价回归覆盖。
- **技术未决（proposal 内验证任务）**：WebView2 控制器要求消息泵 UI 线程；引擎主线程经 `glfwPollEvents`（UpdateSystem）泵消息——能否直接贴主线程须实测，不行则回退专用 UI 线程（引擎调用仍走队列）。

## 5. 首个纵向切片

**2026-11-22 范围追加（用户裁定）**：目标窗口本身做成 **scene view**——渲染后端每帧向其左侧视口区域画一个三角形（糖层已验证路径，视口区域+同区域离屏捕获双目标）；面板以 WebView2 子 HWND 嵌**同一窗口**右侧（单窗口分栏，ImGui 式同窗）；验收加两层像素证据：离屏捕获中心红（渲染证明）+ OS 级屏幕捕获视口区域中心红（**展示证明**，用户原话"你起码得证明有展示渲染后端输出内容的能力"）。显示路径纯 GPU Present，回读只是测试断言；不走 backbuffer 读回（resource-readback 主规范禁令）。详见 change `editor-window-panel` design D2/D11/D12。

只做一个由 C# 编辑器服务登记的原生窗口属性面板：

1. 网页连接 C# 服务，读取该窗口的编辑器对象编号、标题和尺寸。
2. 网页发送修改标题与尺寸的命令，C# 在主线程调用现有窗口表面。
3. 网页收到真实执行后的结果和变化事件，而不是先把本地显示当成成功。
4. 原生窗口关闭或绑定实例变化后，旧对象编号必须失效，网页必须显示该状态。

### 能失败的验收方式

- 网页把标题改为本次测试生成的唯一字符串后，C++ 侧对同一窗口读回的标题必须逐字相同。
- 网页请求一个与当前值不同的合法尺寸后，C++ 侧读回的宽和高必须等于请求值。
- 使用不存在的对象编号发送命令时，必须返回明确错误，且不得调用任何引擎对象。
- 让底层窗口在编辑器服务之外失效后，旧编号再次执行命令必须报失效，不能崩溃或命中新对象。
- 网络回调到达后、主线程执行前，引擎状态不得提前改变；这条用于识别网络线程直接操作引擎的实现。

## 7. 被反驳或排除的结论

以下是设计阶段排除，尚未经过实现实测：

- **把 C++ 接口直接序列化给网页**：会让网页耦合 C ABI、句柄生命周期和引擎内部结构，故排除。
- **网络线程收到命令后立即操作引擎**：违反现有主线程调用边界，故排除。
- **为了网页界面把原生渲染改成 WebGPU**：编辑器方案不需要替换现有后端，故排除。
- **逐帧读回画面并传给网页**：增加同步与拷贝成本，且不是建立编辑器服务的必要条件，故排除。
- **第一步就嵌入网页容器并制作完整场景编辑器**：同时引入过多未决变量，故延后。
