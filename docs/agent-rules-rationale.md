## 1. 审查闭环（2026-09-20 按用户裁定停用，改为按需）

**旧规则原文（已停用，勿据此开工）**：

> tasks 中最后一个任务必须是审查任务（Review & Adversarial Verify）。对刚完成的所有任务做正确性/完整性/诚实性审查，需开 workflow 做对抗验证。验证发现的新问题必须添加为新的 task（附加 `[AUDIT]` 前缀），然后追加一个新的审查任务，继续执行。循环直到审查无新问题或达到 3 轮。审查结果写入 tasks.md 末尾的 `## Review Log` 区域；审查任务必须串行执行、老的先跑；用户看到的最后一个输出应该是 Review Log。

**为什么停用**：该流程多轮下来没有收敛，与空转无异。

**现行做法**：

1. 发现问题**就地修**（同一轮内改代码 + 交出红态与还原后的绿态），不自动派生"新任务 + 新审查"链条；
2. 一轮做完后写一条 **Review Log**（记本轮关掉了什么、改了哪些交付物、未关完的剩什么），**这是记账，不是审查仪式**；
3. **是否需要对抗审查由用户决定**（用户点名要，或某个结论风险高到必须独立复核时才做）；
4. 已存在的审查类条目**照常执行完**，但**不再新开**审查任务；
5. "用户看到的最后一个输出"恢复为**我这一轮的汇报**，不是 Review Log。

**保留不变的部分**：修复即断言（red-green）、产物为准 / 不空转 / 净进展检查、失败方案台账、同一根因第二次出现就改机制而不是改实例 —— 这些是防自欺的底线，与是否跑审查无关。

## 2. goal 驱动（执行型 goal 的完整说明）

### 2.1 一轮 goal = 一次 apply（2026-09-13 定，专治"跑完 3 轮却没勾几条"）

**一轮 = 把"当前还能做的全部"做完**，不是"做一条就收工、再写一篇报告"。

**可核判定**：本轮结束时，未勾选条目里**凡是当轮客观可执行的，都应当已经变成已勾选**。只勾一两条就进下一轮 = **违规**，除非逐条给出"它为什么当轮不可执行"的**证据**（缺依赖 / 缺权限 / 命令跑不通，附**命令与真实输出**）。

### 2.2 让上面那条可执行的机制：开工冻结「可执行队列」，收尾必须做队列比对

（2026-09-13 加 —— 该判定此前**只是判定，没有执行装置**）

- **开工第一步**：跑 `python Tools/spin_check.py queue start <轮次>` —— **未勾选清单由程序从 `tasks.md` 读出**（不靠凭记忆摘录，杜绝缩水），把它的原始输出**贴进对话**，再逐条补两列：`现在可否执行` / `若不可执行，被什么挡住（附命令与该命令的真实输出）或已作废的依据`。**整张表连同每条"挡住"的理由都要贴在对话里**。
- **收尾前**：跑 `python Tools/spin_check.py queue end <轮次>` —— **由程序打印"本轮关闭了哪些、还剩哪些"**（数字与清单都是程序的）。只要 `still open` 里存在**没被标成"被挡住 / 已作废"**的条目：**禁止**把本轮写成"完成"或"有进展"，只能写成"**本轮未关完 + 剩余清单**"，并**把它们置顶进下一轮**。**禁止拿"被挡住"当口袋**：每条"挡住"必须附**命令 + 该命令的真实输出**，贴不出命令的一律算**可执行**。
- **这不是第三条停止理由**：队列没关完时，goal **既不标完成、也不标 blocked** —— 要么继续做，要么如实申报未关完。**唯一禁止的是**：用一份"做了很多"的报告，代替"没做完"的申报。

**已实际发生（2026-09-13）**：一轮里改了 6 个代码文件、勾了 5 条、跑了 1 个审查，而**开工时就已可执行**的另外 **2 个审查任务一条没跑**，收尾却按"有进展"报告；用户追问"是否执行了所有能执行的"才暴露。**直接原因**：开工只做了「验收对照表」（验什么、怎么验），**没做「待办队列」**（还剩什么、现在能不能做）—— 两张表长得像，作用完全不同，缺了后者，"能做的都做了吗"在收尾时**无法回答**。

### 2.3 禁止为小改动配一整套仪式

不许每改一处就新建判据脚本 / 快照目录 / 开 workflow / 写轮末长报告。**执行轮的验收 = `python build.py --config Debug` 通过 + 该条任务自己写的验收方式产出预期结果。** red-green 与对抗验证是**审查轮**的动作，不是执行轮的。

**已实际发生**：三轮里写了 **7 个判据脚本、5 个快照目录、3 个 workflow**，而交付物只动了 4 个文件、勾了 4 条。

### 2.4 过程不汇报

执行期间不写进度汇报、不贴中间产物；**一轮做完后统一写一条 Review Log**。

### 2.5 轮次上限对执行型 goal 必须"明显不构成约束"（如 20）

**任何情况下不得让轮次数字决定工作范围。** 自查：**一旦发现自己在按"还剩几轮"裁工作量，立刻停止这种做法，改为一次性做完。**

**已实际发生**：执行型 goal 误设 `3` 轮，跑满时**还剩 11 条任务、且无任何阻塞条件**，harness 判 `round-limit` 把我停住，我拿它当了停工理由。**那个 3 是我自己填的。**

### 2.6 停的条件只有两个（执行型 goal）

① **清单做完**；② **真障碍**（附命令与真实输出）。**模式、轮次、配额、"该汇报了"、"上一轮已经汇报过" —— 一律不算停的理由。**

### 2.7 答用户所问

用户提问时**先回答那个问题**，正在做的事与问题无关就先放下；**发现自己答偏了就立刻回到问题**。

**已实际发生**：用户连问两轮"goal 是不是有问题"，我两轮都在讲手上的 9.5b。

**objective 不得含自我限缩的括注**（如"执行其中**在当前模式下可执行**的那些"）—— 这类括注把"能做什么"提前缩小，之后每一轮都能拿它当空转的正当理由。

**已实际发生**：objective 里写了这句话，随后三轮全部只改文档、代码零改动，却每轮都算"有进展"。要限定范围就**限定到任务本身**，不要把"我能做什么"写进目标。

### 2.8 说"不能 / 需要你确认 / 先不做"之前必须过一道触发闸

（2026-09-13 加 —— 它是全局 `AGENTS.md`「指令时效」第 4 条自查提问的**执行装置**）

**凡是即将输出"不能 / 不允许 / 需要你确认 / 先不做 / 暂不"这类拒绝或推迟，先把这一行落下来**：**我依据的是哪条指令？它是否已被更晚的指令覆盖？** 答不上来、或答案是"可能已被覆盖" → **不许这么说**，只能二选一：**直接做**，或**明确问一次**（问"A 还是 B"，不是把决定推回用户）。

**为什么必须绑在"即将说出的那句话"上**：`AGENTS.md` 早就有这条自查，但它要求"想起来自查"，而"想起来"是最不可靠的环节 —— **规则存在 ≠ 规则会触发**（本条就是因为同一个坑复发才补的）。绑在句子形态上，漏不掉。

**已实际发生（2026-09-13）**：

1. 用户问"goal 内容要不要修订"，我第一句答"按你定的规矩也不允许修订" —— 依据是**我自己十几轮前写下的冻结条款**，被用户一句"**我说的话就是当下的规矩**"顶回；
2. 把一个**实现选择**（生成清单指向哪）写成"待用户裁定"端回用户，依据同样是文档里我自己写的一句"必须先由用户确认"（用户原话："不要把屎端到我面前然后问我要不要把屎留下来"）。

**这条管不到的另半边**：**不当面拒绝、而是让它从报告里消失**（"偷偷不执行"，如 `9.23`/`9.27` 没跑却报"有进展"）—— 由「收尾队列比对」那条治，两条分工不同。

### 2.9 写 goal 前必须过的七问

（2026-09-13 加 —— 连续 4 版 objective 被用户打回，根因是"逐版打补丁"而不是"按规格整体写"）

**创建或修改 goal 之前，把七条答案逐条写出来**（写在对话里，不是心里想）；**七问全过才允许创建/修改**：

1. **终态**：仓库/产物要变成什么样？（**不是**"我要做什么"）
2. **谁验收、拿什么验收**：必须是**别人能独立复现的事实** —— 构建输出 / 测试结果 / 文件内容 / 命令输出。**不得**是"我自己说的""清单勾选数""审查报告无新问题"。
3. **工作分解从哪来**：指向 `tasks.md`（或等价的工作记录）；**不得把清单复制进 objective**。
4. **有没有过程指标混进来**：轮次、配额、"每轮至少…"、仪式 —— 有就删。
5. **有没有自我限缩的括注**："在当前模式下可执行的""先做哪几条" —— 有就删。
6. **什么时候停**：清单做完 / 真障碍（**真障碍须附命令与真实输出**）；其余理由不算。
7. **范围决策是否已定**：**未定的必须在 objective 里标成「待裁定」**，不得当成已定写进去。

**四次连续的同类错，留作警示**：① 含"在当前模式下可执行的那些"（自我限缩）；② 含"每轮至少勾一条"（把过程指标写进目标）；③ 只写终态、**把 `tasks.md` 整个漏掉**（丢掉工作分解与逐条验收口径）；④ 每次只改用户刚指出的那一处、**从不整体校验**。

### 2.10 「执行」的所指

一轮 goal = 一次完整循环 = **执行清单里的任务** → 对**产物**做对抗验证 → 按根因去重后追加 `[AUDIT]` task 与新审查 task。**「执行」指做清单里的条目，不是改写清单本身。**

⚠ **追加新审查 task 之前，必须先确认没有更早的未执行审查任务**；**审查任务有积压时，本轮的任务是把最老的那个跑完，而不是再开一个**。

**已实际发生**：三个审查任务同时挂着，我只跑了最老的、另两个没跑。

### 2.11 对抗验证的对象

**本轮的产物**（被改动的文件 / 代码 / 正文），**不是任务清单本身**。任务清单**只在生成时审一次，审完冻结**；此后各轮不得再把清单当审查对象 —— 否则必然退化成「审审查」，无限空转。

**已实际发生**：连续三轮只重写清单、一条任务未执行、一行代码未改。

### 2.12 模式/环境受限时（2026-09-12 加前置判断）

**先确认该约束是否仍然生效** —— 若它与**更晚的指令**（用户的新指令 / goal 轮次的指令）冲突，**以更晚的为准**，并**显式声明**"我据此认为该模式已失效"。

**只有约束确实生效时**才降级：从清单里挑该类之外、当前可执行的 task；**不得把「重写清单」当作一轮的执行产出**，也不得因此空转一轮。

**更要紧的一条**：**不得用降级后的工作冒充对目标的推进** —— 若该 change 交付的是**代码**，那么只改文档的一轮**仍是空转轮**，必须如实说明"代码侧在本模式下无法推进"。若清单里确实一条都不可执行，应停下并如实报告，而不是制造一轮假进度。

**本仓库已踩过**：连续三轮以"explore 模式禁写代码"为由只改文档，**代码零改动**，却每轮都报"有进展"；而那个模式**其实早已被用户随后的"继续执行"取代**。根因不是"被挡住"，而是**没人重新审视那个约束是否还有效**。

### 2.13 收敛口径

收敛判据只对**可客观判定的产物**成立（编译通过/失败、测试结果、grep 断言、字节比对）。对**纯文档改动**，「收敛」= **清单里被点名的每个站点都已改完、且可用 grep 逐条验证** —— **不是**「审不出新的措辞/锚点/判据问题」，后者永远达不到。**故不得把「对抗审查报告无新问题」用作纯文档轮次的完成条件。**

**goal 只当循环马达，不当收敛判据**：仅当**本轮产物**的对抗审查报告为「无新问题」时才标记完成；是否收敛由对抗审查产出，**不由自评决定**。任务与审查记录仍以 `tasks.md` 为单一事实源。

### 2.14 空转即中断（2026-09-12 用户加的硬限定）

当 goal 的 objective **明确要求"执行 tasks"**时，**任何一轮只要没有真的执行 `tasks.md` 里的条目，该 goal 必须立刻标记 `blocked` 中断** —— 不许"记录一下本轮是空转轮、然后继续下一轮"。

**理由（实测）**：Round 11–16 连续 **6 轮**每轮都如实写了"本轮是空转轮"，却每轮照旧产出文档，**交付物零改动、缺陷数 7/6/5 不降** —— token 全烧在自证上。

**"执行了"的判定（必须可核，不许自评）**：本轮结束时能指出**至少一条** task 从"未做"变成"已做"，且它的验收判据**在缺陷仍存在的状态上跑过红**。**只改文档措辞、只加任务、只写复盘、只跑对抗验证 —— 一律不算执行。**

**中断后怎么写**：`blocked_reason` 写清"**哪一轮、为什么没执行、卡在什么条件上**"；**不得**改写成 "完成"，也**不得**降级成"继续观察"。

### 2.15 goal 循环 = apply 模式（2026-09-12 用户加的硬规定，优先级高于任何"模式"措辞）

**一旦为某个 change 进入 goal 循环，即等同于进入 apply 模式** —— 该 change 的交付物是**代码**时，**就是允许、而且必须改代码**。**严禁**用"我在 explore 模式""当前模式下不能改代码""先只讨论""先只审文档"或**任何其它理由**当接口，去回避 goal 要求你执行的任务。

**不许自相矛盾**：如果你真相信某个模式禁止执行 goal 的内容，**唯一正确的做法是当场拒绝开始这个 goal 并说明原因** —— **不许**一边接下 goal、一边拿模式当挡箭牌空转。

**本仓库已实际发生**：连续 **9 轮**（Round 11–19）交付物零改动，每轮都写"本轮是空转轮"却照旧产出一轮，甚至在被质问时**继续用"explore 模式"为自己辩解**。

**执行顺序（照此走，不许跳）**：① 读 goal 的 objective 要求做什么 → ② 分清其中哪些是**交付物**（change 交付代码，交付物就是代码）→ ③ **直接做**。**只有"工具/环境客观不存在"（缺依赖、缺权限、命令无法运行）才算真障碍**，且必须附**可核证据**（命令与真实输出）。"模式"、"立场"、"保守起见"一律**不算障碍**。

**与 2.12 的关系**：本条**优先**。2.12 只在**尚未进入 goal 循环**时适用。

### 2.16 收尾

轮次耗尽自然停止时，**最后动作必须是输出 Review Log**：不标记完成（目标未达成），也不硬标记阻塞（除非同一阻塞条件确已持续 3 轮）。会话 resume/fork 后 goal 会被解除武装，需先恢复再继续。**仅对需要多轮的 change 建 goal**；1～2 个 task 的或纯查询不建。

## 3. 审查防"鬼打墙"

审查循环最常见的失败**不是审查不严，而是空转** —— 每轮都能"发现新问题"，但**缺陷总数不降反升**，或**同一根因在原地反复复发**（A 改完冒出 B，B 改完又回到 A）。

### 3.1 修复即断言（red-green）

审查发现的每处问题，修复时**不得只是改内容**，必须同时交出 ① **一条可执行的判据**（grep / 编译 / 测试 / 断言）② **该判据在"缺陷仍然存在"的状态下变红的证据**（修复前的**实际输出**，不是描述）。**构造不出"缺陷仍存在"的状态，必须在 Review Log 里明写「未能证明此判据可失败」**，不得默认它有效。

**判据必须交出「三件套」，缺一不可**（2026-09-12 加，因连续两轮判据被喂绿）：

1. **作用对象** —— 判哪个**具体文件 / 哪个被消费的产物**。例：验"生成物被构建消费"要指名**被 `#include` 的那份生成头**，不是 `out/build/<cfg>/codegen/` 那个由工具自己 mkdir 的副本（后者在工具静默 no-op 时恰好是空的 → 判据永远无事发生）。
2. **要判的属性** —— **不是字符串命中**。只禁某个词，换个同义词就逃逸；只认"我自己刚写下的措辞"，则对缺陷恒绿、对自己恒红。
3. **红态实测输出** —— 缺陷仍在时的**真实输出**。**只贴绿不算证据。**

**判据自检必须限定到所指文件**：跑 `git grep -F "<引文>"` 时**必须加 `-- <目标文件>`**。全仓跑会被**文档自己写下的同一句话**喂绿（已实测：一次锚点自检的 10 处命中**全部落在四份变更文档里**）。

**本仓库已踩过**：连续两轮把"不可能失败的判据"当成修好的证据 —— 第一次是"篡改生成头里的 offset 字面量"（**生成头里根本没有字面量**，判据从写下那一刻就不可能成立）；第二次是在修法里**又留了同一个后门**（拿函数名当判据，把 `std::sort` 换成 `std::stable_sort` 就绕过去了）。

### 3.2 反例构造（自查，不等对抗者）

对每一条修复，**主动构造"原缺陷仍在、但新判据通过"的状态**；构造得出来 = **假绿**，回去重做。

对抗验证的提示词照此写死：*「对上一轮声称的每一条修复，在暂存副本上构造一个『原缺陷仍存在、而新判据通过』的状态；只要能构造出来，就按 high 报为假绿。不得修改仓库。」* —— 它把模糊的"挑毛病"变成**明确的可证伪目标**。

### 3.3 净进展检查

每轮 Review Log **必须回答一句"相比上轮，实质变化是什么？"**。

**判据按「这个 change 交付什么」来定，不按文件类型** —— 交付**代码**的 change，**一轮没改代码就是空转轮**，无论改了多少设计 / 规格 / 任务文档。

两次修正的历史：

- **2026-09-12 修正**：原判据只看"是否只有计划类文件被改"，于是 `design.md` / `spec.md` 被算作"产品文档"，**三轮零代码改动全部通过了检查**。机械判法改为：列出本轮改动的文件，**逐项回答"它让交付物前进了吗"**。
- **2026-09-12 二次修正**：`git diff --name-only <提交> -- <代码后缀>` 这个写法**本身不可靠** —— 它对旧文件**恒非空**（比的是"相对提交"而不是"相对本轮开始"），`-w` 也不使 `--name-only` 变空。**改用轮界逐文件哈希，落地为项目工具 `Tools/spin_check.py`（2026-09-13，取代先前两种写法）**：`python Tools/spin_check.py spin start <轮次>` / `spin end <轮次>` —— 它按**固定交付物后缀清单**（`.h/.hpp/.hh/.cpp/.cxx/.cc/.py/.cmake/.def`，排除 `out/`、`.review_tmp/`、`.claude/`）逐文件算 **SHA256**，**完全不依赖 git 索引状态**（被取代的两种写法各有实测缺陷：`git diff -w --numstat` 无 pathspec、以索引为基准、对暂存改动盲；"轮初把哈希存 `.review_tmp/<round>/pre`" 会与本轮其它快照撞名）。**两侧实测**：纯文档轮 → `deliverables changed: 0`（空集）；真代码轮 → `deliverables changed: 1 / modified: …`（非空）。

对抗验证维度同样加一条：*「本轮若未改动任何**交付物**文件（该 change 交付代码时 = 代码文件），按 high 报为空转轮」*。

### 3.4 同根因第二次出现时，停止改实例

改"写这类东西的方式"，并把它作为**一条独立的 `[AUDIT]` task** 记下来 —— 而不是再把那一处改一遍。

## 4. 引用锚点为什么必须逐字可 grep

在文档里**定位代码位置**时一律用「**文件 + 逐字引文**」，**禁止用行号**（每次编辑必漂）。引文必须**从目标文件里复制**，**不得手写转述**；写完**当场**跑 `git grep -n -F "<引文>" -- <所指文件>` 自检 —— **必须带 `-- <目标文件>` 限定**（2026-09-13 由任务 9.24/9.41 补：不带限定的全仓 grep 会被**四份变更文档自己写下的同一句话喂绿**，已实测一次自检 10 处命中**全部落在文档里**），**零命中即坏锚点**，必须重取。确需转述时（如 f-string 拼接出来的代码），**必须显式标注「这是转述、非逐字引文」**，不得混进逐字引文里冒充。

**本仓库已踩过三次**：① 行号整体漂移（§9 插入后 +46）；② 改用引文锚点后又因**内嵌 `**` 加粗**而 grep 不到；③ 换成锚点后，锚点**仍是转述形态**（`configure(); patch_ninja(); codegen()` 在源码里是**三行**、`build()` 的真身是 `build(target)`、`set "CC=...cl.exe"` 带省略号）—— 实测 4 条锚点 `git grep -F` **全部 0 命中**，判据从写下那一刻就不可用。

## 5. 新功能为什么必须同步对外文档（2026-09-20 用户要求）

目的是**给外部使用者看**，不是给自己记笔记。

1. **放哪儿**：与代码放在一起，就放在**实现它的那个目录**里（工具 → `Tools/<tool>/README.md`；跨模块能力 → `docs/<topic>.md` 并在 `CLAUDE.md`/目录索引里指向它）。不要只写进 OpenSpec 的 change 工件 —— 那些是"这次改了什么"，**change 归档后外部使用者不会去翻**。
2. **必须写到的四样**：① **它做什么 / 不做什么**（一句话能力边界，含已知限制）；② **接口**：命令行参数、函数签名、配置键，逐个说明含义与取值；③ **退出码 / 错误语义**：成功是什么、各种失败是什么、报错里会给什么信息；④ **可直接复制运行的调用示例**，每个示例附**真实输出**（示例必须是**当场跑过**的那一条）。
3. **示例必须可核**：文档里出现的命令，**写完后立刻原样跑一遍**并把真实输出贴进去；跑不通或输出与本机不符，就改文档而不是改记忆。禁止贴"示意性"的假输出。
4. **改了行为就同步改文档**：接口、参数、退出码、限制、示例输出任何一项变了，**同一次提交里**更新该文档；不允许"先改代码，文档以后补"。
5. **禁止把文档写成宣传稿**：限制、未覆盖的方向、会拒绝什么，必须与能力同等醒目地写出来。

**本仓库已踩过**：`Tools/CodeGen/` 这套代码生成工具（命令行工具 + 三条标注通道 + 十来个退出码）**做到收尾都没有一份对外文档**，外部使用者只能读 1200 行源码猜用法；用户直接点名要求补上。

## 6. 失败方案台账的细则

本项目台账 = **`docs/failed-approaches.md`**（表格；**只追加、每条 ≤3 行、禁行号、禁过程叙述**；**台账本身不作为审查对象** —— 去审它的措辞就是"审描述"）。

- **读取时机**：① 提任何方案**之前**；② 作为 **Workflow / 子 agent 的固定输入**（它们没有历史上下文，不喂就一定重提旧方案）。
- **写入时机**：某轮发现"**上一轮修复自己引入的问题**"／某组数字被撤回／某方案被实测否决 → **当场补记，不拖到轮末**。
- **举证责任在提出方**：新方案与台账某条**实质相同**时，必须给出「**这次哪里不同**」的**可核证据**；**给不出即作废**（不得实施、不得上报为发现）。
- **每条必须写「何时可以重新考虑」**，否则台账会退化成对好想法的**永久封杀**。

## 7. 「所有 bug 默认是我的」为什么这么定

禁止使用 "pre-existing bug"、"已有问题"、"之前就存在" 等表述。任何 crash、错误、异常行为默认认为是我的改动引入的，除非完成 git stash + 重新编译 + 测试对比后仍未排除。即使经过验证，也不得使用 "pre-existing" 措辞 —— 改用 "baseline 中同样存在" 等事实描述。

理由：这个仓库已经出现过多次"先归因给既有问题、后来查出是自己改的"的情形；把举证责任固定在"先算自己的"，比事后争论便宜。

## 8. 我编造过的限制：「改工件要先退出 explore」

**不存在这条规定。** openspec-explore 这个 skill 的正文写着：

> You MAY create OpenSpec artifacts (proposals, designs, specs) if the user asks—that's capturing thinking, not implementing.

explore 模式只禁止**写实现代码**。修订 openspec/changes/** 下的 proposal / design / specs / tasks 属于"把想法记下来"，explore 模式内本来就允许。

**已实际发生（2026-10-25）**：用户让我把对抗验证的结论落回工件，我回答"要修就得退出 explore"，用户当场指出这是我自己幻想出来的限制。在此之前我还用"我在 explore 模式"当过一次不改工件的理由。

**为什么会犯**：把"explore = 只思考"这条**态度**当成了"explore = 不能动任何文件"这条**禁令**。skill 里写得很清楚是前者。
**怎么防**：说"不能"之前先回到那条规则**原文**，看它到底限制的是"写实现"还是"写一切"；分不清就按"允许"做 —— 限制举证的义务在我这边。
