## Context

生成代码现在有**两份**：一份在构建目录（`out/build/<预设>/codegen/<模块>/`，`CodeGen.exe -o` 的输出），一份在**源码树**（各模块 `generated/`，跟代码一起入库）。**编译器读的是源码树那份** —— 实测各模块的 include 路径都指向源码树：

```
CACore/CMakeLists.txt:55                     ${CMAKE_SOURCE_DIR}/CACore/generated
Interface/RenderInterface/CMakeLists.txt:16  PUBLIC generated
Interface/ShaderCompiler/CMakeLists.txt:12   ${CMAKE_SOURCE_DIR}/ShaderCompilerSlang/generated
D3D12RenderBackend/CMakeLists.txt:31         PRIVATE "generated"
VulkanRenderBackendNew/CmakeLists.txt:34     PRIVATE "generated"
```

**没有任何目标**把构建目录那层放进 include 路径。于是构建目录那份只用来做一件事：与源码树那份逐字节比，判断"入库的过期了没有"。这带来两个后果：

- 源码树里有 **189 个生成文件**（实测 6 个 `generated/` 目录合计 189 份），但**其中只有 18 份真在版本库里** —— 另外 171 份从来没入库（`git ls-files -- "*/generated/*"` 只有 18 行；`D3D12RenderBackend/generated`、`ShaderCompilerSlang/generated`、`VulkanRenderBackendNew/generated` 在 `git status` 里是未跟踪）。所以"改了类型忘了重新生成"这件事，对那 171 份连"入库副本"都不成立，对拍对的是本机文件；
- `--commit-generated` 每次把 189 份**逐个覆盖写**（内容没变也写）→ 修改时间全刷新 → 因为它们在 include 路径上，引用它们的编译单元被 ninja 判过期、**白编一遍**。

同时生成这段活本身也慢（实测 2026-10-04，Debug 预设）：

```
全量重生成   63 个类型 × 3 种产物 = 189 次调用，每次都要重新解析同一份头
             改动前的实现（`git show HEAD:build.py`）是**纯串行**：内层
             `for emit_flag, suffix in CODEGEN_EMITTERS:` 一行跑完三次再跑下一行，
             任何时刻只有 1 个进程；耗时以当场成对读数为准
什么都不改   configure 0.0 / codegen 1.4 / 编译 2.3 = 3.7 秒（实测，61 条跳过 + 2 条重跑）
             其中"问一句 ninja 要不要重建 CodeGen.exe"占大头，秒数以当场成对读数为准
```

约束与已知事实：

- `CodeGen.exe` 是**构建期**程序（源码 `Tools/CodeGen/`），引擎不链接 libclang（`libclang.dll` 由 `CALIB_CLANG_DIR` 指定，默认 `E:/Projects/CACodeGen/ExternalLibraries/LLVM`，约 100 MB，不入库）；
- 生成物的**字节是契约**：消费单元的编译期断言按它校验字段数、字段名与偏移，所以任何改动都不得改变产物字节；
- `build.py` 的生成段**排在所有编译之前**（先建工具 → 逐条生成 → 再编译引擎），这个顺序不变。

## Goals / Non-Goals

**Goals:**

- **生成代码不再进源码树**：产物只落构建目录，include 路径改指构建目录；仓库里不再有生成代码，也不再有"入库过期"这件事。
- **删掉 `--commit-generated` 与入库副本的逐字节对拍**（它们的唯一用途就是服务"入库"这个前提）。
- **把全量重生成做快**：一次解析出三份产物（189 次调用 → 63 次），并按核数并行多个类型。
- 常态构建的固定开销按时间戳跳过（configure、问 ninja），并把跳过了什么打印出来。
- 进度可见：生成段每条一行、带序号、立刻刷盘。
- 三档耗时（全量 / 改一个被标注的头 / 什么都不改）有可复现的命令与数字，写进 `Tools/CodeGen/README.md`。

**Non-Goals:**

- **不优化"生成器一变就全量重生成"这条规则**：它是刻意的保守选择（见 D2），本 change 只把它的代价压下来。
- 不改生成物字节、不改引擎运行时行为、不改 `CoreTests` 用例数与断言。
- 不给 libclang 建预编译头（要做先量收益，见 Open Questions）。
- 不动 ninja 自身的编译并发设置，也不动"每次构建都构建所有目标"这条既有规则。

## Decisions

### D1 工具是独立工程（自带 `project()`、独立构建目录）

- **做法**：`Tools/CodeGen/CMakeLists.txt` 自带 `cmake_minimum_required(3.12)` 与 `project(CodeGen CXX)`；顶层 `CMakeLists.txt` 不再 `add_subdirectory("Tools/CodeGen")`；`build.py` 在 `out/build/codegen-tool` 里单独 configure/编译它，产物仍落 `out/build/<预设>/bin/CodeGen.exe`（连同旁边的 `libclang.dll`）。
- **为什么**：它给引擎提供生成文件，必须先建好、先跑；独立之后，改它的源码不会牵动引擎那棵树的重新评估，它自己编不过也只红生成段。
- **备选与否决**：留在引擎树里加一个 `add_custom_target` 排序 —— 否：仍共用一次 configure/ninja 图，耦合没解掉。
- **连带影响（实测踩到）**：独立之后，引擎的 `compile_commands.json` 里 `Tools/CodeGen` 的编译单元是 **0 个**，而清单头两行（`TestEmit.h` 的 `EmitSample`、`TestKinds.h` 的 `Kinds`）仍要用真实环境解析 → 那两行报 `no compile env for module 'Tools/CodeGen'`。
- **处置：把归属改对，不引入任何手写清单**（返工 6.8）。第三列的语义是"**真正编译这个类型的模块**"，环境的推导规则一个字不改，变的只是那两行写谁：
  - 这两个夹具的产物是被 `Test/CoreTests` 的编译单元 `#include` 的（`Test/CoreTests/CMakeLists.txt` 里本来就有指向 `generated` 的 include 路径），所以归属改成 `Test/CoreTests`；
  - 该模块能推出一份干净环境（实测 10 个编译单元、13 个 include、7 个宏、无强制包含；整个 `Test` 目录会因为两套宏被拒绝，所以取更具体的 `Test/CoreTests`）；
  - 产物落点随之从 `Tools/CodeGen/generated/` 变成 `Test/CoreTests/generated/`（出仓之后是 `out/build/<预设>/codegen/Test_CoreTests/`），消费方的 include 路径同步改（3.1 的站点之一）；
  - 临时的 `CODEGEN_ENV_FALLBACK`（`Tools/CodeGen` 借 `CACore`）**删掉**。
- **备选与否决**：① 给独立工程打开 `CMAKE_EXPORT_COMPILE_COMMANDS`、读它自己那份 —— 否：那份文件记的是"**怎么编译生成器**"（为链接 libclang 配的参数），与"怎么解析被标注的头"是两码事，生成器也不给自己出码，拿它当环境只是把"借 CACore"换成"借 CMake 的手"，问题一点没解决；② 留着借用表、在基线 spec 里补一条例外 —— 否：那正是基线 spec 禁止的"手写 include 清单"，能删掉就不该留。

### D2 保留"生成器一变就全量重生成"，不为省时间换掉它

- **做法**：账本里"`CodeGen.exe` 的内容哈希"这一项照旧参与指纹；它一变，63 条全部重跑。
- **为什么**：脚本**无法**判断你改的那一行是注释、错误提示还是出码逻辑。任何"先跑一个小样比一比字节、再决定要不要全量"的做法，都必须保证那个小样覆盖了**所有**形状；新增形状（新容器、新种类、新包装规则）时一旦忘了同步，就会漏重生成 —— 而漏掉是**静默的错**，比慢几分钟严重得多。
- **代价**：改生成器的那段时间里每次构建都要全量重生成。本 change 用 D4+D5 把这段时间压到几十秒的量级（具体数字按 2.1 的当场成对读数取）。
- **备选与否决**：① 比小样字节再决定（写进过 tasks，2026-10-04 用户否掉）—— 否：把"安全"换成"快"，且漏判静默；② 让 `CodeGen.exe` 自己打印一个需要人工维护的格式版本号 —— 否：靠"记得改"的约定在本仓库已多次失效。
- **⚠ 这条规则的判据有个缺口，修法已定在 D8**：指纹里的"输入"原本只算清单里那一份头，改它 include 的依赖头会被判"没变"而跳过（实测 63 行里 62 行如此），正是 D2 要防的**静默漏重生成**。**D8 落地之前，D3 的第 3 步（删掉入库副本对拍）不许做** —— 那是当前唯一的兜底。

### D3 生成物出仓：只落构建目录，include 路径改指构建目录

- **做法**：删除源码树里各模块 `generated/` 目录及其 189 个文件；各模块 `CMakeLists.txt` 的 include 路径从源码树改成 `${CMAKE_BINARY_DIR}/codegen/<模块>`；`build.py` 去掉"写库"与"逐字节对拍"两段。
- **为什么**：① 仓库不再被生成代码污染，也不再需要"记得重新生成并提交"；② 每次构建都现场生成，生成失败或某类型被拒会**当场红**，"过期"这种状态根本不存在，对拍机制随之失去意义；③ 顺带消掉 `--commit-generated` 白刷新 189 份文件导致的**白重编**。
- **代价（说清楚）**：① **构建从此必须有 libclang**（`CodeGen.exe` 跑不起来就编不了引擎）—— 现在"入库副本"的存在意义正是让没有 libclang 的机器也能编；② **新克隆/IDE**：第一次构建之前 IntelliSense 找不到那些生成头，构建一次之后正常；③ **`--no-codegen` 失去意义**并应删除（产物不入库，就没有"用上次的产物只编译"这回事）。
- **备选与否决**：保持入库、但"内容没变就不写"（原计划）—— 否：用户明确不要仓库里留生成代码；且"入库 + 对拍"本身要一直维护两份事实。
- **⚠ 出仓带出一条硬约束（2026-10-05 实测踩到）**：产物所在的目录**本身就在解析的包含路径上** —— `Interface/ShaderCompiler/header/Compiler.h` 直接 `#include "UniformElement.Serialization.h"` 等 48 份生成头。所以生成段 MUST NOT 在跑工具之前删掉这一行的产物：实测那样做会让解析当场找不到文件（`--emit-all exit 6 … file not found`），引擎编译跟着红（C1083），而且被删掉的产物再也补不回来（要靠 6.9 的仓库外快照恢复）。
  **替代判据**：`CodeGen.exe` 报出它这一次**真正写出了哪些产物**（`CodeGen wrote: <路径>`），`build.py` 要求这一行的三份都在名单里，缺一份就判这一行失败。这比"先删掉再看有没有"更准，也不动消费者读的那个目录。
- **⚠ 冷启动是死循环，得先占位（2026-10-05 实测）**：`Interface/ShaderCompiler/header/Compiler.h` 直接 `#include` 了 **48 份生成头**，而生成这些类型的行**又必须先解析这个头** —— 构建目录空的时候谁也出不来。实测：把 `ShaderCompilerSlang` 的 72 份产物挪走再构建，**47 行**以退出码 6 失败（失败顺着 include 链扩散，不是那一个模块的 24 行）；把整个 `codegen/` 删掉再构建同样是全红。
  **处置**：登记一行要跑的时候，先给它的三份产物放一个**占位文件**（只在"文件不存在或还是占位内容"时放），让别的行的 `#include` 解析得到；真正的产物随后由工具改名覆盖。失败的行的占位文件会被删掉，免得空头留在包含路径上误导编译阶段。
  **效果**：把整个 `out/build/x64-debug/codegen/` 删掉再 `python build.py --config Debug` → `重跑 63 条、跳过 0 条`、`BUILD SUCCESSFUL`，189 份产物与 6.9 的快照**逐字节相同**。新克隆的第一次构建因此真的能一次过（3.5 的 README 就是照这个写的）。

### D4 一次解析出三份产物（189 次调用 → 63 次）

- **做法**：`CodeGen.exe` 增加"一次调用同时出反射表 / 读写代码 / 哈希代码"的模式（例如 `--emit-all` 配一个输出目录参数），`build.py` 每条只调一次；产物仍分三个文件、命名与字节不变。
- **为什么**：现在一个类型启动三次，同一份头被 libclang **解析三遍**，解析是这里最贵的动作。一次调用出三份，等于把这块活直接砍到三分之一，且与并发叠加。
- **接口影响（必须同步）**：README 的接口表、退出码表（保留"一次给两个**不同**发射标志 = 退出码 10"这条既有规则，新增的是"一次出全部"这一个开关）、`verify_readme.py` 里的示例命令。
- **备选与否决**：继续三次调用、只靠并发 —— 否：那是用硬件掩盖三倍白干的活。

### D5 多条并行，上限有界

- **做法**：生成段按核数并行多个类型（先取 `min(8, 核数/4)`），失败消息按清单顺序汇总，保证输出稳定可读。
- **为什么**：每个 `CodeGen.exe` 实测约 80 MB 内存，32 逻辑核 / 43 GB 可用，只开 3 个进程纯属浪费。
- **代价**：日志会交错 → 每条打印一行 `[n/总数] 类型名` 并刷盘；上限保守是为了不与编译争内存和磁盘。

### D6 固定开销按时间戳跳过，并打印跳过了什么

- **做法**：CMake 输入（`CMakeLists.txt` / `*.cmake` / `CMakePresets.json`）都比 `build.ninja` 旧 → 跳过 configure（`--configure` 可强制）；`Tools/CodeGen` 下的源文件都比 `CodeGen.exe` 旧 → 跳过"问 ninja"（省下的秒数以当场成对读数为准）。
- **为什么**：这是常态构建里唯一"什么都没变却照付"的开销。
- **代价**：跳过是**静默**的风险点，所以必须打印一行"跳过了什么、为什么"，禁止无声跳过。

### D7 进度可见

- **做法**：生成段每条打印 `[n/总数] 类型名`，并 `flush=True`；完成的产物逐行打印"与谁一致"。
- **为什么**：日志重定向到文件时靠 Python 缓冲，外面完全看不出是"在推进"还是"卡住了"（本仓库为此误判过一次，白等好几轮）。

### D8 账本的"输入"按生成器**实际读过的文件**算，并盯住包含目录的增删

- **为什么**：产物字节由整条包含链共同决定。改一个不在清单里、却被清单头 include 的头（例如 `CACore/header/CACore/CAHash.h` —— `ShaderLibrary.h` 里 `programHash` 字段的类型就来自它），今天不会触发重跑：账本只哈希清单里那一个文件，判"没变"→ 跳过 → 编译继续吃旧产物、构建报成功。这正是 D2 要防的**静默漏重生成**；而本 change 又要删掉"入库副本逐字节对拍"这个兜底，所以 D8 必须排在 D3 的第 3 步之前。
- **做法**：① `CodeGen.exe` 把它这一次**真正读过的文件**列出来（libclang 的 `clang_getInclusions`，不用自己分析 `#include`），随产物一起交给 `build.py`；② 账本按这份名单**逐个文件存内容哈希**（路径 + 哈希），不再只存清单里那一个文件；③ 下一轮构建重新算这份名单 —— 内容变了、文件没了、名单里多出条目，都算"输入变了"，这一行重跑；④ 再加一道"**包含目录里多出或少了文件也算变**"：防的是"新加一个同名头把旧头挡住"，这种情况只看老名单看不出来。
- **代价**：账本从几十 KB 涨到几 MB；每轮多算上千个文件的哈希（实测算 252 个文件 0.03 秒，量级没问题）。哈希在单次构建内按路径缓存，不重复算。
- **不许走样**：这一条 MUST NOT 改变生成物字节，也 MUST NOT 让"什么都不改"的构建重新生成 —— 落地之后仍要能打印"重跑 0 条、跳过 63 条"。
- **备选与否决**：① 保守退回"`-I` 目录下有头比账本新就重跑" —— 否：判据落在**修改时间**上，`git checkout`、复制文件、切分支都会刷新时间，会把用不上这个头的行也一起重跑，代价更大且仍不如按名单准；② 不做，继续靠"入库逐字节对拍"兜底 —— 否：本 change 正要删掉对拍，留着不做等于把兜底拆了。

## Risks / Trade-offs

- **没有 libclang 就完全不能构建** → README 顶部写明前置条件与 `CALIB_CLANG_DIR` 的设置方法；`verify_readme.py` 的"没建好"提示语要说清怎么装、怎么设；构建失败信息要能区分"工具没建起来"与"引擎编译失败"。
- **IDE 首次找不到生成头** → README 写明"新克隆先跑一次构建"；必要时给 IDE 一条只生成不编译的入口（`python build.py --config Debug --codegen-only` 之类，若确有必要再加，不预先发明）。
- **改命令行接口**（D4）会牵动退出码表、README 示例与 `verify_readme.py` → 三处同步改，并有"命令原样可跑、0 处不符"的读数。
- **删除 189 个生成文件**是不可逆的改动：其中只有 18 份在版本库里（`git checkout` 能取回），另外 171 份从未入库、删掉只能重新生成 → 必须**删之前先快照到仓库外**（返工 6.9）；同时必须同步改另一个 change（`retire-legacy-serde-hash`）里以那三个源码树目录为扫描目标的判据，否则两边互相打脸（返工 6.10、5.2）。
- **README 的示例文本没有自动判据**：`verify_readme.py` 只比退出码、不比 stdout 文本，实测它的序列化 / 哈希产物示例（`Serialization.h`、`::cacore::serializer`、`Hasher.h`、`custom_hash_trait`）与真实输出**已经不符**，而判据照样全绿 → 返工 6.5、6.7。
- **全量重生成仍要几十秒** → 把三档读数写进 README，避免"以为没变快"或"以为已经很快了"。
- **并发打满内存/磁盘** → 上限 `min(8, 核数/4)`，用三档读数决定是否上调。

## Migration Plan

1. **返工先做**（tasks 第 6 节）：6.1（账本按生成器读过的文件算输入，见 D8）必须排在第 4 步（删掉入库对拍）之前 —— 它是那之前唯一的兜底；6.8（把清单头两行的归属改成 `Test/CoreTests`、删掉借用表，见 D1）与 6.9（产物快照）必须排在删源码树 `generated/` 之前。
2. `CodeGen.exe` 支持一次出三份（含退出码、README、示例同步）——先做，因为后面的读数都建立在它上面。
3. `build.py` 改成"每条一次调用 + 行级并发"；保留账本跳过与进度打印。
4. 生成物出仓：删源码树 `generated/`、改各模块 include 路径、删 `build.py` 里的写库与对拍、删 `--commit-generated` 与 `--no-codegen`。
5. 固定开销跳过与进度打印（已在工作区）收口，文档化。
6. 三档耗时读数写进 README；同步另一个 change 的措辞；完整构建 + `CoreTests` 收尾。
