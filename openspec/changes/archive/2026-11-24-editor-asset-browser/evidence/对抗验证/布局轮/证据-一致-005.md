## 3.3 与 spec 场景的对应关系（逐条核）

| spec 壳要求场景 | 场景要求的内容 | tasks 3.3 是否覆盖 |
| --- | --- | --- |
| 三分区同窗铺满客户区 | GetWindowCount 增量 1；读数行含面板矩形、视口区域与 dock 矩形且三者铺满客户区 | 覆盖窗口计数与面板/视口；**dock 矩形未列进断言清单**（只有 3.2 的实现描述提到），且视口高的期望值来源未定 |
| 单窗口尺寸同步 | 读数行显示两个控制器 Bounds 与视口区域同步为新三分区布局 | 覆盖（「改尺寸同步断言含两控制器 Bounds」），期望值同样缺 dock 高 |
| 运行时缺失明确禁用 | no-runtime 自检 | 既有断言已覆盖（Main.cpp:4704-4730） |
| 资源缺失明确错误页 | 面板或 dock 资源缺失返回说明错误页 | 3.3 未涉及（见面 4 证据的附注：该项在 tasks 3.2 里只有实现描述、无验收） |

## 为什么算矛盾（不是措辞问题）

- 3.3 的断言方向与 spec 场景一致，但**期望值来源**与 tasks.md 的验收口径冲突：仅剩「从读数行取 dock 矩形」这一条，会让「视口高 = 客户区高 − dock 高」变成用被测物验证被测物（读数行同时是布局的输出与断言的输入），判据永真。
- 既有测试的先例明确是「不设环境变量、把文档默认值写死」（面板宽 320），所以缺的不是写法，而是 dock 高的默认值（主张-一致-002）与「测试要不要显式设 dock 高」的决定。

## 建议修法

1. 3.3 明确：测试设 `CASCADED_EDITOR_DOCK_HEIGHT=<固定值>`，守卫清理该键，断言写死期望矩形（client、dock、viewport、panel 四个矩形逐值给出）。
2. 把「读数行含 dock 矩形」列入 3.3 的断言（对应 spec 场景第一条），不只写在 3.2 的验收里。
3. 若走「默认值写死」路线，先按主张-一致-002 把默认值钉死，再在 3.3 写明该数字。
