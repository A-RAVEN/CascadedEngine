`Main.cpp:5503-5516`、`5535-5543`（窗口 backbuffer 中心，逐字）：

```cpp
// 采样点 = **左侧视口区域中心**（不是整张 backbuffer 中心：右侧 320px 是面板条），按
// backbuffer 尺寸 / 读数 client 尺寸换算（两者应相等，缩放时也不抓偏）。
...
const uint32_t sampleX = static_cast<uint32_t>((bbViewport.x + bbViewport.w / 2) * bbScaleX);
const uint32_t sampleY = static_cast<uint32_t>((bbViewport.y + bbViewport.h / 2) * bbScaleY);
```

两条像素判据的采样点都是「读数行给的区域的正中心」，而被测渲染的三角形本来就画在渲染目标中心。**视口高是 520 还是 640、dock 高是 200 还是 1，只要场景图跟着变，采样点就跟着落在红色三角中心**。因此「像素读回中心仍按新视口区域精确匹配 (255,0,0,255)」这句话今天就已经成立，它对 dock 高的正确性零分辨力；能分辨的只有第二节那三组写死数字。

## 五、红态推演：一个合法配置能让 3.3 全绿而布局是错的

- 假设按 3.2 的「默认值与范围 1..客户区高−1」把 dock 高实现为 1px（在范围内、合法配置）：视口高 = 720−1 = 719，dock 高 = 1，读数行三矩形自洽 → 「铺满客户区」的方程全过。
- 像素采样点按读数行算（第三节）→ 中心仍是红色 → 两条像素判据全过。
- 3.3 若按字面把期望写成「视口高=ClientHeight−DockHeight」且 DockHeight 取自同一读数行，则上述布局不产生任何红。
- 结论：3.3 在缺少写死 dock 高的条件下是**对布局错误不敏感的自洽判据**（恒真方向），符合 blocking。

（4.2 的截图能看出 dock 高 1px 时列表不可见，但那是另一条无法执行/无法判不符的手工验收，见证据-验收-004；不能拿来救 3.3 的自动化判据。）
