# 证据 影响-003：线程边界的「运行期读数断言」用既有 NoteNativeCall 机制造不出来

对应主张：`主张-影响-003.json`（severity = blocking）

审查对象：`specs/editor-asset-browser/spec.md` 场景「监听线程零引擎调用（运行期）」；`tasks.md` 2.3 / 4.1；对照 `Scripting/Managed/Editor/EditorService.cs`、`Scripting/Managed/Editor/EditorSceneView.cs`、`Test/GPUBackendTester/Main.cpp` 的既有线程边界判据。

审查快照：`spec.md`（editor-asset-browser）`D5A8589119E11EEE…`、`tasks.md` `6A7FBBD466202D21…`（SHA-256 前 16 位）。

## 一、修订后的 spec/tasks 要求什么

`spec.md:64-67`：

> #### Scenario: 监听线程零引擎调用（运行期）
> - **WHEN** 执行 list-assets 命令
> - **THEN** 枚举/FileInfo/HasResource 的引擎调用 MUST 计入主线程命令计数（s_cmdCalls）；监听线程引擎调用增量 MUST 为 0（运行期读数断言，非仅代码路径核对）

`tasks.md:26`：

> ……→ **线程边界运行期断言**：list-assets 期间引擎调用计入命令计数（主线程 s_cmdCalls），监听线程引擎调用增量 0（沿用既有 NoteNativeCall 机制，非仅代码核对）。

这条是首轮修订加的；加的方向对，但「沿用既有 NoteNativeCall 机制」这个前提本身不成立。

## 二、既有机制只有一个全局计数，没有线程归属

`EditorService.cs:98-123`：

```text
private static int s_nativeCalls;
private static int s_cmdCalls;
private static bool s_inCommand;
...
internal static void NoteNativeCall()
{
    ++s_nativeCalls;
    if (s_inCommand)
    {
        ++s_cmdCalls;
    }
}
```

- 两个计数器都是 `static int`，`NoteNativeCall` 里没有 `Environment.CurrentManagedThreadId`，也没有任何 per-thread 计数；
- `s_cmdCalls` 只在 `s_inCommand == true` 时增长，而 `s_inCommand` 只在主线程 `ExecuteCommand` 的入口置真（`:651`）、`finally` 置假；
- 监听线程若调用 `HasResource` / `GetResourceRootPath` 并（假设）调 `NoteNativeCall()`，它只会把同一个 `s_nativeCalls` 加一，不会落到独立的「监听线程增量」里。

## 三、读数行只在 Tick 里写，且主线程每帧固定 +1

`EmitReadings` 只在 Tick 的 state==2 分支调用一次（`:163`），读数行在 `:1428` / `:1430`：

```text
EditorService.cs:1428: " nativeCalls=" + s_nativeCalls +
EditorService.cs:1430: " cmdCalls=" + s_cmdCalls +
```

而 `CheckObjectHealth` 每帧对每个对象调用 `WindowShouldClose` 并立刻 `NoteNativeCall`：

```text
EditorService.cs:520: shouldClose = obj.Window.WindowShouldClose();
EditorService.cs:521: NoteNativeCall();
```

`EditorSceneView` 里的渲染调用一处 `NoteNativeCall` 都没有（grep 计数 0），所以 `s_nativeCalls` 既不是「全部引擎调用」，也不是「线程可归属的调用」。后果：

1. **不 Tick 的窗口里没有新读数**：测试无法在「监听线程可能调用引擎」的 800ms 窗口内读 `nativeCalls`（文件里只有上一次 Tick 的旧行）。
2. **Tick 之后读数被主线程帧增量污染**：即使监听线程真的调了 `HasResource`，它加的一与 `CheckObjectHealth` 每帧固定加的一混在一起，没有线程 ID 就无法断言「监听线程增量 0」。
3. **`s_cmdCalls` 的正控也不成立**：门面调用（`GetResourceRootPath` / `HasResource`）不会自动调 `NoteNativeCall`；tasks 2.3 没有要求给它们补这一句。4.1 写「list-assets 期间引擎调用计入命令计数（主线程 s_cmdCalls）」，但实现里不补 `NoteNativeCall` 的话 `cmdCalls` 只会是 0（或只包含别的调用），4.1 要么红、要么被写成一个恒真断言。

## 四、既有线程边界判据为什么不能照抄

`TestEditorWindowPanel` 的线程边界是「发 set-title → 不 Tick → 窗口标题不变」（`Main.cpp:5201-5236`）：它依赖**标题**这个引擎侧可观察状态，网络线程如果直接调 `SetWindowName` 会立刻改变标题。

`list-assets` 没有等价的引擎侧可观察状态：监听线程若调 `GetResourceRootPath` / `HasResource`，不会改变任何窗口/标题/图状态，只可能改变计数器。也就是说，照抄「不 Tick 断言 X 不变」的写法没有 X 可断言，只能断言计数器——而计数器又不能归因。

## 五、建议改法（可执行）

1. **加线程归属**：在 EditorService 启动时记录主线程 ID：

```text
private static int s_mainThreadId;              // StartService 时 = Environment.CurrentManagedThreadId
private static int s_listenerNativeCalls;       // 仅非主线程调用时 ++
```

`NoteNativeCall` 里按 `Environment.CurrentManagedThreadId != s_mainThreadId` 分流，`EmitReadings` 增加一行 `listenerNativeCalls=`。4.1 断言：

```text
readings.lastCmd == "list-assets" && readings.cmdCalls >= 2 && readings.listenerNativeCalls == 0
```

其中 `cmdCalls >= 2` 的正控依赖在 `GetResourceRootPath()` 与每个 `HasResource()` 后补 `NoteNativeCall()`（tasks 2.3 现在没写这一句）。

2. **或者用可观察副作用**：让 list-assets 在监听线程只做入队；在命令真正执行前，任何「资产快照」字段都不改变。测试在「不 Tick」窗口读一个引擎侧可观察量（例如窗口标题/对象计数），断言它不变——但资产快照是 C# 内部状态，C++ 侧读不到，仍需读数通道，实际又回到 1。

3. **口径修正**：spec 场景里「枚举/FileInfo/HasResource 的引擎调用」应改成「门面调用（GetResourceRootPath / HasResource）」；`FileInfo` 与 `Directory.EnumerateFiles` 是 BCL IO，不是引擎调用，不能要求它们进 `s_cmdCalls`。

4. 如果决定不做线程归属，就必须把 spec 场景从「运行期读数断言」降级为「代码路径核对」并写明理由——但那等于承认首轮修订加的运行期判据是假的，不能保留现在的写法。
