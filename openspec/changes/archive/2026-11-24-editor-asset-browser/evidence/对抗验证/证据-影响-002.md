# 证据 影响-002：门面异常（1014）不在 list-assets 的捕获范围，客户端会再次静默挂起

对应主张：`主张-影响-002.json`（severity = blocking）

审查对象：`specs/editor-asset-browser/spec.md` 要求 1；`design.md` D3；`tasks.md` 2.3 / 4.1；对照 `CSharpHost/private/CSharpHost.cpp`、生成绑定 `out/build/x64-debug/codegen/bindings/cs_script__IResourceRegistry.Bindings.cs`、`Scripting/Managed/Editor/EditorService.cs`、`Scripting/Managed/Host.cs`。

审查快照：`spec.md`（editor-asset-browser）`D5A8589119E11EEE…`、`design.md` `BE438A9C9811FB8C…`、`tasks.md` `6A7FBBD466202D21…`（SHA-256 前 16 位）。

## 一、规格要求「门面失败」显式报错

`spec.md:5`：

> 门面失败 / 根非法 / 枚举 IO 错误 MUST 显式 E_ASSET_ROOT，MUST NOT 用 ok 空数组冒充成功。

`design.md:52` 把这条展开成三条：

> 门面未绑/根为空字符串/目录不存在 → 显式 E_ASSET_ROOT（不静默空列表冒充成功；目录存在但无文件 = 合法空态 ok 空数组）。

`tasks.md:17`（2.3）只把捕获范围写成 IO 异常：

> **处理内捕获 IO 异常（DirectoryNotFoundException/UnauthorizedAccessException/IOException，含 FileInfo 读取）转 E_ASSET_ROOT**（不许穿出到 Host.Tick 外层 catch 致客户端静默挂起）；门面未绑/根非法/目录不存在 → E_ASSET_ROOT

三条合起来，没有任何一行覆盖「门面调用本身抛异常」。

## 二、真实运行期的门面失败是 1014 异常，不是「未绑定」

`CSharpHost.cpp` 的 `RegisterResourceRegistry` 是无条件登记：拿不到 `ResourceManagingSystem` 时只是打错误日志，门面照样登记。

```text
CSharpHost.cpp:540: if (registry == nullptr)
CSharpHost.cpp:542: // 不静默不登记：门面照样登记，每个方法会经错误通道 1014 点名「注册表未就绪」。
CSharpHost.cpp:543: CA_LOG_ERR("CSharpHost：ResourceManagingSystem 没有登记；资源注册表门面仍登记"
CSharpHost.cpp:546: m_resourceRegistry = std::make_unique<ResourceRegistryFacade>(registry);
CSharpHost.cpp:547: SetInterfaceInstance(kBindingInterfaceIdcs_script__IResourceRegistry, nullptr, ...);
```

门面的每个方法先过 `EnsureRegistry`；注册表为空时写 1014（`ERROR_RESOURCE_OPERATION_REJECTED`）：

```text
CSharpHost.cpp:355: bool EnsureRegistry(char const* action) const
CSharpHost.cpp:357:     if (m_registry != nullptr) { return true; }
CSharpHost.cpp:361:     std::string text = "资源注册表未就绪（ResourceManagingSystem 没有登记）：";
CSharpHost.cpp:363:     Report(cs_script__IResourceRegistry_ERROR_RESOURCE_OPERATION_REJECTED, text.c_str());
CSharpHost.cpp:364:     return false;
```

`GetResourceRootPath` 与 `HasResource` 也走同一通道（`GetResourceRootPath` 在 310–329 行，`HasResource` 在 246–266 行）；`EnsureRegistry` 失败时返回空串/false，但错误码已经写进生成错误通道。

托管侧生成的表面每次调用后都 `ThrowIfFailed`，所以这些错误不是「返回空/false」，而是抛异常：

```text
IResourceRegistry.Bindings.cs:100: public const int ERROR_RESOURCE_OPERATION_REJECTED = 1014;
IResourceRegistry.Bindings.cs:84:  throw new IResourceRegistryException(code, ReadError(self));
IResourceRegistry.Bindings.cs:197: int result = IResourceRegistryBindings.HasResource(...);
IResourceRegistry.Bindings.cs:198: IResourceRegistryBindings.ThrowIfFailed(lease.Self);
IResourceRegistry.Bindings.cs:225: ulong length = IResourceRegistryBindings.GetResourceRootPathLen(...);
IResourceRegistry.Bindings.cs:226: IResourceRegistryBindings.ThrowIfFailed(lease.Self);
```

也就是说，当编辑器的资产根读取失败时，`list-assets` 处理里的 `GetResourceRootPath()` 或 `HasResource()` 抛的是 `IResourceRegistryException("资源注册表未就绪……（错误码 1014）")`，不是返回空串。

## 三、异常会穿出 ExecuteCommand，requestId 没有 result

`EditorService.ExecuteCommand` 的 catch 只有两类（`:773` / `:782`）：

```text
catch (ObjectDisposedException)
{
    if (s_objects.TryGetValue(command.ObjectId, out EditorObject disposed)) { ... }
    Enqueue(client, EditorProtocol.BuildError(command.RequestId,
        EditorProtocol.ErrorObjectInvalidated, "对象 " + command.ObjectId + " 已失效"));
}
catch (IWindowException ex)
{
    Enqueue(client, EditorProtocol.BuildError(command.RequestId,
        EditorProtocol.ErrorObjectInvalidated, "对象 " + command.ObjectId + " 的绑定失效（错误码 " + ex.Code + "）"));
}
```

`IResourceRegistryException` 不是这两类，直接穿到 `Host.Tick` 的外层 catch：

```text
Host.cs:366: s_lastError = "Tick 抛异常：" + ex.GetType().Name + ": " + ex.Message;
```

外层只把文本写进 `s_lastError` 并返回 `ErrException`，**不会给该 requestId 回 result**。设计 D3 自己已经用同样的机制解释过 IO 异常为什么必须在处理内捕获（「IO 异常会穿到 Host.Tick 外层 catch 吞成 s_lastError、该 requestId 无 result 客户端静默挂起」），门面异常走的是同一条路径。

另外，如果门面租约被 Dispose，`ObjectDisposedException` 会落进 `:773` 的 catch，被报成 `E_OBJECT_INVALIDATED`（对象 0 已失效），而不是 `E_ASSET_ROOT`——错误码语义也不对。

## 四、4.1 的「门面未绑」构造的是另一种状态

`tasks.md:26` 的失败面是：

> 门面未绑 E_ASSET_ROOT（CASCADED_EDITOR_SELFTEST=no-facade）

`design.md:52` 说明这个开关是「门控开但自检=no-facade 时跳过门面绑定」，并且写明「运行期 CSharpHost Init 无条件登记门面，无开关则该分支不可构造」。

这恰好说明：**「门面未绑」是自检专用的状态**；运行期真正的门面失败是「门面已登记、注册表缺失 → 1014 异常」。4.1 没有构造后者，tasks 2.3 也没有要求捕获后者，所以 spec 要求 1 的「门面失败」在真实运行期仍然会静默挂起。

## 五、建议改法

1. `list-assets` 处理内：

```text
try { root = registry.GetResourceRootPath(); ... HasResource(rel) ... }
catch (IResourceRegistryException ex) { 回 E_ASSET_ROOT（文本含 ex.Code 与 ex.Message）; }
catch (ObjectDisposedException)        { 回 E_ASSET_ROOT（门面表面已释放）; }
```

不要复用 `:773` 的 `E_OBJECT_INVALIDATED` 映射；`list-assets` 没有对象编号，那个错误码会误导客户端。

2. 4.1 增加可构造的红态。优先级从高到低：
   - 托管侧做一个会抛 `IResourceRegistryException` 的 `IResourceRegistry` 测试壳，让 Host 助手在自检时绑它（无原生改动，能验证 catch 与错误码）；
   - 或者在 CSharpHost 增加「注册表缺失」的进程级自检（需要改原生侧，与本批「不碰原生」冲突时要明确记录）；
   - 如果两条都不做，spec/design 必须写明这条失败面不可构造、只能代码走读核对，并说明理由——不能保留 MUST 却没有实现与判据。

3. tasks 2.3 的验收从「监听线程无引擎调用（代码路径核对）」之外，补上「门面异常 → E_ASSET_ROOT 回该 requestId，客户端不超时」这一条，并把它和 4.1 的「IO 异常不挂起」并列成同一类失败可见判据。
