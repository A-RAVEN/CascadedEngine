## 一、1.2 / 1.3 的全部验收只有“构建过”

> - [ ] 1.2 镜像 `EditorWeb/src/protocol.ts`：AssetEntry 接口、CommandName 加 'list-assets'、ResultOk.value 加 assets、EventMessage 加 'assets-changed'。验收：`npm run build`（EditorWeb）过；字段名与 PROTOCOL.md 逐字一致（对照）。

`npm run build` 的实际内容只有类型检查与打包：

## 三、`assets-changed` 的形状与现有 TS 类型冲突

`editor-window-panel` 的 MODIFIED 规范写“assets-changed 无 objectId”：

```text
PS> Select-String -Path 'openspec/changes/editor-asset-browser/specs/editor-window-panel/spec.md' -Pattern 'assets-changed 无 objectId'
spec.md:4: ……事件（object-changed / object-invalidated / **assets-changed**）广播给所有已连接客户端（assets-changed 无 objectId）。
```

当前 `protocol.ts` 的 `EventMessage` 仍要求 `objectId: number`，`fields` 只允许三个窗口字段：

```text
PS> Select-String -Path 'EditorWeb/src/protocol.ts' -Pattern 'event:|objectId'
protocol.ts:74: event: 'object-changed' | 'object-invalidated';
protocol.ts:75: objectId: number;
```

任务 1.2 只写“EventMessage 加 'assets-changed'”，没有说要改成“两个事件形状的联合类型”，也没有说 `fields` 的键集合。`npm run build` 不会因为一个未使用的联合成员而失败；这条形状要求仍然没有可失败判据。

## 五、已核实能红的部分

- **未知命令被拒**：`EditorProtocol.cs:173` 对 `s_knownCommands` 的成员检查会在形状校验阶段拒绝未知命令；既有 `TestEditorWindowPanel` 已用 `explode` 断言 `E_BAD_MESSAGE`（`Main.cpp:5327` / `5332`）。这条现有机制是真的，不是恒真判据。
- **`list-assets` 无 `objectId` 不被拒**：`EditorProtocol.cs:180` 的 `IsObjectScoped` 只列四个对象作用域命令；`list-assets` 只要不进这个集合，缺 `objectId` 就能通过形状校验。新用例若发送不带 `objectId` 的 `list-assets`，会在这一步真的报警。
- **构建失败**：`tsc --noEmit` 与 C# 编译能抓住语法错误、类型不匹配；它们抓不住的是“与 PROTOCOL.md 不一致”和“未使用的联合成员”。

## 六、建议改法

1. 新增可执行的协议一致性判据（脚本或 tester 断言）：从三处抽出 `AssetEntry` 字段集合、`list-assets` / `assets-changed` 名称、七个错误码、协议版本，逐项比较；判据必须能因字段名、版本号、错误码或命令集不一致而非零退出，并附红态样例。
2. 在 1.2/1.3 的镜像步骤里明确加 `E_ASSET_ROOT` 到 `ErrorCode` 联合与 C# 错误码常量；`assets-changed` 在 PROTOCOL.md 写死“无 objectId”与 `fields` 键集合，`EventMessage` 改成可区分两个事件形状的联合类型。
3. 2.2 的“默认提供者单测”要么落到可执行的 C# 测试入口（tester 里的 C# 探针或可被测试调用的 `AssetDisplay`），要么删掉“单测”并明确由 4.1 承担；不能只留“构建过”。
