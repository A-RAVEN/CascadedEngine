# 证据 影响-001：第 23 个编辑器用例与既有 TestEditorWindowPanel 在同一进程里互斥

对应主张：`主张-影响-001.json`（severity = blocking）

审查对象：`openspec/changes/editor-asset-browser/tasks.md` 4.1 / 5.1；对照 `Scripting/Managed/Editor/EditorService.cs`、`Test/GPUBackendTester/Main.cpp`、`proposal.md` 的「不动既有 22 用例」。

审查快照：`tasks.md` `6A7FBBD466202D21…`、`proposal.md` `7F0B81E81C1C5D46…`（SHA-256 前 16 位；2026-11-23 22:34 之后读取）。

`tasks.md:26`（4.1）：

> tester 第 23 用例 `TestEditorAssetBrowser`（Main.cpp + --list 登记）：……并设到 ResourceManagingSystem → 起编辑器服务 → WebSocket 发 list-assets 断言条目与真实文件逐条一致……

`tasks.md:31`（5.1）：

`proposal.md:28`：

三句合起来的含义：第 23 个用例要进全量，既有 22 条一条都不改。

## 二、真实代码：编辑器服务是进程级一次性状态机

状态赋值只有四处，没有任何复位到 0 的路径：

```text
PS> Select-String -Path 'Scripting/Managed/Editor/EditorService.cs' -Pattern 's_state\s*=\s*[0-9]'
EditorService.cs:144: s_state = 1;
EditorService.cs:150: s_state = 2;
EditorService.cs:289: s_state = 4;
EditorService.cs:298: s_state = 3;
```

Tick 的门控（`EditorService.cs:135`）：

```text
if (!Enabled || s_state == 3 || s_state == 4)
{
    return;
}
```

Shutdown 落状态（`EditorService.cs:240` / `:289`）：

```text
s_listenerStop = true;
...
s_state = 4;
```

既有 `TestEditorWindowPanel` 收尾主动停服务（`Main.cpp:5894-5903`）：

```text
// 收尾：先主动停服务（M11，隔离后续用例）……
::SetEnvironmentVariableA("CASCADED_EDITOR_STOP", "1");
pumpFrames(1);
::SetEnvironmentVariableA("CASCADED_EDITOR_STOP", nullptr);
if (!LogContains(readingsPath, "已关闭（测试请求停止"))
```

停服务之后 `s_state == 4`，下一个测试再设 `CASCADED_EDITOR=1` 也没有用：`Tick` 在 `:135` 直接返回，既不会 `StartService`，也不会建窗。

全量运行是同一个 `TestContext ctx`（`Main.cpp:8764`）、同一个模块管理器、同一个托管运行时；`TestEditorWindowPanel` 与 `TestCSharpAssets` 在 `--list`（`Main.cpp:8724` / `8736`）和 run-all（`Main.cpp:9099` / `9114`）里各出现一次。既有编辑器用例明确「收尾停服务隔离后续用例」，所以：

- 新用例放在 `TestEditorWindowPanel` **之后**（例如 `Main.cpp:9114` 与 `9116` 之间，最自然的追加位置）：新用例设 `CASCADED_EDITOR=1` 后 `Tick` 在 `EditorService.cs:135` 直接返回，编辑器服务永远不启动，连端口都不监听，4.1 的「起编辑器服务」第一步就失败。
- 新用例放在 `TestEditorWindowPanel` **之前**：新用例如果按既有规范收尾停服务，`TestEditorWindowPanel` 同样起不来；如果不停服务，`TestEditorWindowPanel` 会拿不到自己设的端口 18391（服务已经在本用例的端口上跑着），它的分栏窗口计数也会被上一会话污染——而 proposal 又不允许改既有 22 个用例。

也就是说，在「不动既有用例」的前提下，`s_state = 4` 这个状态让两个编辑器用例在同一进程里没有合法先后顺序。

## 三、为什么这是影响面漏算，不是实现细节

1. `--list` 的 23 条与全量 run-all 是两套顺序；`docs/testing.md` 还要求清单与 `--list` 逐条一致、测试注册在 `runTestWithDiagnostics` 列表里。新用例只写「Main.cpp + --list 登记」既没有指定 run-all 位置，也没有指定会话边界。
2. 5.1 的「（去掉新增）」已经假定新用例在全量里；如果为了绕开冲突把它排除在全量之外，5.1 的对比口径、`docs/testing.md` 的「当前 N 个测试，注册在 runTestWithDiagnostics 列表里」和「--list 23」会互相矛盾。
3. 这不是「新用例写麻烦一点」的问题：`EditorService` 的静态状态在托管程序集里，tester 进程只加载一次托管运行时；已有 `TestCSharpWindowCallbacks` 的注释说明「之后的用例不可能再用 C#」，证明测试是按单进程单运行时组织的，不能靠「再起一个进程」蒙混。

## 四、红态怎么构造（给验收用）

- 造一个只做「`CASCADED_EDITOR=1` → 两次 Tick → 发 list-assets → 收结果」的最小用例 A，再在它后面跑既有的 `TestEditorWindowPanel`（或反过来），观察第二个用例的读数：`state=starting`、`clients=0`、端口连不上、`LogContains(readingsPath, "已关闭（测试请求停止")` 只在第一个用例出现。当前工件的 4.1/5.1 没有这种先后断言，所以这条红态不会被发现。
- 如果改成可重启：同一进程里两个用例的 `[编辑器] 监听线程已启动` 行应各出现一次，两个用例的收尾各自有「已关闭（测试请求停止」行，端口各自绑定成功。

## 五、建议改法

1. **首选可重启**：`EditorService` 增加显式会话生命周期（`Start/Stop` 或 Tick 内复位），`Shutdown` 之后允许 `CASCADED_EDITOR=1` 重新 `StartService`；把「两个编辑器用例同进程先后跑都通过」写进 4.1/5.1 的验收，并在 `docs/testing.md` 里说明 run-all 的先后。
2. **次选分进程**：新用例只在 `--test TestEditorAssetBrowser` 下运行，不加入 run-all；在 tasks/spec/5.1 里把「--list 23 条、全量仍 22 条、新用例单独命令」写死，并接受它不在全量报告里的代价。
3. 无论哪条，都要在 tasks 4.1 里补一句「本用例与 TestEditorWindowPanel 的会话先后」和对应红态（当前工件完全没有提到 `s_state == 4` 这个既有状态）。
