# 证据-溯源-001：所谓「v1 纯加法」与新增错误码 `E_ASSET_ROOT` 都与生效规范冲突

> 定位以逐字引文为准；行号是 2026-11-23 审查时实测值，工件修订后会漂移，复核请用引文 grep。
> 本条不是措辞问题：它决定实现者照工件写会不会违反一条仍在生效的 MUST，以及 `openspec validate` 之外还有没有语义冲突。

## 一、主张摘要

- 主张编号：主张-溯源-001
- 攻击面：无中生有（把一个「会改变生效规范封闭枚举」的改动说成「纯加法、既有要求不变」）
- 严重度提示：blocking
- 工件：`proposal.md` / `design.md` / `tasks.md` / `specs/editor-asset-browser/spec.md`
- 一句话：生效规范把命令集与错误码集写成封闭枚举，本批新增 `list-assets` 已改变命令集语义、design 还允许新增 `E_ASSET_ROOT`；proposal 却写 Modified Capabilities 为「无」，tasks 又写「错误码沿用 E_*」——三处互斥，且 `E_ASSET_ROOT` 无任何协议层出处。

## 二、工件原文

`proposal.md:23`（Modified Capabilities 整行）：

> （无。`editor-window-panel` 的协议 v1 / 线程边界 / 单窗口分栏壳要求不变——资产命令是 v1 加法、资产区在既有右面板内；PROTOCOL.md 按既有「唯一事实源」要求更新。）

`design.md:45`：

> - 错误码沿用既有 `E_*`；根非法/门面未绑用 `E_INVALID_ARG` 或新增 `E_ASSET_ROOT`（PROTOCOL.md 定，三处同步）。

`tasks.md:9`（1.1 节选）：

> 错误码沿用 E_*（根不可用点名）；协议版本保持 1；既有命令/事件不动。

`specs/editor-asset-browser/spec.md:24`（节选）：

> 新增 MUST 仅为加法：命令 `list-assets`（非对象作用域）、事件 `assets-changed`、类型 `AssetEntry`……字段名/错误码逐字一致。协议版本 MUST 保持 1。……**既有命令/事件形状 MUST NOT 改动**。

`specs/editor-asset-browser/spec.md:29`（同一要求下的场景判据，本身也自相矛盾）：

> - **THEN** 字段名与错误码 MUST 逐字一致；协议版本 MUST 均为 1；**既有命令集 MUST 不变（只多 `list-assets`）**

（「命令集 MUST 不变」与「只多 list-assets」在同一句里互斥；按字面，要么命令集不变、要么多一条命令。）

## 三、生效规范原文

`openspec/specs/editor-window-panel/spec.md:36`（该能力唯一的协议要求，仍在生效）：

> 协议 MUST 为 JSON 文本帧：hello/welcome 握手携带 protocolVersion（当前 1），版本不符 MUST 回 E_PROTOCOL_VERSION 并关连接；命令（get-object / list-objects / set-title / set-size / undo）携带 requestId 与 objectId；结果携带 requestId 与 ok/value 或 error{code,message}，**按 requestId 回发起客户端**；事件（object-changed / object-invalidated）**广播给所有已连接客户端**。set-size 的宽 MUST > 面板宽、高 MUST >0，否则 E_INVALID_ARG。**错误码 MUST 限于 E_PROTOCOL_VERSION / E_UNKNOWN_OBJECT / E_OBJECT_INVALIDATED / E_INVALID_ARG / E_UNDO_EMPTY / E_BAD_MESSAGE。** 形状错或未知命令 MUST 回 E_BAD_MESSAGE 且不入引擎队列。`Scripting/Managed/Editor/PROTOCOL.md` MUST 是 C# 与 TS 两侧类型的唯一事实源，两侧逐字段镜像。

两个封闭点：
1. 命令集在括号里逐条列了五条；新增 `list-assets` 后，这句话在生效规范里就不再为真，按 OpenSpec 口径应有一条 `MODIFIED` 增量改这句话，而不是声明「无」。
2. `错误码 MUST 限于` 后列了六条；`E_ASSET_ROOT` 直接违反这条 MUST。即使退回 `E_INVALID_ARG`，也超出该码在 PROTOCOL.md 里的既有触发定义（参数非法：`set-size` 的宽或高 ≤ 0、宽 ≤ 面板宽、类型不是整数；`set-title` 的 title 不是字符串），「门面未绑 / 根不可用」不属于参数非法。

## 六、边界（我核了什么、没核什么）

- 核了：生效规范原文、PROTOCOL.md 原文、两侧镜像原文、`E_ASSET_ROOT` 全仓出现位置、`E_INVALID_ARG` 的既有触发定义。
- 没核：`openspec validate` 能否报出这类语义冲突（结构校验大概率通过，所以不能用它当判据）；也没有跑任何构建或测试。
- 为什么不是「措辞」：两条都是 MUST 级封闭枚举；照 design 写 `E_ASSET_ROOT` 会让生效规范当场为假，照 proposal 的「无」登记则新命令集没有规范增量——两种写法都留下「规范与实现不一致」的真实后果。
