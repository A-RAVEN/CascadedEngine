# 证据 003：监听线程边界仍只有“代码路径核对”，没有可失败测试

对应主张：`主张-验收-003.json`（severity = blocking）

审查对象：`specs/editor-asset-browser/spec.md` 场景「监听线程零引擎调用」；`tasks.md` 2.3 / 4.1；对照 `Test/GPUBackendTester/Main.cpp` 的既有线程边界用例。

审查快照：`spec.md` `83E0F933550EFAF0…`、`tasks.md` `82A8E1D6703946E2…`（SHA-256 前 16 位；2026-11-23 22:29:58–22:30:12 写入）。

## 一、spec 的 MUST 与 tasks 的判据不是一回事

spec 场景（`spec.md:64-67`）：

> #### Scenario: 监听线程零引擎调用
> - **WHEN** 核对资产枚举代码路径
> - **THEN** 枚举/FileInfo/HasResource MUST 都在主线程 DrainInbound/ExecuteCommand 路径；监听线程 MUST 无引擎绑定调用（沿用既有边界判据）

任务 2.3 的验收（`tasks.md:17`）：

> 验收：构建过；2.4/4.1 断言过；监听线程无引擎调用（代码路径核对）。

“代码路径核对”是人工走读，不是可执行判据；它不能因为实现把 `HasResource` 或 `Directory.EnumerateFiles` 放到监听线程而变红。

任务 4.1 的步骤（`tasks.md:26`）已经包含条目一致、刷新 +1、空根、根非法、门面未绑、IO 异常，但没有任何线程边界步骤：

```text
tasks.md:17: 验收：构建过；2.4/4.1 断言过；监听线程无引擎调用（代码路径核对）。
```

## 二、既有线程边界用例只覆盖 set-title

`TestEditorWindowPanel` 的线程边界断言是“发命令后不调 Tick，窗口标题不变”：

```text
PS> Select-String -Path 'Test/GPUBackendTester/Main.cpp' -Pattern '命令发出后、下一次 Tick drain 之前|E_EDITOR_THREAD_BOUNDARY'
Main.cpp:5201: // ⑤ 线程边界：命令发出后、下一次 Tick drain 之前，C++ 侧标题必须不变（网络线程不许直接动引擎）。
Main.cpp:5207: // 只泵引擎消息、**不调 Tick**：监听线程有时间收包入队，但主线程没有 drain —— 标题必须不动。
Main.cpp:5234: fail("E_EDITOR_THREAD_BOUNDARY", "drain 之后标题没有变成新值");
```

这条判据依赖“标题”这个可观察状态；`list-assets` 没有等价的“标题不变”。如果新实现把 `HasResource` 直接放在监听线程调用，它仍可以把结果发回客户端，4.1 只等结果，不会红。现有 `EditorService` 里已经有 `s_cmdCalls` / `s_nativeCalls` 与主线程 `DrainInbound`，可以直接复用，但当前没有任何针对 `list-assets` 的断言：

## 三、已核实能红的部分（本轮修订已补的失败面）

- **门面未绑**：tasks 4.1 已加入 `CASCADED_EDITOR_SELFTEST=no-facade`，2.1 也写“no-facade 时 list-assets 回 E_ASSET_ROOT”；这条现在有构造路径，不再是本主张对象。
- **枚举 IO 异常**：tasks 2.3 已加入捕获转 `E_ASSET_ROOT`，4.1 已加入“根指向不存在目录”步骤；这条现在有测试步骤。
- **未知命令**：见证据 001，既有 `explode` 断言能红。

## 四、建议改法

把 4.1 的线程边界写成可失败步骤：连接后发 `list-assets`，只泵窗口消息、不调 `Host.Tick`，断言在超时窗口内没有结果、`cmdRequest` / `cmdCalls` 不变；再 Tick 并断言结果到达。或者在 C# 侧对 `GetResourceRootPath` / `HasResource` 的包装里记录调用线程号，测试断言监听线程调用次数为 0。只写“代码路径核对”不能算验收；既有 `set-title` 的标题不变判据要照抄成 `list-assets` 版本，不能拿旧用例代替。
