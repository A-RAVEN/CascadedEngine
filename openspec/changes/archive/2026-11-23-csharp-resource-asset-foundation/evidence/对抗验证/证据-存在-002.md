## 一、产物结构：加一个接口必然改三份聚合产物、必然加两份产物

门面编号 13 一登记，这两个文件各多一行 —— 字节必变。加两行之后，`BindingRegistry.Bindings.cpp`（表数组/登记函数）随 `.h` 同源生成，同样必变。三份聚合产物不可能「逐字节相同」。

### 一个接口两份产物，不是「一份」

```text
$ Select-String -Path 'build.py' -Pattern 'CODEGEN_BINDING_PRODUCT_SUFFIXES'
L1182: CODEGEN_BINDING_PRODUCT_SUFFIXES = (".Bindings.cs", ".Bindings.cpp")
L1179: # 逐接口绑定的期望产物形状（… 23 个 stem 全部两件套）
```

所以 spec 的「新增产物只有门面那一份」本身就与生成器规则不符：门面至少出 `.Bindings.cs` + `.Bindings.cpp` 两份；若 `--emit-registry` 另出分片，还要算分片（上一批把 `reverse-resource-importer.registry.part` 也计进了「多余」）。

## 二、上一批的实测读数（同类动作的既有事实）

`openspec/changes/archive/2026-11-23-resource-importer-refactor/evidence/0.2-5.1-5.2-封存回归换锚.txt` L16-19 逐字：

```text
- 旧锚（213）对拍当前产物：缺失 0 / 不一致 3 / 多余 5。
  不一致 3 = BindingRegistry.Bindings.cpp/.h + EngineApi.Bindings.cs（宿主登记表新号 11=ResourceImporter/12=ResourceImporterProductions，合法变化）。
  多余 5 = ResourceImporter.Bindings.cpp/.cs + ResourceImporterProductions.Bindings.cpp/.cs + reverse-resource-importer.registry.part（导入器反向产物）。
  既有正向产物（8 接口 .Bindings.cpp/.cs 等）不在差异里 = 逐字节回到旧锚。
```

也就是说：**上一批加两个接口时，「不一致 3」被明确登记为合法变化**，判据用的是「差异逐文件指认完毕，无指认不了的差异」，不是「每份产物逐字节相同」。本 change 沿用「每份逐字节相同」等于把上一批判红的同一现象重新判红，且 tasks 5.1 的「任何一份产物差异即红」让本 change 永远不可能收尾。

## 三、锚文件本身的两个数（避免混读）

```text
旧锚封存件.txt: 213 行（头：# 条目数 213）
新锚.txt:       218 行（头：# 条目数 218）
```

本 change 的 tasks 5.1 / spec 场景写「旧锚 218 份」—— 语义上指「本批开工前的基线 = 上一批的新锚 218」，数是对的；但同一归档里还存在一份名字叫「旧锚」的 213 条文件，字面容易读岔。建议直接写文件名（`archive/2026-11-23-resource-importer-refactor/evidence/新锚.txt`，218 条），并把本批新锚的预期写成「218 + 门面产物份数」，份数以实测登记。

## 四、能失败的新判据（建议写法）

1. 8 个既有正向接口 + 4 个反向接口的 `.Bindings.cs/.cpp`（含 `fixture/` 段）与旧锚逐字节相同 —— 差异即红，无需人工指认。
2. 三份聚合产物的每一处差异必须在 `evidence/5.1-旧锚比对.txt` 里指认到「门面编号 13 的登记行」；指认不出来的差异即红（保留严格性）。
3. 新锚条目数 = 旧锚 218 + 实测新增份数，且新增份数必须与 `CODEGEN_BINDING_PRODUCT_SUFFIXES` 的「两件套」规则对得上。

三条都能失败：删掉门面编号 13 的登记行 ⇒ 第 2 条红；把某个既有接口产物改一个字节 ⇒ 第 1 条红；新锚少登记一份 ⇒ 第 3 条红（现有 `check_binding_baseline.py` 的「条目数与实际行数不符 ⇒ 退出 2」已提供该机制）。
