# 证据-溯源-003：CoreTests「全绿」没有命令、没有份数，验收不可失败

> 定位以逐字引文为准；文中行号是 2026-11-23 审查时的实测值，主循环修订后可能漂移。

## 一、主张摘要

- 主张编号：主张-溯源-003
- 攻击面：无中生有（数字缺失导致验收不可核）
- 严重度：minor
- 工件：`openspec/changes/csharp-resource-asset-foundation/tasks.md`
- 一句话：`tasks.md:37` 的 5.1 只写「CoreTests 全绿」，没有命令、没有 `PASSED` 份数、没有可失败的读数；现有基线明确是 `CoreTests exit 0 PASSED 26`，工件却把 26 省掉。执行者无法判断「全绿」是 26 条还是少跑了几条，也无法在 CoreTests 红时定位。

## 四、为什么这是缺口

1. **「全绿」是散文，不是判据**：没有退出码、没有 `PASSED` 行数、没有日志路径；CoreTests 少跑 1 条也仍是「全绿」，跑的是旧产物也仍是「全绿」。
2. **份数已知却省略**：既有文档与上一批 evidence 都写了 26，本批只要照抄就能把判据钉死；省略后，执行者若写了 25 或 27 条，没人能凭工件判断哪个对。
3. **同句的验收不覆盖它**：5.1 的验收写的是「逐条比对零差异 + 新锚 221 自洽对账」，只覆盖绑定基线与 report，不覆盖 CoreTests；5.2 的场景对照也只列 registry 6 要求 / asset-layer 6 要求，没有 CoreTests 一行。
4. **不是编造错数字**：工件没有写 26 以外的错数；问题是该写的份数没写，导致验收不可失败。这属于「数字无出处 / 验收不可核」，不是「数字造假」。

## 五、改法

在 5.1 写死三样：

```text
命令：out\build\x64-debug\bin\CoreTests.exe
期望：退出码 0；输出中 `PASSED` 行数 = 26（若本批新增 CoreTests，写新的期望数并点名新增用例）
读数：evidence/5.1-CoreTests.txt
```

并在 5.2 的场景对照表里加一行「CoreTests 26 行 ↔ 5.1-CoreTests.txt」，这样「全绿」才有可失败的判据。

如果本批确实新增了 CoreTests 用例（例如把某个新门面直检放进 CoreTests），把期望数改成 26 + 新增条数，并在任务里点名新增用例名；不要用「全绿」代替份数。
