# 证据-溯源-001：Load 的「与导入器管线同构」是假的，失败加载会静默丢旧资产

> 定位以逐字引文为准；文中行号是 2026-11-23 审查时的实测值，主循环修订后可能漂移，复核时请用引文 grep。

## 一、主张摘要

- 主张编号：主张-溯源-001
- 攻击面：无中生有（把不存在的「同构」说成既有事实）
- 严重度：blocking
- 工件：`openspec/changes/csharp-resource-asset-foundation/design.md`
- 一句话：导入器管线是「先产出新对象 → 成功后才放旧条目 → 再注册」，设计却让 `AssetDatabase.Load` 走「先放旧条目 → 再读文件 → 再解析 → 再新建」；读文件或解析失败时旧资产已经被销毁，而规范把「注册表 MUST 无该路径条目」写成期望，等于把这次静默丢失固化。

## 三、源码与规范原文

### 3.1 导入器管线：先产出，后释放，再注册

命令：

```powershell
Get-Content 'GeneralResources/private/ResourceImportingSystem.cpp' | Select-Object -Skip 79 -First 14
```

真实输出（关键行）：

```text
80: 					IResource* produced = productions->NextResource();
81: 					if (produced == nullptr)
82: 					{
83: 						throw resource_creation_error("导入器产出了空资源（路径 " + relativePath +
84: 							"，标签 " + importer->GetTags() + "）");
85: 					}
86: 					// 单一强所有者：注册表里这一份 shared_ptr（与 CreateResource 逐字同构）。
87: 					castl::shared_ptr<IResource> resource(produced,
88: 						[](IResource* releasedObj) { delete releasedObj; });
89: 					// 重导入替换：先放掉同路径的旧条目再注册。MUST NOT 依赖 RegisterResource 的
90: 					// get_or_create —— 那会把旧对象静默留下来，重扫之后消费者仍拿到旧库。
91: 					m_ResourceManagingSystem->ReleaseResource(relativePath);
92: 					m_ResourceManagingSystem->RegisterResource(relativePath, resource);
```

顺序是：`NextResource()` 先产出（80）→ 产出为空先抛（83-84）→ 包 shared_ptr（87-88）→ **产出成功之后**才 `ReleaseResource`（91）→ `RegisterResource`（92）。

主规范 `openspec/specs/resource-importer/spec.md:31` 原文：

> ScanSourceDirectory MUST 对每导入器 Produce()→while HasNext() 拉 NextPath/NextResource→包 shared_ptr→先 ReleaseResource(path) 再 RegisterResource(path,shared_ptr)（重导入替换，MUST NOT get_or_create 静默留旧）→SerializeAll 无条件执行

注意规范这句的「先 ReleaseResource 再 RegisterResource」指的是**注册之前**先放旧，不是说「先放旧再去产出」；产出（`NextResource`）在 Release 之前。

### 3.2 设计给 Load 规定的顺序：先释放，后读，再解析

`design.md` 的 D6 `Load` 条与 `tasks.md` 的 3.3 条都写死了：

```text
HasResource(path) 为真
  → 先 ReleaseResource(path)
  → GetResourceFullPath(path)
  → File.ReadAllBytes
  → 按魔数分派解析
  → Create
  → 填数据
```

与 3.1 对照，第一处差异就是「释放」和「产出新对象」的先后：导入器先产出、失败不动旧；设计先释放、失败旧已没了。

### 3.3 失败场景把「旧条目已没了」写成期望

`specs/csharp-asset-layer/spec.md` 的「版本字节被改时加载点名失败」场景要求版本损坏时「注册表 MUST 无该路径条目」。按 3.2 的顺序，这条断言恰好会通过——因为旧条目在读文件之前就被释放了。它没有区分两种状态：

- 正常替换：旧条目退役、新条目注册；
- 失败加载：旧条目退役、**没有任何新条目**，旧资产数据丢失。

规范只写了「无该路径条目」，读起来像在防「留下半个新对象」，实际把「旧对象也没了」一起接受了。

## 四、对照表

| 步骤 | 导入器管线（源码实测） | 设计给 Load 的规定 | 失败时的后果 |
|---|---|---|---|
| 1 | `NextResource()` 产出新对象 | `HasResource` 判断 | 无 |
| 2 | 产出为空 → throw（旧条目未动） | `ReleaseResource` 放掉旧条目 | **旧资产已被销毁** |
| 3 | 包 `shared_ptr` | `GetResourceFullPath` + `File.ReadAllBytes` | 文件缺失/IO 错误 → 异常，旧资产已没了 |
| 4 | `ReleaseResource` 放旧 | 按魔数解析 | 版本/魔数/截短 → 异常，旧资产已没了 |
| 5 | `RegisterResource` 注册新 | `Create` 新建并注册 | 工厂异常 → 旧资产已没了 |

结论：「与导入器管线 ScanSourceDirectory 同构」这句话与源码相反；「先释放旧条目再新建」也不是导入器的顺序（导入器是「先产出、后释放」）。

## 五、为什么这是「无中生有」而不是措辞问题

1. 工件把「导入器管线的替换语义」当成既有规矩引用，但源码里这条规矩的核心是「**产出成功之前不动旧条目**」；工件只抄了「先 Release 再 Register」的半句，把「先 Release 再产出」写成同构。
2. 这个错误不是无害的：它直接决定了失败加载时旧资产是保留还是丢失。按工件实现，`Load` 一个损坏文件就会先把内存里的好资产销毁；规范又把「注册表无该路径条目」写成期望，测试会绿，用户不会收到「旧资产已丢弃」的提示。
3. 违反项目规则「静默降级（悄悄少给、让调用方以为拿到的就是全部）一律算缺陷」：失败异常点名了「解析失败的原因」，但没有点名「旧资产被丢弃」这个副作用，也没有恢复路径。

   HasResource(path) 为真 → 先读文件 → 解析 → 造对象（Create）
