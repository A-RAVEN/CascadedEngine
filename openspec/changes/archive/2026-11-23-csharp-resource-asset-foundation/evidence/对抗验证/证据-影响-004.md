# 证据-影响-004：同路径再 Create 时门面返回 void，C# 拿到的是没登记的新对象

## 结论

门面 `CreateResource(typeName, path)` 返回 void，意味着门面把 `ResourceManagingSystem::CreateResource` 返回的 `shared_ptr` 丢掉了。注册表在「路径已存在」时不会装入新对象，于是这条分支的静默结果是：

- 注册表继续持有旧对象；
- 工厂刚造出的新对象被门面丢掉并析构；
- C# 工厂队列拿到的新对象看上去创建成功，实际没有进注册表；
- `HasResource(path)` 仍为 true，不抛异常；`SerializeAll` 写的是旧对象的字节，`GetResource` 返回旧对象。

## 代码链

注册表实现（`GeneralResources/private/ResourceImportingSystem.cpp`）：

```cpp
castl::shared_ptr<IResource> CreateResource(castl::string const& typeName,
                                            castl::string const& path) override
{
    IResourceFactory* factory = GetFactory(typeName);
    ...
    castl::shared_ptr<IResource> resource(created, [](IResource* releasedObj) { delete releasedObj; });
    RegisterResource(path, resource);
    return resource;
}
```

`RegisterResource`：

```cpp
void RegisterResource(castl::string const& path, castl::shared_ptr<IResource> resource) override
{
    if (!resource) { throw ... }
    cacore::PathHash key(path);
    m_PathToResource.get_or_create(key, [&](cacore::PathHash const&)
        {
            return resource;
        });
}
```

`CACore/header/CACore/CASharedDic.h` 的 `get_or_create`：

```cpp
auto found = m_Map.find(inKey);
if (found != m_Map.end())
{
    return found;
}
```

键已存在时直接返回旧条目，连 `createFunctor()` 都不调用，所以新对象根本不会进表。`CreateResource` 仍然把新对象作为返回值交出去。

门面（design D2 逐字）：

```cpp
virtual void CreateResource(castl::string const& typeName, castl::string const& path) = 0;
```

design D2 的理由是：

```text
**CreateResource 返回 void 而不是 shared_ptr**：C# 侧对象经工厂跟踪拿（D4），不需要资源句柄；
```

这句话在「路径不存在」时成立；在「路径已存在」时，工厂队列拿到的正是那个没进表的对象。C# 没有办法发现差异，因为门面既不返回对象也不返回布尔。

## 工件只定义了 Load 的替换语义

design D6：

```text
`Load(path)`：`HasResource(path)` 为真 → 先 `ReleaseResource(path)`（替换，与导入器管线
`ScanSourceDirectory` 同构——MUST NOT 依赖 get_or_create 静默留旧）
```

这里明确知道 `get_or_create` 会静默留旧，但只在 `Load` 里绕开了它。`AssetDatabase.Create` 的语义是「门面 CreateResource → 出队 → 返回对象」，直接 `Create` 一个已有路径时没有任何前置释放或失败。

spec 的失败场景只覆盖：

```text
**WHEN** 用未注册类型名调 `CreateResource`，或工厂 Create 抛异常 / 返回 null
**THEN** MUST 抛错且文本点名类型名或原因；`HasResource` MUST 为 false；注册表 MUST 无空条目
```

没有「同路径已有资源」这一条。4.2 列出的失败面四项（坏句柄 / 未注册类型 / 损坏版本 / 缺失文件）也不含它。

## 影响

这不是「用户误用才会遇到」的边缘：`AssetDatabase.Create(typeName, path)` 是公开给 C# 脚本的入口，路径来自脚本或场景文件，重名是正常输入。更糟的是它完全静默：不抛、不返回空、`HasResource` 为真，只有落盘字节或后续 `GetResource` 才能看出对象不是刚造的那个；如果脚本只检查「Create 没抛异常」，就会把旧数据当新数据写出去。

## 改法

二选一，写进 spec 并加用例：

1. **明确拒绝**：门面在委托前 `HasResource(path)`，为真就抛 `resource_creation_error`，文本点名「路径已存在，Create 不替换，先 ReleaseResource」；
2. **显式替换**：门面先 `ReleaseResource(path)` 再委托，与 D6 的 `Load` 同构，并把「Create 即替换」写进 spec。

无论哪条，4.2 的失败面加一条可失败断言：同路径二次 `CreateResource` 后，要么抛且旧对象仍在，要么 `GetResource(path)` 必须是工厂队列刚交出的对象、`SerializeAll` 后的文件字节是新数据；探针阶段末仍断言队列为空。
