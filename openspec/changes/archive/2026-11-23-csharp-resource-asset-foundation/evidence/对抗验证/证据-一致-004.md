# 证据-一致-004：3.1 与 3.2 标 [P]，但 3.2 编译期依赖 3.1 的资产类型

## 主张

`tasks.md` 把 3.1（`Texture2D.cs` / `Mesh.cs`）与 3.2（`AssetFactoryBase` + `Texture2DFactory` / `MeshFactory`）都标成 `[P]`，即两条可并行。但 3.2 的两个具体工厂必须构造具体资产：`Texture2DFactory.Create()` 返回 `new Texture2D()`，`MeshFactory.Create()` 返回 `new Mesh()`。没有 3.1 的两个类，3.2 的代码不能编译，`[P]` 与实际依赖不符；按并行派发时 3.2 的「构建过」会先红。

## 原文

`openspec/changes/csharp-resource-asset-foundation/tasks.md`：

> 3.1 [P] `Scripting/Managed/Assets/Texture2D.cs` 与 `Mesh.cs`：继承 `ResourceBase`，字段与 `Serialize()` 格式按 design D5（魔数 CATX/CAMH + formatVersion=1 + 小端逐字段）。网格顶点布局 MUST 与 `SceneRenderer.cs` 常量逐字相同：步长 24、位置偏移 0、颜色偏移 12、颜色 float3（验收：C# 侧三个常数与 SceneRenderer 的 VertexStride/PositionOffset/ColorOffset 逐字对照，写死期望；错一个即 4.3 像素判据红）。验收：构建过；4.2 的 C++ 读盘逐字节对照过。

> 3.2 [P] `Assets/AssetFactoryBase.cs`（Create 入队跟踪）+ `Texture2DFactory` / `MeshFactory`（GetResourceType 写死类型名）。验收：4.2 的 FIFO 与阶段末队列空断言过。

## 既有代码的形状

`Scripting/Managed/ResourceProbe.cs` 里的反向工厂 `ProbeFactory`：

```csharp
public override ResourceBase Create()
{
    ++CreateCount;
    var resource = new ProbeResource();
    LastCreated = resource;
    return resource;
}
```

工厂在 `Create()` 里直接 `new` 具体资源类型。主规范 `openspec/specs/csharp-resource-factory/spec.md` 也规定：

> C# 公开抽象基类 ResourceFactoryBase（abstract GetResourceType / abstract ResourceBase Create()）

`AssetFactoryBase` 若要「在 `Create()` 里把新对象入队」，仍然要拿到一个具体对象；无论实现方式是 `new Texture2D()`、`new Mesh()`，还是基类调用子类的 `protected abstract ResourceBase CreateAsset()`，`Texture2DFactory` / `MeshFactory` 都在编译期引用 3.1 的类型。用 `typeof(Texture2D)` 或反射也只是换一种引用方式，依赖仍然存在。

## 依赖关系

- 3.1：定义 `Texture2D` / `Mesh`（被 3.2 引用）。
- 3.2：定义 `AssetFactoryBase` + 两个具体工厂；其中 `AssetFactoryBase.cs` 本身可以不引用具体类型，但 `Texture2DFactory` / `MeshFactory` 必然引用 3.1。
- 3.3：`AssetDatabase` 依赖 3.1 的资产类型与 3.2 的工厂——这一点 tasks 已经正确地把 3.3 与 3.1/3.2 分开、没有标 `[P]`。

## 为什么是 misleading

- 顺序执行时，按 3.1 → 3.2 做不会出问题，所以不阻塞。
- 但 `[P]` 的语义就是可并行；如果调度者据此把 3.1 与 3.2 交给两个执行者同时做，3.2 的代码在 3.1 落盘前无法编译，3.2 的「构建过」验收必然先红，执行者会误以为 3.2 自身写错了。
- 3.2 的验收「4.2 的 FIFO 与阶段末队列空断言过」把功能验收推到 4.2，但并没有取消 3.2 的编译依赖；把「验收推到 4.2」当成「可以并行」的理由不成立。

## 改法

1. 去掉 3.2 的 `[P]`，写成「3.2（依赖 3.1）」。
2. 或拆成两条：
   - 3.2a `[P]`：只写 `AssetFactoryBase.cs`（不引用 `Texture2D` / `Mesh`）；
   - 3.2b：写 `Texture2DFactory` / `MeshFactory`，明确排在 3.1 之后。
3. 如果流程上本来就不按 `[P]` 并行（单执行者顺序做），那么至少在 tasks 的表头说明 `[P]` 只是给多执行者调度的提示，并把 3.2 标成「需 3.1 先落盘」，避免读者误解。

## 复核方式

- 只创建 3.2 的文件、不创建 3.1 的两个类，执行 `python build.py --config Debug`：应出现找不到 `Texture2D` / `Mesh` 的编译错误。这就是 3.2 对 3.1 的红态。
- 反过来，先创建 3.1、再创建 3.2，构建应通过；这说明依赖方向是 3.2 → 3.1，而不是两者对等并行。
