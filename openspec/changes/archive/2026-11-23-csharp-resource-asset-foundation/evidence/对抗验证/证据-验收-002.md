# 证据 002：缺行红态引用的 9999 反例是另一条分支，构造不出缺行红态

对应主张：`主张-验收-002.json`（severity = misleading）
审查对象：`tasks.md` 1.3 的「缺行机制沿用既有 …（引用 Main.cpp 既有用例 L1865 的 9999 反例，不做产品代码变异）」
审查快照：`tasks.md` 14:46:34（SHA-256 `859d5f2495379678…`）

## 结论

`GetInterfaceApi` 有两条独立失败分支，文本不同：

| 分支 | 触发条件 | 错误文本 |
|---|---|---|
| ① `FindRoute == nullptr` | 编号不在路由表里（9999） | 「未知接口编号 9999：当前登记 12 个接口（…）」 |
| ② `route->role == Unregistered` | 编号在路由表里，但 `kBindingPolicies` 没有它 | 「接口 …（编号 13）没有在宿主角色登记表里登记（默认实例 / 目标类型表必须二选一）」 |

本批要证明的是 ②，引用的 9999 用例测的是 ①。两者不是同一条判据，错误文本也对不上 spec 场景要求的「点名编号未登记」。更麻烦的是任务同时写了「不做产品代码变异」——而删掉 `kBindingPolicies` 那一行重建，是唯一能在现有机制下构造 ② 的手段。

```cpp
                   route->name, interfaceId);

        return 0u;
    }

```

模板出处 `Tools/CodeGen/CodeGenMain.cpp:14569-14582`。`role` 由 `ApplyPolicies` 问宿主的 `CSharpHostBindingRequiresInstance` 决定（`CSharpHost.cpp:140-149`：命中 `kBindingPolicies` 返 1/0，未命中返 -1 ⇒ `Unregistered`）。

## 后果

- spec 场景「缺登记行时取表失败点名」的 THEN 要求「错误文本点名编号未登记」，本批没有任何读数能证明它；5.2 的「无『声称过但无读数』的行」在这一行上要么留空（等于承认没验），要么拿 9999 的「未知接口编号」文本冒充（文本对不上，属假绿）。
- spec 还写了「与既有反向接口缺行同款判据」——既有 9/10/11/12 号反向接口的缺行同样从未测过，这句话也落空。

## 建议改法

1. 把 1.3 的验收改成一次真红态（主循环做变异，CLAUDE.md 允许：「跑整套、启动程序、做变异由主循环自己做」）：
   - 临时注释掉 `kBindingPolicies` 里门面那一行 → `python build.py --config Debug` → tester 调 `GetInterfaceApiForTest(13u, nullptr, 2u, 0u, nullptr, nullptr)`；
   - 期望：返回 0；`LastError()` 含「没有在宿主角色登记表里登记」**且不含**「未知接口编号」（用来区分两条分支）；`GetInterfaceInstance(13, nullptr) == nullptr`；
   - 还原、重建、复跑 4.2，读数存 `evidence/1.3-缺行红态.txt`。
2. 删掉「引用 `Main.cpp` 既有用例 L1865 的 9999 反例」这句；9999 只覆盖未知编号分支，留在原处即可。
3. 若坚持不改产品代码，就照既有 `CASCADED_CSHARP_SELFTEST=abi-mismatch` 的 Debug 自检开关模式加一个等价门控（属于产品代码改动，需在 design 里写明）。
