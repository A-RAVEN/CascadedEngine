# 证据 003：`Serialize` 抛异常的 1012 不在 `SerializeAll` 这次调用里上报

对应主张：`主张-验收-003.json`（severity = blocking）
审查对象：`specs/csharp-resource-registry/spec.md` 场景「落盘时反向 Serialize 抛异常可上报」+ `tasks.md`
审查快照：registry spec 14:45:47（SHA-256 `82411941d8f4154e…`）、`tasks.md` 14:46:34（`859d5f2495379678…`）

## 结论

现有反向代理对「C# 实现抛异常」的语义是**下一次调用上报**：这一次只把 1012 落进错误槽、中止写入、直接返回。`ResourceManagingSystem_Impl::SerializeAll` 没有 try/catch，紧接着对空批调 `SubmitAndWait`（空批首行就返回），循环继续、方法正常返回。于是第一次 `SaveAll` 既不落盘也不报错——正是场景禁止的「静默跳过该资源假装成功」；1012 要等下一次在同一个对象上再调方法（再一次 `Serialize`）才抛出，若期间资源被释放，代理析构时错误直接丢掉。tasks 里没有任何一条断言这个场景。

## 机制证据

### 1. 代理实现：失败只落槽、不写、不提交

`out/build/x64-debug/codegen/bindings/resource_management__IResource.Bindings.cpp:180-210`：

```cpp
    void Serialize(ca_io::WBatch* inWriter) override
    {
        reportPendingError("Serialize");
        ...
        const uint64_t length = (m_slots.SerializeLen != nullptr) ? m_slots.SerializeLen(m_user) : UINT64_MAX;
        if (length == UINT64_MAX)
        {
            const std::string detail = takeImplementationError();
            setError(resource_management__IResource_ERROR_REVERSE_EXCEPTION, detail.empty() ? "反向实现返回长度失败" : detail);
            return;
        }
        ...
        if (written > 0u) { inWriter->Write(written, buffer.data()); }
        inWriter->SubmitAndWait();
    }
```

注意两点：错误在下一次进方法时由 `reportPendingError` 抛出（第 182 行），不是本调用内；失败分支不执行 `inWriter->SubmitAndWait()`。

### 2. 资源系统 SerializeAll 无 try/catch

`GeneralResources/private/ResourceImportingSystem.cpp:116-126`：


### 3. 空批不落盘

`IOManager_FS/IOManager.cpp:403-406`：

```cpp
	void WriteBatchImpl::SubmitAndWait()
	{
		if (m_Batchs.IsEmpty())
			return;
```

`WriteBatch` 只构造批（同文件 296-299），文件流在提交任务里才 `GetOStream` 打开（同文件 415）。`Test/GPUBackendTester/Main.cpp:1432` 的注释为同一机制作证：「必须先排队：空批在 SubmitAndWait 首行就返回」。⇒ 失败那一轮连空文件都不会生成，C# 看不到任何迹象。

### 4. 既有测试证明语义是「下一次调用」

`Test/GPUBackendTester/Main.cpp:6652-6683`（既有 TestCSharpResourceFactory ④）：


这条用例测的是**裸反向调用**；门面 `SerializeAll` 路径没有覆盖。

## 后果

- spec 这条 MUST 在「首次 SaveAll 就要报错」的读法下，按设计的「直委托」实现做不到；5.2 的场景对照表拿不到该场景读数，要么留空（违反「无『声称过但无读数』的行」），要么写一条没跑过的读数。
- 更糟的是没人会发现：失败资源这一轮不落盘、不报错、不生成空文件，只有下一次 `Serialize` 才抛 1012；如果期间 `ReleaseResource` 把对象释放了，代理析构（同文件 165-177）不会上报错误，1012 永久丢失。

## 建议改法

二选一，不能留一条机制上做不到的 MUST：

1. **按现有机制改场景并加断言**（代价小）：改成两段——第一次 `SaveAll`：该资源路径不存在文件、其余资源正常落盘、方法不抛；第二次 `SaveAll`（同一对象再 `Serialize`）：抛 1012、文本含原始异常文本。在 4.2 的失败面里加这一条（现在只有四条），红态用「把 C# `Serialize` 的 throw 去掉」构造，读数存 `evidence/4.2-serialize 抛.txt`。
2. **若产品要求第一次就报错**：就得在 design 里写明手段（门面 `SerializeAll` 直委托看不到逐资源错误，必须在反向通道或 C# 侧补检查），并重新评估「GeneralResources 零改动」这个目标——不能既不报错又写 MUST NOT 静默跳过。
