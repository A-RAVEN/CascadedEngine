# 证据-一致-001：审计表汇总表未改，1.4/1.5 之后脚本仍红

## 主张

修订后的 1.4 与 1.5 补上了「审计表主表九行」与「`check_bindable_audit.py` 的 `INTERFACES` 一项」，但都没有改归档审计表的**范围汇总表**。该汇总表目前写的是「13 个接口 / 合计 105」；脚本会把它与头文件实算数字逐项核对，新增门面后实算是 14 / 114。1.4 还明确要求「只追加不动旧行」，所以汇总表的两处改动（新接口的条数行、合计行）被挡在编辑范围之外。结果是：1.4 与 1.5 都完成后，`check_bindable_audit.py` 仍会因「汇总表缺少接口」与「合计不符」非零退出，而 spec 与 design D7 却承诺这一步 exit 0。

## 原文

`openspec/changes/csharp-resource-asset-foundation/tasks.md` 1.4：

> 审计表追加九行（唯一一份：`openspec/changes/archive/2026-10-18-csharp-bindable-surface/evidence/bindable-audit.md`，只追加不动旧行）：逐行写投影形状 / 分配归属 / 错误通道。验收：`Select-String 'IResourceRegistry'` 在该文件计数 = 9；脚本绿须与 1.5 同步完成（单独追加九行会因僵尸行红，见 1.5）。

同文件 1.5：

> `Tools/CodeGen/check_bindable_audit.py` 的 `INTERFACES` 表加 `"cs_script::IResourceRegistry": ("Interface/ScriptHost/header/ScriptHost/IResourceRegistry.h", "IResourceRegistry")` 一项。验收：`python Tools/CodeGen/check_bindable_audit.py` exit 0，输出接口数 13→14、方法对账数 105→114（基线实测存 `evidence/1.5-审计基线.txt`）……

`design.md` D7 与风险行：

> 九行追加进那一份……同时给该脚本的 `INTERFACES` 表加 `cs_script::IResourceRegistry` 一项……改后脚本绿（接口数 13→14、方法数 105→114，实测基线）。

> [审计表在归档里被改] → 既有惯例（脚本要求唯一一份，前批同样追加）；只追加九行，不动旧行。

`specs/csharp-resource-registry/spec.md` 接线要求与新场景：

> 门面 MUST 完成全部接线：……审计表九行、`check_bindable_audit.py` 的 `INTERFACES` 表加门面一项、宿主实例注册。

> 同步后 MUST exit 0（接口数 13→14、方法对账数 105→114，实测基线）

归档审计表 `openspec/changes/archive/2026-10-18-csharp-bindable-surface/evidence/bindable-audit.md`：

> **13** 个接口……合计 **105** 条公开方法

> | **合计** | **105** | |

## 脚本的硬判据

`Tools/CodeGen/check_bindable_audit.py` 的汇总表判据（脚本自己的注释）：

> 范围汇总表必须与头文件实算数字一致（任务 1.1）：只加行不改合计、或漏写新接口都是失败。

脚本实际检查：

- 对 `INTERFACES` 里的每个接口，汇总表必须有同名行，否则报「汇总表缺少接口 {interface} 的方法条数（头文件实算 {computed}）」；
- 汇总表「合计」必须等于 `sum(expected.values())`，否则报「汇总表合计不符：写 {summary_total}、头文件实算 {sum(expected.values())}」。

把 `cs_script::IResourceRegistry` 加进 `INTERFACES` 后，`expected` 是 105 + 9 = 114，`method_counts` 是 14 个接口；归档汇总表还是 13 / 105，两条报错都会出现，脚本退出码 1。

## 两条路径的读数

- 只做 1.4（九行）不做 1.5：九行全不在 `expected` 里，脚本报九条「僵尸行」，退出码 1。
- 做 1.4 + 1.5（九行 + `INTERFACES`）但不改汇总表：九行对上了，但汇总表缺 `cs_script::IResourceRegistry` 一行、合计仍 105，脚本报「汇总表缺少接口」与「汇总表合计不符」，退出码 1。
- 当前未改工件时的读数：「扫描 13 个接口、对账 105 条方法、命中 0 处问题」——正是 13 / 105 的现状；要让 1.5 的「13→14、105→114」成立，汇总表必须同步改。

## 为什么是 blocking

1. 1.5 的验收命令就是 `check_bindable_audit.py` exit 0；按 1.4 + 1.5 做完仍 exit 1，任务无法完成。
2. 若为了过脚本临时改汇总表，就违反 1.4 的「只追加不动旧行」；任务文字与实际动作冲突。
3. `build.py` 的 `--emit-binding` 还会把同一个脚本的 `--json` 结果当闸门（CodeGen 原文「CodeGen: 拒绝 —— 审计表对账不绿（脚本退出码 %d）」），所以汇总表不改还会把构建一起弄红。
4. spec 与 design D7 已经写死了「同步后 MUST exit 0（13→14、105→114）」，这等于把不可能的任务写进了规范。

## 改法

1. 在 1.4/1.5 之后（或直接扩 1.5）加一条：
   - 范围汇总表加一行 `cs_script::IResourceRegistry`，方法条数 9，头文件 `Interface/ScriptHost/header/ScriptHost/IResourceRegistry.h`；
   - 合计行 `| **合计** | **105** | |` 改为 `| **合计** | **114** | |`；
   - 正文「**13** 个接口……合计 **105** 条公开方法」改为「**14** 个接口……合计 **114** 条公开方法」。
2. 把 1.4 的「只追加不动旧行」改成「追加九行 + 汇总表新行 + 合计行（旧行中只改合计）」；design D7 与风险行、registry spec 的接线要求、proposal 的「审计表（归档内单一文件追加行）」同步写上汇总表的两处改动。
3. 若不想动汇总表，则必须在 spec 里把「脚本 exit 0」改成「主表九行对账通过、汇总表允许滞后」——但那会放松既有判据，不如直接补两行。

## 复核方式

```powershell
# 现状：13 / 105 / 0
python Tools\CodeGen\check_bindable_audit.py

# 做 1.4 + 1.5、不改汇总表后重跑：应出现
#   汇总表缺少接口 cs_script::IResourceRegistry 的方法条数
#   汇总表合计不符：写 105、头文件实算 114
# 退出码应为 1；这就是本主张的红态。
```
