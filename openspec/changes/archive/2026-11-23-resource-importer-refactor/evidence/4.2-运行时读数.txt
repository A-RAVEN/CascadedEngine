## 红态（缺陷态先存档）

迭代过程中实际撞到并修掉的两个红态（都是**这条用例自己**报出来的，读数与根因各有一份证据）：

1. 「重导入之后旧 C# 资源的保活计数不是 0（读数 1 / 0）」→ 判据选错观测量（保活表按槽位下标、槽位会复用），
   改判旧句柄代际失效。见 `4.2-旧句柄保活口径.txt`。
2. 「C++ 对照资源读回来的值是 0，期望 20261122」→ 测试桩没按“读是排队的”写（`IOBatch::Read` 只登记目的地，
   字节在 `SubmitAndWait` 才落地）。见 `4.2-C++对照回读.txt`。

两个**产品缺陷态**的红（临时注入、跑完恢复）：

- **导入器写错字段**（Vulkan `shaderInfo.path = cacore::PathHash("REDSTATE_BYTE_MUTATION")`，其余不动）⇒ ⓪
  字节对拍红，实测：

  ```
  GPUBackendTester --backend vulkan --test TestCSharpImporter  → exit 1
  导入器产出的 ShaderLibrary 序列化字节与改动前不一致：
    实际 4fd16466f2ba7d5ea0f71a23280a0cfb0c53efb53639a319ca731e91b9e2174f
    期望 7a3d7d0c5ff8ac8ba014e6a256e2babcb737c7d69105c5481e474be0d8977c81
  ```

  期望值正是改前封存的那个哈希 ⇒ 这一条不是“改期望值”，而是**产品侧字节真变了**时判据会红。

- **管线去掉 `ReleaseResource`**（只留 `RegisterResource`，即 get_or_create 静默留旧）⇒ ③ 重导入替换判据红，
  实测：

  ```
  GPUBackendTester --backend d3d12 --test TestCSharpImporter  → exit 1
  重导入替换没有生效：消费者还拿到旧对象（get_or_create 式静默留旧）
  ```

两处改动跑完已**逐字恢复**（`RED-STATE` 标记全仓 0 命中；恢复后的两行分别是
`shaderInfo.path = shaderPathHash;` 与 `m_ResourceManagingSystem->ReleaseResource(relativePath);`），
随后复绿：

```
python build.py --config Debug                                → BUILD SUCCESSFUL（exit 0）
GPUBackendTester --backend vulkan --test TestCSharpImporter  → pass（729ms，exit 0）
GPUBackendTester --backend d3d12  --test TestCSharpImporter  → pass（474ms，exit 0）
```

⇒ 4.2 的验收两半都成立：两后端全断言过；两个产品缺陷态各自能把它弄红。
