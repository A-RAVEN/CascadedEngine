# 证据-一致-004：新增一个 .shLib 不再满足既有「条目数 +1」判据

- 攻击面：工件一致性（面⑥：枚举整合去重/排序与既有判据）
- 结论：排序与去重键本身不冲突；但枚举整合改变了「新增一个文件 → 条目数 +1」这条生效规范的场景，本 change 没有 MODIFY 它，现有测试用 .mesh 夹具也抓不到。
- 与并行面的关系：`主张-影响-002` 已覆盖「逐条一致」的条目集合冲突、`主张-影响-004` 已覆盖 assets-changed 不广播；本条只补 :21 的「条目数 MUST +1」这条未被覆盖的 MUST。

## 一、生效规范的两条判据（未修改）

生效规范 :16：

> 返回条目 MUST 与真实文件逐条一致（path/nodeId/sizeBytes/kind/modifiedUtc/registered/children 七项）；nodeId MUST = path = 相对资源根路径

生效规范 :21：

> 第二次结果 MUST 含新增文件条目；条目数 MUST +1

## 二、新行为怎么改条目集合

新能力规范 :19 / :24：

> MUST 有 `ShaderSourceDisplayProvider`（kind=shader-library），`Describe(shLib 上下文)` MUST NOT 产 shLib 自身条目，MUST 扫源目录……递归 `*.slang` 产每个源文件一条
> 结果 MUST NOT 含 shLib 条目；MUST 含每个 .slang 源条目……源条目数 MUST 等于源目录 .slang 文件数

实测源目录有 16 份 .slang：

```text
PS> (Get-ChildItem 'CAResources/Shaders' -Recurse -File -Filter *.slang).Count
16
PS> Get-ChildItem 'CAAssets' -Filter *.shLib | Select-Object -ExpandProperty Name
D3D12ShaderLibrary.shLib
VulkanShaderLibrary.shLib
```

于是「向资源根新增一个 .shLib」的三种可能结果：

| 实现/状态 | 新增文件条目 | 条目数变化 | :16 / :21 |
| --- | --- | --- | --- |
| 提供者已注册、源根可解析 | 无（shLib 条目被隐去） | +16（16 条源条目） | 两条都假 |
| 提供者已注册、源根不存在 | 无 | +0（空源列表） | 两条都假 |
| 提供者未注册（若可能） | 有 | +1 | 只有这种退回旧行为时才成立 |

只要有任意一条路径被本 change 采用（正常实现是前两条），生效规范 :16/:21 就被违反；而这两条不是本 change 的 MODIFIED 对象（本 change 只改了显示提供者那一条）。

## 三、现有测试为什么抓不到

```text
PS> Select-String -Path 'Test/GPUBackendTester/Main.cpp' -Pattern 'addedRelative ='
Test\GPUBackendTester\Main.cpp:6793:		const std::filesystem::path addedRelative = "Added/Extra.mesh";
```

刷新用例新增的是 `.mesh`（数据型，走默认提供者），仍满足「+1」；本 change 的 tasks 3.1 只测「源条目增删→assets-changed」，没有测「向资源根新增一个 .shLib」。因此这条规范冲突在自动化验收里完全不可见。

## 四、排序/去重面（通过项）

现有代码按 Path 序数排序：

```text
PS> Select-String -Path 'Scripting/Managed/Editor/EditorService.cs' -Pattern 'entries.Sort'
EditorService.cs:1133:            entries.Sort((left, right) => string.CompareOrdinal(left.Path, right.Path));
```

MODIFIED :5、design :42、tasks :17 都写「按 path 序数排序」，去重键 nodeId 在源条目上等于 path（design :30「nodeId=path」），未发现排序与去重键互斥；这一项**没有** blocking。冲突只在新增文件的条目计数语义。

## 五、为什么算矛盾

- 「向资源根新增一个文件 → 条目数 MUST +1」是一个全称判据；.shLib 是资源根里真实存在的文件类型，新增它时新行为给出 +16 或 +0，判据必假。
- change 没有 MODIFY :16/:21，归档后生效规范会同时要求「与真实文件逐条一致/+1」与「隐去 shLib、产源条目」，后续验收必有一条红。
- 唯一覆盖刷新的测试用 .mesh，冲突被夹具选择掩盖。

## 六、建议修法

1. MODIFY :16/:21：把「真实文件」限定为「资源根内按扩展名映射为数据型的文件」，把「+1」限定为「每个输入文件产出的条目集合大小」；代码型文件单列一条口径（新增 .shLib → 条目数变化 == 其源条目数，或明确不参与 +1 场景）。
2. tasks 3.1 增加红态：临时资源根新增一个 .shLib，断言 shLib 条目不存在、源条目数 == .slang 文件数、`assets-changed` 的 added/removed 等于写死值（按选定口径）。
3. 若决定代码型文件不触发刷新语义，写进规范并给出对应的「不广播」断言，不要留给实现自由选择。
