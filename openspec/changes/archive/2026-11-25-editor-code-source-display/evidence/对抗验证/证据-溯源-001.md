# 证据-溯源-001：16 份 .slang 属实，但「两份 shLib 都由这 16 份编译来」只对 D3D12 成立

> 定位以逐字引文为准；行号是 2026-11-25 审查时实测值。

## 一、主张摘要

- 主张编号：主张-溯源-001（面① 数字溯源）
- 攻击面：无中生有
- 严重度：misleading
- 工件：`design.md:9`、`design.md:52`、`spec.md`（源目录约定）
- 一句话：树内 16 份 .slang 是真的；但 VulkanShaderLibrary.shLib 里存了 21 条源路径，5 条在树里已没有对应文件。

## 二、工件原文

`design.md:9`：

> shLib 落 CAAssets（VulkanShaderLibrary.shLib/D3D12ShaderLibrary.shLib），由 `CAResources/Shaders/` 下 **16 个 .slang** 编译来。

`design.md:52`：

> 约定假定 shLib←CAResources/Shaders 全部 .slang，与 ShaderImporter 扫描根一致。

## 三、命令与真实输出

```powershell
PS> (Get-ChildItem CAResources -Recurse -Filter *.slang -File).Count
16
PS> (Get-ChildItem CAResources -Recurse -Filter *.slang -File | Where-Object { $_.FullName -notmatch '\\Shaders\\' }).Count
0
```

树内 16 份（相对 `CAResources`、去扩展名）与 shLib 字节里的 `Shaders/...` 串对比：

```powershell
PS> # 读两份 shLib 的原始字节，取 ASCII 里所有 Shaders/[A-Za-z0-9_/]+ 并去重
PS> # 结果：
VulkanShaderLibrary.shLib：21 条
```

导入器确实把「相对扫描根、去扩展名」的路径写进 PathHash（因此库里的串与树内相对路径可逐字对齐）：

`ShaderImporter_Vulkan.cpp:343-345`：

```cpp
auto relative_path = cafs::relative(p.path(), effectiveSourcePath);
auto shaderpath = relative_path;
shaderpath.replace_extension("");
```

## 四、结论与建议

- 16 是 CAResources/Shaders 下 .slang 的实数，这一点没问题。
- 「两份 shLib 都由这 16 份编译来」对 D3D12 库成立；对 Vulkan 库不成立：它携带 21 条源路径，其中 5 条在树里没有对应 .slang（4 条是 `.hslang` 名，1 条是已删的 `TestTriangleWithStructuredBufferColor2`）。说明这份 Vulkan shLib 不是当前 16 份源编出来的，或者至少没有随源删除而重建。
- 建议：design/spec 改成「D3D12 库与当前 16 份一一对应；Vulkan 库为历史产物，含 5 条无源路径」，或把「重建 shLib 后重新对账」写成一条可失败任务（例如比对 shLib 路径集合与源目录集合，差集必须为空）；不要把两份库混成一句「由 16 个编译来」。

## 五、边界

- 核了：16 份 .slang 的计数与位置、两份 shLib 的 ASCII 路径串（长度前缀 + 正斜杠）、导入器的路径生成逻辑。
- 没核：没有执行导入器重建 shLib（只读环境，不跑构建/tester），因此不能断定 Vulkan 库过期是历史遗留还是当前构建也会这样；本主张只陈述「现有 CAAssets 里的字节与工件的 16 份描述不一致」。
