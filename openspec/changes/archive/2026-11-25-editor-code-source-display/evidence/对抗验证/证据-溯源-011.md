# 证据-溯源-011：「源条目数==源文件数」是恒等式，抓不到 shLib 与源目录的不一致

> 定位以逐字引文为准；行号是 2026-11-25 审查时实测值。

## 一、主张摘要

- 主张编号：主张-溯源-011（面⑥ 静默降级/验收）
- 攻击面：无中生有
- 严重度：misleading
- 工件：`tasks.md:21`、`tasks.md:26`、`spec.md:24`
- 一句话：提供者按枚举文件逐个产条目，「源条目数==源文件数」必然成立；它抓不到 shLib 里有 5 条无源文件、或某个源文件没编进 shLib 这两类不一致。

## 二、工件原文

`tasks.md:21`：

> .slang/.cs 源条目逐条 path/kind/sizeBytes/registered==写死期望 + 源条目数==源文件数

`spec.md:24`：

> MUST 含每个 .slang 源条目，path/kind=shader-source/sizeBytes/registered 逐条等于写死期望；源条目数 MUST 等于源目录 .slang 文件数

## 三、实测的库/源不一致

```text
CAResources/Shaders 递归 .slang：16 份
CAAssets/VulkanShaderLibrary.shLib：21 条源路径串
  库有树无（5）：Shaders/CameraData、Shaders/GlobalDirectLighting、
                Shaders/InstancedStaticMesh、Shaders/MeshMaterial、
                Shaders/Test/TestTriangleWithStructuredBufferColor2
CAAssets/D3D12ShaderLibrary.shLib：16 条，与树一一对应
```

按 design D3，所有程序集条目都被隐去，所以 Vulkan 用户看不到这 5 条 shader 名；而提供者只扫源目录，产 16 条，验收断言「16 == 16」通过。缺陷（shLib 携带 5 条没有源文件的路径）在现有判据下不可见。

## 四、反向也不可见

`ShaderImporter_Vulkan.cpp:358-361`：

```cpp
if (pCompiler->HasError())
{
    CA_LOG_ERR("ShaderImporter_Vulkan: Shader compile failed for {}", p.path().generic_string());
}
```

编译失败只记日志，不产 m_ShaderFiles 条目；提供者仍会把该 .slang 当源文件列出。验收按「源条目数==源文件数」也通过——用户以为这个 shader 在库里，实际上没有。这是「多给」，同样静默。

## 五、结论与建议

- 恒等式问题：源条目数完全由 `Directory.EnumerateFiles` 决定，断言它等于同一个枚举的计数，不可能失败（除非实现不按枚举产条目）。这不是有效的验收判据。
- 建议（加严，不放松）：
  1. 加一条对账断言：`shLib 的源路径集合 − 源目录 .slang 集合 = 空`（现在会红：差 5 条），并要求把差集写进 evidence；如果决定「历史多余条目允许存在」，则必须在 UI/日志里显示「库里有 N 条无源文件的着色器」。
  2. 反向：`源目录 .slang 集合 − shLib 源路径集合` 若非空，必须标出「未编译进库的源文件」，而不是默默当源显示。
  3. 这两条都建立在「PathHash 串可读」上（见主张-溯源-004）；若坚持不读 shLib 字节，至少要在验收里写死「本批不校验库/源一致性」并把它列为已知限制，不能用一个恒真断言冒充覆盖。

## 六、边界

- 核了：两份 shLib 的路径集合、16 份源文件、编译失败分支、验收原文。
- 没核：没有跑导入器验证「编译失败的 .slang 一定不进 m_ShaderFiles」（按代码路径推断：只有 `HasError()==false` 分支才写库）；没有在 Vulkan 上核对 5 条无源路径是历史遗留还是当前构建也会产生（只读环境，不重建 shLib）。
