# 证据 影响-009：4.1 回归写在 4.2 构建之前，跑的是不含新用例的旧二进制

对应主张：`主张-影响-009.json`（severity = misleading）

审查对象：`tasks.md` 4.1 / 4.2；对照归档基线 `2026-11-25-source-importers-png-obj/evidence/4.1-全量-*.json`。

审查快照（SHA-256 前 16 位）：`tasks.md` `90FD91739A78EC59`。

## 一、工件怎么写

`tasks.md:26`（4.1）逐字：

> 4.1 回归零差异（主循环跑）：现有 22 用例同进程两后端 name+status 与基线（归档 2026-11-25-source-importers-png-obj/evidence/4.1-全量-*.json）零差异；TestCodeSourceDisplay 独立进程过；CoreTests exit 0 + PASSED 26（evidence/4.1-CoreTests.txt）；绑定基线 check_binding_baseline.py 0/0/0（evidence/4.1-基线.txt）；check_csharp_host_readme 0 问题；--list/docs/testing.md 同步。验收：零差异 + CoreTests 26 + 基线 0/0/0 + README 0 问题。

`tasks.md:27`（4.2）逐字：

> 4.2 编译验证（最后）：python build.py --config Debug 失败修到成功；成功后复跑 4.1 读数不变。验收：BUILD SUCCESSFUL + 复跑一致（evidence/4.2-构建.txt）。

## 二、冲突在哪

4.1 的两条断言依赖「包含 3.1 新用例与 2.x 全部改动的二进制」：

- `--list` 含 `TestCodeSourceDisplay`；
- `TestCodeSourceDisplay` 独立进程跑过。

但完整的「编译验证」在 4.2，且明确标了「（最后）」。其余任务（1.1/1.2/2.1/2.2/2.3）的验收只写「构建过」，是逐任务构建，没有一条要求「4.1 之前做一次覆盖全部改动的最新构建」。按清单字面顺序，4.1 很可能跑到一个早于 3.1 的二进制：`--list` 里根本没有新用例，4.1 的第一条断言当场红。

## 三、为什么这是「静默」问题

即使中间构建包含新用例，4.1 与 4.2 之后复跑的读数也来自两次不同的构建，工件只要求「读数不变」，没有任何证据记录被测二进制的路径/时间/哈希；归档基线 JSON 也不含可对应的构建标识（实测 grep `commit|build|version` 零命中）。于是「现有 22 用例零差异」可以是在旧产物上成立的结论，读它的人无法分辨。

## 四、建议改法

1. 顺序改成「构建 → 4.1 回归」（或把 4.2 的构建步骤移到 4.1 前，4.2 只保留「记录构建产物 + 复跑」）。
2. 4.1 的每份证据记录被测二进制绝对路径与构建时间（或哈希），4.2 复跑用同一二进制。
3. `--list` 期望条数写死（现有 25 + 新增 1 = 26），docs/testing.md 的清单同步以这个数为判据。
