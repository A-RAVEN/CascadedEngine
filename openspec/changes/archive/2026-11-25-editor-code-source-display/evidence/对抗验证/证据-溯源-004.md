# 证据-溯源-004：PathHash 是字符串包装，shLib 字节里就有源路径串

> 定位以逐字引文为准；行号是 2026-11-25 审查时实测值。

## 一、主张摘要

- 主张编号：主张-溯源-004（面② 声称核）
- 攻击面：无中生有
- 严重度：blocking
- 工件：`design.md:9` / `design.md:28` / `spec.md:19`
- 一句话：PathHash 不是「只存哈希不存串」，它内部有 `castl::string m_Name`，CodeGen 序列化写的就是这个串；两份 shLib 的字节里能直接数出 16/21 条源路径。因此「C# 拿不到源路径串 → 只能扫源目录」的论证不成立。

## 二、工件原文

`design.md:9`：

> `m_ShaderFiles` 键是 `cacore::PathHash`＝源路径**哈希**非路径串，`ShaderFileInfo.path` 也是 PathHash

`design.md:28`：

> shLib 的 m_ShaderFiles 键是路径哈希、C# 拿不到源路径串，故**扫源目录约定**取源文件。

`spec.md:19`：

> 源映射 MUST 走扫源目录约定（shLib 的 m_ShaderFiles 键是源路径哈希非路径串，C# 侧拿不到源路径串）。

## 三、源码证据（PathHash 存串）

`CACore/header/HashKeys.h:159-319`（节选）：

```cpp
struct PathHash
{
    constexpr PathHash() : m_HashValue(0), m_HashValid(false), m_Name("") {}
    PathHash(const char* str) { ... m_Name = cafs::path(str).generic_string(); ... }
    PathHash(castl::string const& str) : m_Name(cafs::path(str).generic_string()) { ... }
    ...
    constexpr castl::string string() const noexcept { return castl::string(m_NameView); }
    constexpr char const* c_str() const noexcept { return m_NameView.data(); }
    ...
private:
    castl::string_view m_NameView;
    bool m_HashValid;
    result_type m_HashValue;
    castl::string m_Name;
};
```

CodeGen 的包装类型特化（`HashKeys.h:478-485`）：

```cpp
template<>
struct wrapper_traits<::cacore::PathHash>
{
    static constexpr bool is_wrapper = true;
    using inner_type = castl::string;
    static inner_type get_data(::cacore::PathHash const& obj) { return obj.string(); }
    static void set_data(::cacore::PathHash& obj, inner_type const& data) { obj = ::cacore::PathHash(data); }
};
```

即序列化写入的是 `m_Name` 的字符串，不是只写 64 位哈希。运行期也依赖这个串：`ResourceImportingSystem.cpp:120` 用 `m_AssetRootPath / key.Get()` 组落盘路径，若 PathHash 不存串就无法写文件。

## 四、字节证据（shLib 里就有源路径）

VulkanShaderLibrary.shLib 偏移 0 起的十六进制（字符串从偏移 16 开始，长度前缀 0x11 = 17 字节）：

```text
10 00 00 00 00 00 00 00 11 00 00 00 00 00 00 00
53 68 61 64 65 72 73 2F 46 69 6E 61 6C 42 6C 69 74   ← "Shaders/FinalBlit"
11 00 00 00 00 00 00 00 53 68 61 64 65 72 73 2F 46 69 6E 61 6C 42 6C 69 74  ← 同一串第二份（键 + ShaderFileInfo.path）
```

两份库的 ASCII 路径集合（相对 CAResources、去扩展名）：

```text
VulkanShaderLibrary.shLib：21 条（含 5 条树内已无文件的路径）
D3D12ShaderLibrary.shLib：16 条（与 CAResources/Shaders 的 16 份一一对应）
```

C# 侧拿得到：shLib 就在 `CAAssets/` 下，是被 `Directory.EnumerateFiles` 枚举到的普通文件；编辑器侧的 `EditorService` 本来就在用 `System.IO`（`EnumerateAssets` 里 `new FileInfo(file)`），读同一目录下 shLib 的字节做 ASCII 扫描就能得到这些路径串。即便不解析完整 CodeGen 格式，这 21 条串也是可读的。

## 五、结论与建议

- 「PathHash 是哈希、非路径串」为假；「C# 拿不到源路径串」为假。spec 把一条 MUST 的理由建立在这两句话上，属于无中生有。
- 后果：design 的 Non-goal「程序集溯源元数据」、Risk「程序集内嵌源路径留身份重设计批」也建立在假前提上；同时「扫源目录」方案会漏掉 shLib 里有、源目录里没有的 5 条（见主张-溯源-011）。
- 建议（不放松判据）：要么改成「路径串可从 shLib 字节读出，但本批不做解析，选源根约定」并把 Non-goal/Risk 改成显式取舍；要么直接用 shLib 里的路径集合与源目录集合做对账（加一条差集为空的断言）。无论哪条，spec 的 MUST 理由必须改成可核的事实。

## 六、边界

- 核了：HashKeys.h 的成员/构造/比较、wrapper_traits、两份 shLib 的字节串、ResourceImportingSystem 的 key.Get() 用法、EditorService 的 System.IO 使用。
- 没核：没有在 C# 里实现 shLib 解析器，也没有验证 CodeGen 生成的 PathHash 读写代码（生成物在 out/build 下，未打开逐行核）；字节里的长度前缀与 wrapper_traits 的对应关系是推断 + 实测串一致，未做完整反序列化验证。
