## 二、协议文档怎么定义 path

`Scripting/Managed/Editor/PROTOCOL.md:122-123` 逐字（2.6 表格）：

> | `nodeId` | string | 稳定条目编号。**v1 = `path` = 相对资源根的正斜杠路径**（见下）；v2 溯源落地后仍保持稳定 |
> | `path` | string | 相对资源根的正斜杠路径（例：`CSharpProbe/Probe.tex`） |

`PROTOCOL.md:101-104`（assets-changed）：

> 本次资产枚举相对**上一次枚举快照**的条目增删数（按 `path` 比对；首次枚举没有上一条快照，不发该事件）……

存量规范把 PROTOCOL.md 定为唯一事实源（`openspec/specs/editor-asset-browser/spec.md:30`）：

> ……MUST 先改 `Scripting/Managed/Editor/PROTOCOL.md`，再镜像 `EditorWeb/src/protocol.ts` 与 `EditorProtocol.cs`，字段名/错误码逐字一致。

`EditorWeb/src/protocol.ts:19-20` 的注释仍是：

> 资产条目（PROTOCOL.md 2.6）：v1 一文件一条目，children 恒为空数组、nodeId = path = 相对资源根的正斜杠路径……

## 三、消费方会看到什么

`EditorWeb/src/assets.ts:81`：

```text
[entry.path, ''],
```

路径列直接渲染 `entry.path`。本批之后同一个 `assets` 数组里会同时出现：

```text
VulkanShaderLibrary.shLib          ← 相对资源根
CAResources/Shaders/FinalBlit.slang ← 相对工程根
```

两个根混在一列，用户与客户端都无法从字符串本身判断该拼哪个根。存量规范第 2 条要求「三处镜像逐字一致」，但那条验收只比字段名与错误码，字段含义变了它照样绿——协议语义变更没有任何可失败的判据。

## 四、附带风险：同键不同文件

`assets-changed` 与去重都按字符串键（快照按 `path`，D6 按 `nodeId`）。当 `CASCADED_EDITOR_ASSET_ROOT` 指向工程根（README 写「任意已存在目录」）时，`CAResources/Shaders/X.slang` 既会作为资源根文件被枚举（kind=file），又会作为源条目出现（kind=shader-source），两个不同来源共享同一字符串键，去重会误删其中一条（保留哪条取决于枚举顺序），见主张-影响-005。

## 五、建议改法

1. 先定 `path` 语义，三选一：保持相对资源根 + 另加字段；把 path 重定义为「显示路径」并写明按 kind 区分；用保留前缀的虚拟路径。
2. 无论哪种，2.3 增加任务：改 `PROTOCOL.md` 2.6 + 镜像 `protocol.ts` / `EditorProtocol.cs`，验收命令写成「三处逐字含新定义」的 grep（能失败）。
3. 在 spec 里补场景：源条目的 path 在 dock 路径列如何显示、客户端不得把它拼到资源根。
