# 证据-溯源-008：path/nodeId 改成「相对工程根」，但协议钉死「相对资源根」且没有改协议的任务

> 定位以逐字引文为准；行号是 2026-11-25 审查时实测值。

## 一、主张摘要

- 主张编号：主张-溯源-008（面⑤ 字段语义）
- 攻击面：无中生有
- 严重度：blocking
- 工件：`design.md:30`、`design.md:38`、`spec.md:19/:33`、`tasks.md`（2.3 无协议改动）
- 一句话：源条目的 path/nodeId 用了新基准（工程根），而 PROTOCOL.md 与已生效规范要求「相对资源根」；同一批 list-assets 条目里出现两种基准，且没有改协议文档的任务。

## 二、工件原文

`design.md:30`：

> 源文件不在 CAAssets，path 用**相对工程根**的源路径（如 `CAResources/Shaders/Test/TestSimpleTriangle.slang`、`Scripting/Managed/Host.cs`），nodeId=path。

`design.md:38`：

> path/nodeId=相对工程根源路径

## 三、已生效协议

`Scripting/Managed/Editor/PROTOCOL.md:122`：

> | `nodeId` | string | 稳定条目编号。**v1 = `path` = 相对资源根的正斜杠路径**（见下）；v2 溯源落地后仍保持稳定 |

`:123`：

> | `path` | string | 相对资源根的正斜杠路径（例：`CSharpProbe/Probe.tex`） |

`openspec/specs/editor-asset-browser/spec.md:16`：

> nodeId MUST = path = 相对资源根路径；children MUST 空；modifiedUtc MUST ISO 8601 UTC；sizeBytes MUST 等于 FileInfo 实测字节

## 四、现有实现基准

`EditorService.cs:1102`（枚举数据型文件时）：

```csharp
string relative = Path.GetRelativePath(root, file).Replace('\\', '/');
```

即现有条目的 path 都是相对资源根（`root = registry.GetResourceRootPath()`，默认 CAAssets）。design 的源条目示例 `CAResources/Shaders/Test/TestSimpleTriangle.slang` 是相对仓库根，不是相对 CAAssets；同一批 assets 数组里会出现两种基准。

## 五、任务与验收没有覆盖这项变化

```powershell
PS> Select-String tasks.md -Pattern 'PROTOCOL|protocol|EditorWeb|三处镜像'
（0 命中：tasks 2.3 只要求「新 env 登记 CSharpHost/README」，没有改 PROTOCOL.md / protocol.ts / EditorProtocol.cs 的任务）
```

`tasks.md:21` 的验收只按写死期望比 path；`spec.md:47` 说「list-assets 七字段形状不变」——形状确实没变，但 path 的基准变了，属于语义变化，不在「形状」判据里。

## 六、后果

- 消费方（dock 页面、后续打开源文件的逻辑、任何按「资源根 + path」拼路径的代码）拿到 `CAResources/Shaders/Test/TestSimpleTriangle.slang` 会拼成 `CAAssets/CAResources/...`，找不到文件。
- 去重按 nodeId：如果将来某个真实 CAAssets 文件与源条目相对路径碰巧同名（例如 `Scripting/...` 被复制进资源根），会被误判为同一条而丢条目。
- 同一数组里两套基准，协议没有字段能区分「这条 path 相对谁」。

## 七、结论与建议

- blocking：要么把协议改成显式表达基准（例如新增 `pathBase` 字段，或规定源条目 path 用相对资源根的可解析形式如 `../CAResources/...`），并同步 PROTOCOL.md / EditorWeb/src/protocol.ts / EditorProtocol.cs 三处；要么把源条目的 path 改成相对资源根（`../CAResources/Shaders/...`）并写清允许 `..` 的语义。
- 无论选哪条，tasks 都要加一条「协议三处镜像 + 场景断言 path 基准」的任务，否则这条语义变化没有可失败判据。

## 八、边界

- 核了：PROTOCOL.md 两行、已生效 spec:16、design 两处、EditorService 现有路径基准、tasks 无协议改动。
- 没核：没有看 EditorWeb 前端如何使用 path（只读仓库前端代码未逐行核）；不能排除前端只是显示字符串、不拼路径，但协议契约本身已冲突。
