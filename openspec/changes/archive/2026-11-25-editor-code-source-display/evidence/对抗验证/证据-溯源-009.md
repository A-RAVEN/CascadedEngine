## 三、注册/去重语义核查（这一半不成立）

`design.md:24`：

> **去重**：注册显示资源的 path 若已在 CAAssets 枚举到（如 shLib），不重复引入（以文件枚举那条为准）

`design.md:28`（shLib 的提供者来源）：

> `ShaderSourceDisplayProvider`（kind=shader-library）：`Describe(shLib 上下文)` **不产 shLib 条目**，改扫源目录…

同一份 design 里有两套注册：

- D1：`Register(kind, path, provider)` / `Resolve(kind, path)`（按类型 + 路径绑定，用于 shLib 的按种类/按路径精确绑定）；
- D2：`RegisterDisplayResource(kind, path, provider)`（显示资源表，用于不在 CAAssets 的 dll）。

shLib 在 CAAssets 里、被正常枚举，按 D1 的 path 绑定处理即可；它从没被写成 `RegisterDisplayResource` 条目。D2 的「如 shLib」把一个不属于显示资源表的对象当成去重例子，且没有任务写「谁、在哪个后端实例里、用哪个 path 注册 (shader-library, shLib)」。spec 场景只说：

`spec.md:9`：

> 对 (shader-library, "VulkanShaderLibrary.shLib") 注册一个提供者，对另一路径未注册

这是 D1 的精确绑定，不是 D2 的显示资源。实现者按不同读法会得到两种结构（shLib 是 path 绑定还是显示资源条目），去重行为也随之不同。

## 四、结论与建议

- env 命名：属实，不 blocking；建议 2.3 里把三个名字和默认值/范围写进 README 表（与现有表同格式）。
- 注册/去重：建议 D2 删掉「如 shLib」这个例子，改为「注册显示资源的 path 若已在 CAAssets 枚举到（例如以后把某个 .dll 放进资源根）」，并在 2.1 明确 shLib 用 D1 的 `Register(kind, "VulkanShaderLibrary.shLib", provider)` 还是按种类默认注册（两种都能工作，但去重/覆盖行为不同，必须写死一种）。

## 五、边界

- 核了：三个 env 名的全仓命中、README 编辑器 env 表、D1/D2 两套注册的原文、spec 场景的注册写法、CAAssets 两份 shLib。
- 没核：没有实现或运行注册表，无法验证「哪一种读法能通过 3.1 的断言」；本条只报工件内部机制描述不一致。
