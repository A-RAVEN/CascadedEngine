# 证据-验收-011：assets-changed 判据没钉条数与 fields

## 1. 新工件的写法（命令 + 真实输出）

```powershell
Select-String -Path 'openspec/changes/editor-code-source-display/tasks.md','openspec/changes/editor-code-source-display/specs/editor-code-source-display/spec.md' -Pattern 'assets-changed' | ForEach-Object { $_.Filename + ':' + $_.LineNumber + ': ' + $_.Line.Trim() }
```

真实输出：

```text
tasks.md:21: - [ ] 3.1 tester 用例 `TestCodeSourceDisplay`…→ list-assets 断言 **shLib/dll 条目不出现** + .slang/.cs 源条目逐条 path/kind/sizeBytes/registered==写死期望 + 源条目数==源文件数；源增删→assets-changed；红态：…
spec.md:47: MUST 新增 tester 用例 `TestCodeSourceDisplay`…断言 shLib/dll 条目隐去 + .slang/.cs 源条目逐条写死期望 + 源增删 assets-changed + 红态（…）
```

「源增删→assets-changed」没有条数、没有 fields、没有「无变化不广播」的负控；spec 里也没有 `#### Scenario` 覆盖它（它只在 requirement 散文里）。

## 2. 现有协议语义（逐字引文）

`Scripting/Managed/Editor/EditorService.cs`：

```csharp
/// 与上次成功枚举的路径快照比对，有增删就广播 `assets-changed`（fields 只有 added / removed）。
/// 首次成功枚举只记快照、不发事件（没有"上一次"可比）；其它客户端收到事件后重发 list-assets。
```

## 3. 现有用例的判据（命令 + 真实输出）

```powershell
Select-String -Path 'Test/GPUBackendTester/Main.cpp' -Pattern '期望恰好 1 条|fields 不是 added=1/removed=0' | ForEach-Object { $_.LineNumber.ToString() + ': ' + $_.Line.Trim() }
```

真实输出：

```text
6864: std::snprintf(detail, sizeof(detail), "第二次枚举收到 %d 条 assets-changed，期望恰好 1 条", changedCount);
6869: fail("E_ASSETBROWSER_EVENT", "assets-changed 的 fields 不是 added=1/removed=0：added=\"" + addedField + "\" removed=\"" + removedField + "\"");
```

## 4. 结论

已有的正确写法（恰好 1 条 + added=1/removed=0 + 事件绑定到第二次枚举）没有被新用例采用；新验收可以被「每次枚举都广播」或「计数写错」的实现骗过，也可以被「只收到任意一条事件」满足。缺「无变化 → 0 条」的负控则连抑制逻辑是否生效都判不出来（现有语义明确要求首次不广播）。
