## 2026-11-05 裁决一：`Tools/check_csharp_host_readme.py` 加入允许改动范围

**问题**：该脚本现在从三处**手写物**读 ABI 真值 —— `Host.cs` 的 `ExpectedAbiVersion = 8;`、
`CSharpHost.cpp` 的 `s_engineApiVersion = 8;` / `static_assert(sizeof(EngineApi) == 80u` /
`s_interfaceId*` 常量、`Scripting/Managed/EngineApi.cs` 的 `*InterfaceId` 字段。本 change 的
任务 3.1 / 3.2 要求这三处全部退役（改生成常量、说明 struct、删除手写镜像），脚本会走
`JudgeFailure` 退出 2；而任务 4.1 的验收要求它退出 0。启动提示的"允许改动文件范围"未列这份脚本。

**裁定**：批准把 `Tools/check_csharp_host_readme.py` 加入允许改动范围。改法三条硬约束：
① 对拍结构不变（README 全文读数 == 代码真值），只把真值来源换成生成产物
（`BindingRegistry.Bindings.h` 的 `kEngineApiVersion` / `sizeof(EngineApi) == 80u` /
`kBindingInterfaceId*`，生成 `EngineApi.Bindings.cs` 的编号常量）；README 现有每一类扫描项
（函数表 N 字节 / ABI vN / sizeof == N / 托管侧期望 N / 编号表 / 探针开关）都必须有对应新锚点；
② 生成产物缺失或读不到关键常量 ⇒ 保持退出 2（判据自身失效），不许"找不到就跳过"；
③ 红态可构造并留档：README 故意残留一处 v8 或错误字节数 ⇒ 脚本非零点名，改回 ⇒ 退出 0。

**依据引文**：
- `openspec/changes/render-interface-merge/proposal.md`：「判据：`Tools/check_csharp_host_failures.py`
  （期望 8→9）、`Tools/CodeGen/check_bindings.py`（登记表产物纳入对账）、
  `Tools/check_csharp_host_readme.py`、`Tools/CodeGen/check_bindable_audit.py` 口径不变但审计表行仍是硬门。」
- `openspec/changes/render-interface-merge/tasks.md` 4.1：「`check_csharp_host_readme.py`/`check_bindable_audit.py`
  同步与 `SurfaceSignatureCheck.cs` 实测定性：README 的 v8=80 字样、编号表来源说明改后 readme 判据退出 0」。
- `openspec/changes/render-interface-merge/specs/csharp-host/spec.md`：「`CSharpHost/README.md` 全文、
  `Tools/check_csharp_host_readme.py` 与 `Tools/check_csharp_host_failures.py` 三处 MUST 同步为同一 v9=80 读数，
  任一残留旧值即非零。」
- 主 agent 2026-11-05 消息原文：「裁定：**A 批准**。……是我启动提示的允许清单漏抄，现在补齐：

## 2026-11-05 裁决二（执行者自裁，design 开放问题级）：夹具接口与登记表的两个阶段

**问题**：任务 1.1 要求"让该夹具进入登记表发射输入"，而 design D2 写"既有夹具头
（`Tools/CodeGen/BindableShapes*.h`）不进真实登记表"。同时任务 2.1 之前真实接口还是无号
`CA_BIND()`，主登记表无法用真实头发射。

**自裁**：分两个阶段，最终态与 design D2 一致：
- **1.x（任务 1.1–1.4）**：主登记表（产物落 `codegen/bindings/`）的发射输入就是新夹具头
  `BindableShapes.RenderRegistry.h`（编号 8/9）。它是**暂时的**：此阶段真实接口没有编号，
  主登记表只能拿它跑通"编号解析 → 分片 → 汇合 → 两侧产物 → 闸门"。因此这一阶段生成的
  `EngineApi.Bindings.cs` 会引用 `IBindRegistry8/9Bindings` —— 它们与 `EngineApi.Bindings.cs`
  同目录、同一次生成、同一程序集，编译成立。注意 `EngineApiBindings` 用的是生成的
  `EngineApiMirror` 名字（不是手写的 `EngineApi`），所以期间不与 `Scripting/Managed/EngineApi.cs`
  冲突；手写 ABI 仍由宿主使用，直到任务 3.1/3.2 退役。
- **2.1 起（最终态）**：真实接口加号后，主登记表输入换成两个真实头
  （`WindowSystem.h`、`ScriptRenderBridge.h`），夹具登记表移到 `codegen/bindings/fixture/`；
  该子目录不在 `Scripting.Managed.csproj` 的 `$(CascadedBindingDir)\*.Bindings.cs` 通配范围内，
  也不在宿主 include 路径上 —— **夹具接口不进真实宿主的登记表 CS/路由**，与 design D2
  的豁免口径一致。

**理由**：夹具头不在宿主 include 路径上（生成的接口产物用基名 `#include` 自己的头），把夹具
路由编进宿主会找不到头文件；而 1.x 阶段主登记表又必须有一个输入。两阶段切换只改
`build.py` 的 `CODEGEN_REGISTRIES` 与 `check_bindings.py` 的期望表，源头（`CA_BIND(编号)` 标注）
不动。

**依据引文**：

  （真实接口此步未加号，登记表发射对"进表接口缺编号"的非零拒绝只能靠夹具演练证明）。」
- `openspec/changes/render-interface-merge/design.md` D2：「既有夹具头（`Tools/CodeGen/BindableShapes*.h`）
