# 证据-验收-012：截图验收没有写死期望

面：⑥ 截图视觉验收。severity：misleading。

## 工件原文

- `tasks.md:21`：「3.2 截图视觉验收（主循环）：导入真实 PNG/OBJ 后交互打开资产浏览器，CapturePreviewAsync 抓窗（不前置，AGENTS §2）+ read_image 核对底部 dock 显示 kind=texture/mesh registered 条目。验收：evidence/3.2-截图.png + read_image 核对记录；抓不到/不符判不通过。」
- `specs/source-importers-png-obj/spec.md:49-52`：「**WHEN** 导入真实 PNG/OBJ 后交互打开资产浏览器 / **THEN** 底部 dock MUST 显示 kind=texture/mesh 的 registered 条目；CapturePreviewAsync 抓窗经 read_image 核对，MUST NOT 置前/最小化/移动用户窗口」
- `design.md:46`：「截图视觉（编辑器类）：导入后资产浏览器 dock 显示真实 texture/mesh 条目（CapturePreviewAsync 不前置）。」

## 已有抓窗通道（这部分没问题）

`CSharpHost/README.md:428` 已有现成钩子：

> `CASCADED_EDITOR_SELFTEST=capture-dock=<png 路径>`：dock 控制器就绪后每约 0.5 秒把 dock 当前渲染内容用 `CapturePreviewAsync` 覆盖落盘（视觉验收抓窗；不置前/不最小化/不移动用户窗口）

所以「抓窗」本身有工具；问题在「核对什么」。

## 结论

工件没有写死应出现的条目：哪两个路径、什么 kind、registered 是 true、dock 里应有多少行，都没有。`read_image` 的核对记录是散文，主循环可以写「看到 texture/mesh 条目，通过」而无法被第三方复核；如果 `CAAssets` 里已有上一次导入留下的 `.tex`/`.mesh`，旧条目也能满足「真实 texture/mesh 条目」，无法证明这次导入成功。把两行写死（唯一夹具名 + kind + registered + sizeBytes），并要求截图与同一时点的 `list-assets` 读数逐项对上，才能让「不符」有判据。另：既然门控开触发导入目前没有驱动（见验收-008），截图前必须先把导入跑通，否则 dock 里根本没有新条目——这一点也要写进 3.2 的前置步骤。
