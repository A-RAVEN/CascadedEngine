# 影响面其余检查：④ 绑定产物（未发现 blocking）与次级发现

本文件不占 claim 配额，记录没有立成 claim 的检查结果与次级发现（父 agent 可决定是否升级为 claim）。

## 一、④ 绑定产物逐字节不变：核到，未发现 blocking

### 1. `CODEGEN_ANNOTATED` 只收原生头文件，与新增 C# 无关

`build.py`（逐字引文）：

> `# Codegen manifest: header (relative to PROJECT_DIR, the file the sidecar parses), the type name, and`
>
> `# the CMake module root that owns it (used to pick that module's compile env from compile_commands.json).`
>
> `CODEGEN_ANNOTATED = [`

清单条目全部是 `Tools/CodeGen/*.h`、`Interface/.../*.h`、`VulkanRenderBackendNew/...`、`D3D12RenderBackend/...` 的原生头；`Scripting/Managed/` 下没有任何条目。

### 2. 新增 C# 靠 SDK 默认通配编译，不需要进任何清单

`Scripting/Managed/Scripting.Managed.csproj` 只显式加生成的绑定文件（逐字引文）：

> `<Compile Include="@(CascadedBindingFile)" />`

工程里没有 `EnableDefaultCompileItems=false`；现存的 `Scripting/Managed/Assets/Mesh.cs`、`Texture2D.cs` 等也没有出现在 csproj 的 `Compile` 项里，却一直在编译 —— 证明 `**/*.cs` 默认通配生效，新增 `Scripting/Managed/Assets/Importers/*.cs` 会被自动编入。

### 3. 绑定基线的覆盖范围只到生成产物

`Tools/CodeGen/check_binding_baseline.py` 文件头（逐字引文）：

> 输入有两样：
>
> · 基线文件：`<sha256>\t<相对产物目录的路径>` 一行一个…
>
> · 产物目录：`out/build/<预设>/codegen/bindings`（含 `fixture/` 子目录）。

判定口径（逐字引文）：

> ① 基线里列出的文件在产物目录里找不到  ⇒ 缺失；
>
> ② 找到但 SHA-256 与基线不同          ⇒ 内容变了；
>
> ③ 产物目录里有、基线里没有、也不在「允许新增」清单里 ⇒ 多余。

新增纯 C# 文件不在这三类的输入里；工件 4.1 的「缺失0/不一致0/多余0」判据成立。**结论：④ 的声称与判据一致，未发现 blocking。**

## 二、次级发现 A（建议升级为 claim）：新门控会让 `check_csharp_host_readme.py` 变红，任务清单里没有它

`Tools/check_csharp_host_readme.py`（逐字引文）：

> `HOST_CS = REPO / "Scripting" / "Managed" / "Host.cs"`
>
> `USER_SCRIPT_CS = REPO / "Scripting" / "Managed" / "UserScript.cs"`
>
> `used_env = parse_env_names(read(HOST_CS)) | parse_env_names(read(USER_SCRIPT_CS))`
>
> `missing = sorted(name for name in used_env if name not in readme_env)`
>
> `problems.append("README 的环境变量表缺这些开关：" + "、".join(missing))`

`design.md` D1 把门控读在 `Host.cs`（「Host.Tick 里 EnsureBound 后调」）；只要 `Host.cs` 里出现 `Environment.GetEnvironmentVariable("CASCADED_SOURCE_IMPORTERS"…)`，这个脚本就会要求 `CSharpHost/README.md` 的环境变量表登记该名字。工件里没有 README 登记任务，`tasks.md` 4.1 的回归清单也没有这个脚本（只列了 `check_binding_baseline.py`）；而 `docs/testing.md` 的最小集合明确跑它（逐字引文）：

> `python Tools\check_csharp_host_readme.py`

同类漏项在归档里已有先例：`openspec/changes/archive/2026-11-24-editor-web-render-spike/evidence/对抗验证/证据-影响-003.md` 与 `处置` 记录过「新门控撞第④项」，当时补的任务是「门控登记 CSharpHost/README + 4.1 回归命令清单加该脚本」。

## 四、次级发现 C：3.1 要求「Texture2D.Parse/Mesh.Parse 读回」，但 Parse 是 internal，tester 在 C++ 侧

`tasks.md` 3.1（逐字引文）：

> 断言 ② 落盘存在 + Texture2D.Parse/Mesh.Parse 读回像素/顶点/索引==写死期望（逐字节）

两边代码（逐字引文）：

> `internal static Payload Parse(byte[] bytes, string sourcePath)`（`Texture2D.cs`）

> `internal static Payload Parse(byte[] bytes, string sourcePath)`（`Mesh.cs`）

C++ tester 无法调用托管程序集的 `internal` 静态方法；现有 `TestCSharpAssets` 的做法是 C# 侧把读回的十六进制写进读数文件、C++ 侧读原始文件字节并写死期望对照（`Main.cpp` 的 `hexOf` / `appendFloat` 一段）。3.1 没有写这条读数通道（`CASCADED_SOURCE_IMPORTERS_*` 只规划了目录变量）。
