## 一、结论

`Host.Tick` 这个挂点真实存在（`Host.cs:303 EnsureBound()` 后有一串探针调用，`ResourceImporterProbe.Tick` 在 `Host.cs:330`），但「C# 造出导入器」不等于是「C++ 管线能拉到它」：`AddImporter` / `ScanSourceDirectory` 都只有 C++ 入口，C# 侧没有绑定，也没有任何任务安排原生侧接线。按 design D1 + tasks 2.3 的字面实现，门控开只会造出一个托管对象，② 文件不会产生。

## 三、影响

1. Host.Tick 里创建的 C# 导入器实例如果不把强句柄交出去，C++ 侧拿不到句柄，`ResolveImpl` 无从调用，`AddImporter` 无从添加。
2. 即使 tester 用例（3.1）里补了 C++ 侧接线，tasks 2.3 的验收（单独「门控开→② 落盘 + HasResource 真」）仍然不成立：2.3 的验收跑不到 3.1 的 C++ 代码。
3. 所以要么在 2.3 之前补「句柄出口 + 原生 AddImporter」两条任务，要么把 2.3 的验收降级成 C# 侧读数（创建成功/标签/Produce 被调），把落盘与 HasResource 移到 3.1。

## 四、修法（建议）

- 新增任务 A：C# 导入器创建后把强句柄、门控状态、标签写进约定读数文件（照 `ResourceImporterProbe` 的 `CASCADED_CSHARP_IMPORTER_READINGS` 模式，变量名独立，避免与旧探针冲突）。
- 新增任务 B：tester 用例按 `TestCSharpImporter` 先例读句柄 → `ResolveImpl` → `AddImporter` → `ScanSourceDirectory`，并断言 `Produce` 调用次数、② 文件、`HasResource`。
- 或者：把「注册导入器」做成一个可绑定门面（会改绑定面/接口，与 2.3「不改接口」冲突，需在工件里明确取舍，二者只能选一）。
