# 证据-一致-005：走工厂/AssetDatabase 时第二轮重导入必撞门面「同路径先拒绝」并双份所有权

## 主张

design D4 第一条路径让导入器在 Produce 内用 `AssetDatabase.Create`，它第一件事就是门面 `CreateResource` → 注册。于是第二轮重导入对同一路径再 Create 时，门面守卫直接拒绝（1014），`Produce()` 抛异常，`ScanSourceDirectory` 中止；spec 的「第二轮注册新对象替换旧」无法发生。若绕开门面先 `ReleaseResource`，则管线又会对已被注册表持有的 C# 对象二次包 `shared_ptr` 并再注册，所有权重复。

## 两条时序（按 D4 第一条）

**第一轮**：Produce → `AssetDatabase.Create("Texture2D", "Textures/foo.tex")` → 门面 CreateResource → 注册表里已有 `Textures/foo.tex`；再 `NextResource()` 返回同一个托管对象 → 生成 glue 用 `CreateProxy` 再造一个代理 → 管线 `ReleaseResource`/`RegisterResource` 同一路径。结果：同一托管对象两次代理、双重所有权。

**第二轮**：Produce → `AssetDatabase.Create` 同一路径 → `HasResource` 真 → `ReportRejected` 抛 1014 → `Produce()` 异常 → `ScanSourceDirectory` 在 `while (HasNext)` 之前/之中终止，连 `SerializeAll`（第 96 行）都不会执行。spec 的「第二轮替换」场景永远达不到。

## 为什么是 blocking

1. spec 的重导入场景（第 40–43 行）与 `resource-importer` 规范的「CreateProxy 单一强所有者」都被这条路径否掉。
2. 失败方式是「异常穿出 Produce」，与 design D5 的「失败可见」也不同：一个源文件的坏数据不该让整轮扫描中止（但按 D5，坏文件确实抛；这里是正常文件在第二轮被拒）。
3. 这不是措辞问题：门面守卫的 `HasResource` 分支在现有代码里已经存在（`CSharpHost.cpp:229-233`），按 D4 实现必然触发。

## 改法

1. design D4 删掉工厂/AssetDatabase 分支，统一走「直接 new + CreateProxy + 管线注册」。
2. 若坚持要复用资产工厂：在 AssetDatabase 新增「只造不注册」入口（例如 `CreateUnregistered`），并且它 MUST NOT 调门面；同时增加工厂注册与门面绑定的任务（参照 `ResourceAssetProbe.cs` 第 136–138 行）。但这会改既有资产层语义，需要单独 MODIFIED `csharp-asset-layer`，与该 change「不改其要求」冲突 —— 不推荐。
3. spec 的重导入场景保留不变（这是既有规范的正确语义）。

## 复核方式

1. 改后导入器文件 grep `AssetDatabase|IResourceRegistry` 应 0 命中。
2. 红态：若实现仍走门面，跑第二轮 `ScanSourceDirectory`，日志必须出现「资源路径已存在，先释放再新建」且 `SerializeAll` 未执行 —— 这就是本条的证据。
3. 绿态：按「直接 new」实现后，`TestCSharpImporter` 的「旧代理 1001、新对象 ReferenceEquals 假」断言风格可直接复用，证明第二轮真替换。
