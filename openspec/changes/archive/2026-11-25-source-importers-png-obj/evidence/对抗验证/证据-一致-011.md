# 证据-一致-011：门控放在 Host.Tick，但导入只能由 C++ 管线扫描触发（且扫描早于首个 Tick）

## 主张

design D1 与 tasks 2.3 把新门控接在 `Host.Tick`（托管），但真正执行「导入」的是 C++ 的 `ResourceImportingSystem::ScanSourceDirectory`；托管侧没有 `AddImporter` / `ScanSourceDirectory` 的任何绑定入口。整机唯一一次启动扫描在 `Main.cpp:10588`，出现在测试开始之前；所有托管 `Tick` 调用都在测试函数体里或收尾循环里。既有 C# 导入器先例是 C++ 测试自己 `AddImporter` + `ScanSourceDirectory`。因此按 design 实现，门控打开也不会导入；proposal 的「本批门控触发导入」没有落地任务。

## 为什么是 blocking

1. 门控位置与触发机制不匹配：Host.Tick 里的代码最多能创建托管导入器对象，无法把它们塞进原生 `m_ResourceImporters`，也无法调用扫描。
2. 启动扫描发生在首个 Tick 之前：即使托管门控在 Tick 里创建了导入器，本轮扫描已经过去了；除非 C++ 再加一次显式扫描（没有任务）。
3. 先例已经证明 C# 导入器必须由 C++ 侧接线（`AddImporter` + `ScanSourceDirectory`，Main.cpp:8881-8887）；工件把这件事写成「门控接入 Host.cs」，会让实施者做完托管侧后误以为门控已生效。
4. 三处说法不一致：design（Host.Tick 调）、tasks（门控接入 + 管线拉取）、proposal（门控触发导入）没有任何一处点出 C++ 接线任务。

补一条反驳预防：既有探针确实提供过一条 C#→C++ 的句柄通道 —— `ResourceImporterProbe` 把 `importer_handle` 写进 `CASCADED_CSHARP_IMPORTER_READINGS` 文件，C++ 侧 `readU64("importer_handle")` 后 `ResolveImpl` + `AddImporter`（Main.cpp 第 8852、8872–8881 行）。但本 change 的 design/tasks **没有写这条通道**：没有读数文件变量、没有句柄读数、没有「C++ 读句柄再 AddImporter」的任务。所以不能拿「先例存在」当成「工件已规定」；要么把这条通道写进 tasks，要么按方案 B 改 C++ 启动接线。

## 改法

- 方案 A（本批最省）：沿用 `TestCSharpImporter` 模式 —— 在 `TestSourceImporters` 里 C++ 侧 `AddImporter` 两个 C# 导入器（经 `ResourceImporterBindings.Create` 的强句柄 + `ResolveImpl`），再调 `ScanSourceDirectory`；门控只用于让 C# 侧在测试的 Tick 阶段把导入器对象建好并写读数。proposal 删「门控触发导入」，spec 的门控场景改成「门控开时测试可驱动导入」。
- 方案 B（产品级）：新增 C++ 接线任务：在 Main.cpp:10588 之前按门控创建/解析两个导入器并 `AddImporter`；同时加断言「门控关闭时 `m_ResourceImporters` 不含这两个、启动扫描零新产出」。这需要改 C++ 测试启动路径，proposal 的 Impact 要同步列出。

## 复核方式

1. 改后 tasks 必须能指到一条具体的 C++ 接线任务（文件 + 函数 + 位置），否则仍是空承诺。
2. 绿态：门控开 + `TestSourceImporters` 跑完后日志出现 `Textures/*.tex`、`Meshes/*.mesh` 的注册与落盘；`HasResource` 真。
3. 红态：门控关时同一用例断言这两个导入器未被 `AddImporter`、启动扫描产物与基线零差异。
