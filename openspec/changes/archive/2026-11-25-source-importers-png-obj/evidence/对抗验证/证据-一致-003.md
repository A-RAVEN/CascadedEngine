# 证据-一致-003：OBJ 索引基数/负索引/未引用顶点未规定，「写死期望」不可推导

## 主张

工件把「位置+默认色、stride 24」的布局说清了（这一点与 `Mesh.cs` 三常量、`SceneRenderer.cs` 三常量逐字一致），但 OBJ 面索引怎么映射到 `IndexData` 没写清：1 基要不要减 1、负索引怎么算、未被面引用的顶点算不算 VertexCount。tasks 1.2 / 3.1 的验收是「解析顶点/索引 == 写死期望」「VertexCount/IndexCount/VertexData/IndexData == 写死期望」，期望值只能从工件推导 —— 现在推不出来。

## 为什么是 misleading 而不是 blocking

- 它不会让构建或运行直接失败：实施者任选一种口径都能写出自己的「写死期望」，测试照样绿。
- 但它让判据失去分辨力：错误的映射（例如 1 基直传）与正确的映射会各自配一份「写死期望」，红态也构造不出（因为断言期望就是实现者自己写的）。这正好是「期望值不从被测物推导」原则被破坏的地方。
- 同一文件里「缺顶点/索引越界」还依赖口径：1 基直传时 `f 1/...` 会被当成越界，实施者会以为是坏文件；负索引则可能被误判。

## 改法

在 design D3 与 spec 第 19 行补三句并同步 tasks 1.2 的期望：

1. `f` 的顶点索引按 **1 基**读入，写 `IndexData` 前减 1；
2. 负数索引按「当前已解析 `v` 数 + 负数」转绝对下标，转完 `<0` 或 `>=` 顶点数 → `AssetFormatException` 点名文件与索引值；
3. `VertexCount` = `v` 行数（未被引用的顶点保留、不重排、不去重），三角形按面出现顺序 + 扇形顺序追加。

再把立方体夹具的具体期望写死（8 顶点 / 12 三角 / IndexCount=36 / 前 12 个索引值 …），红态加一条「把某个 1 基索引改成 0，必须点名越界」。

## 复核方式

1. 改后 grep 口径关键词应命中 ≥3（1 基、负数、未引用）。
2. 用同一份已知 OBJ，按工件三条口径手算期望，与 tasks 里写死的数字逐项比；不一致即工件仍未收敛。
3. 红态：把夹具里一个 `f` 索引从 1 改成 0（1 基口径下越界）→ 解析必须抛 `AssetFormatException` 并点名该索引；若静默通过，说明口径落进了代码却没进判据。
