# 证据-溯源-003：工件没写「多 IDAT 必须拼接」，验收夹具也覆盖不到

> 定位以逐字引文为准；行号是 2026-11-24 审查时实测值。

## 一、主张摘要

- 主张编号：主张-溯源-003
- 攻击面：无中生有（把「PNG 的 IDAT 是一段 zlib 流」当成了完整事实）
- 严重度：blocking（会误导实现，且现有验收抓不到）
- 工件：`design.md:28`、`tasks.md:9`、`spec.md:5`
- 一句话：PNG 允许任意多个 IDAT 块，压缩流是**全部 IDAT 数据字段的拼接**；工件只写「IDAT（zlib 流）」，没写拼接，验收也没有多 IDAT 夹具。

## 三、规范原文（RFC 2083）

第 990-994 行：

> There can be multiple IDAT chunks; if so, they must appear
> consecutively with no other intervening chunks.  The compressed
> datastream is then the concatenation of the contents of all the
> data fields of the IDAT chunks.

第 1665-1675 行：

> In a PNG file, the concatenation of the contents of all the IDAT
> chunks makes up a zlib datastream as specified above.  This
> datastream decompresses to filtered image data as described elsewhere
> in this document.
>
> It is important to emphasize that the boundaries between IDAT chunks
> are arbitrary and can fall anywhere in the zlib datastream.  There is
> not necessarily any correlation between IDAT chunk boundaries and
> deflate block boundaries or any other feature of the zlib data.  For
> example, it is entirely possible for the terminating zlib check value
> to be split across IDAT chunks.

## 五、结论与建议

- 按工件实现，最自然的写法是「找到 IDAT 块 → 取它的数据 → 跳过 2 字节 → 解压」。这对单 IDAT 的小图成立；对多 IDAT 的合法文件，解压输入被截断，DeflateStream 要么提前结束（长度不足），要么在下一个块之前就碰到流尾。
- 验收侧同样抓不到：1.1 / 3.1 只要求「已知 PNG 夹具」，没有要求多 IDAT 夹具；一个只读第一个 IDAT 的实现在现有判据下可以全绿。
- 建议改法（不放松判据）：
  1. design.md:28 改为「按顺序拼接所有 IDAT 块的数据字段后作为一条 zlib 流解压」；
  2. tasks.md 1.1 的夹具要求里加一条「多 IDAT 夹具（同一 PNG 拆成 ≥2 个 IDAT 块），解码像素与单块版逐字节一致」；
  3. spec.md 的场景里点名多 IDAT 也算合法输入。
- 注意：这条不是要引入新功能，只是把 PNG 既有规则补全；判据只会更严。

## 六、边界

- 核了：RFC 2083 第 990-994、1665-1675 行；工件的 IDAT 表述与「多 IDAT/拼接」0 命中。
- 没核：没有生成或解码任何真实多 IDAT PNG（只读环境，不跑构建/测试）；没有核 PNG 第三版是否改过这条（自 1.0 起未变，多块规则一致）。
