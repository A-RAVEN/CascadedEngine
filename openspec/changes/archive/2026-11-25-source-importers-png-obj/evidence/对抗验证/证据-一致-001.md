# 证据-一致-001：`Mesh.Parse` / `Texture2D.Parse` 是托管 internal，C++ tester 调不到

## 主张

tasks 3.1 把「`Texture2D.Parse` / `Mesh.Parse` 读回像素/顶点/索引 == 写死期望」写成 `Main.cpp` 里 `TestSourceImporters` 的断言，但两个 `Parse` 都是 `Scripting.Managed` 程序集内部的 `internal static` 方法，C++ tester 没有任何调用路径；工件也没有新增 C# 探针或导出的任务，这条验收不可执行。

顺带核实本面被点名的一致性：Mesh 顶点布局四处**是一致的**，不是缺陷 —— `Mesh.cs` 第 31–33 行 `VertexStride = 24` / `PositionOffset = 0` / `ColorOffset = 12`，`SceneRenderer.cs` 第 42–44 行 `VertexStride = 24` / `PositionOffset = 0` / `ColorOffset = 12`，design D3、spec 第 19 行、tasks 1.2、`csharp-asset-layer` 规范第 11 行都写 24/0/12（位置 float3 + 颜色 float3，stride 24）。OBJ 无法线/UV 而 Mesh 布局是位置+色这件事，design D3 明写「忽略 vt/vn 本批不支持」「OBJ 无顶点色，色用写死默认」，映射说清了。

## 为什么是 blocking

1. 3.1 的验收命令是「独立进程跑 tester 用例」，断言点却在另一个语言/进程边界内；按 tasks 做完不可能拿到这条读数。
2. `internal` 不是公开面，任务没有授权改可见性，也没有新增探针任务；实施者只会得到两条路：违规改资产层可见性，或悄悄不验。前者动既有资产层，后者让 3.1 的「逐字节」判据变空。
3. 同一批 tasks 的其它验收都写了读数来源（`evidence/1.1-*.txt`、`CASCADED_*_READINGS`），只有这条没写，属可执行性缺口而不是措辞问题。

## 改法

- 方案 A（推荐，沿用现有惯例）：加一条 C# 探针任务 `Scripting/Managed/SourceImporterProbe.cs`（与 `ResourceAssetProbe.cs` 同款：环境变量门控、阶段机、读数文件），在探针里调 `Texture2D.Parse` / `Mesh.Parse`（同程序集可见）把宽高/格式/像素/顶点/索引读数写文件；`TestSourceImporters` 读同一份读数断言。这样 `internal` 不需要改。
- 方案 B：C++ 直接读落盘文件，按 CATX 头部 28 字节、CAMH 头部 32 字节解析后与写死期望比字节；与 `csharp-asset-layer` 的「C++ 侧读文件、期望值写死在 C++ 侧」同源。
- 无论哪条，都要在 tasks 里写清「验的是落盘原始字节，不走注册表 Deserialize」。

## 复核方式

1. `Select-String -Path 'Scripting/Managed/Assets/Mesh.cs' -Pattern 'internal static Payload Parse'` 应仍命中 1 行（证明 `internal` 未被改）。
2. 按改后的 tasks 走：先跑 C# 探针拿到读数文件，再跑 `GPUBackendTester.exe --test TestSourceImporters`；把读数文件路径与 tester 日志一起存档到 `evidence/3.1-*.txt`。
3. 红态：把探针里某个期望像素改错 1 字节，tester 必须非零退出并点名该字段；若不红则判据不合格。
