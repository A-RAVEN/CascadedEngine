# 证据-溯源-015：design 允许导入器用 AssetDatabase，而它就是注册表写入口

> 定位以逐字引文为准；行号是 2026-11-24 审查时实测值。

## 一、主张摘要

- 主张编号：主张-溯源-015
- 攻击面：无中生有（把「不调注册表」当成「文件里不出现那五个词」）
- 严重度：blocking（规范 MUST 与 design 的推荐做法互斥，词面判据抓不到）
- 工件：`design.md:36`、`spec.md:33`、`tasks.md:14`、`tasks.md:15`
- 一句话：`AssetDatabase.Create` 第一行就是 `CreateResource`，`Load` 里的 `ReleaseResource`、`SaveAll` 里的 `SerializeAll` 同理；导入器照 D4 写就违反了「注册/落盘 MUST 由管线做」，而 grep 仍然是 0。

## 四、管线自己的注册与落盘（证明「双写」）

`GeneralResources/private/ResourceImportingSystem.cpp:77-96`（节选）：

> while (productions->HasNext())
> {
>     castl::string const relativePath = productions->NextPath();
>     IResource* produced = productions->NextResource();
>     …
>     m_ResourceManagingSystem->ReleaseResource(relativePath);
>     m_ResourceManagingSystem->RegisterResource(relativePath, resource);
> }
> …
> m_ResourceManagingSystem->SerializeAll();

即：管线在 NextResource 之后本来就会 Release+Register+SerializeAll。导入器若再走 `AssetDatabase.Create`，同一个路径会被 `CreateResource` 先注册一次（且 `CreateResource` 内部还会 `RegisterResource`），随后管线再 Release 再 Register；`AssetDatabase.SaveAll` 又会在管线之外多落盘一次。

`Scripting/Managed/ResourceAssetProbe.cs`（既有用法，证明 AssetDatabase 是给**测试/加载侧**用的，不是给导入器用的）：

> 见该文件里 `new AssetDatabase(registry)` / `Create` / `Load` / `SaveAll` 的调用点（探针自己在 C# 侧新建/落盘/读回，不经过管线）。

## 六、结论与建议

- design D4 把两条路并列，但只有第二条（直接 `new` 资产交迭代器）与 spec 的「注册由管线做」相容；第一条（AssetDatabase）必然间接写注册表/落盘，而词面 grep 抓不到。
- 这不是「措辞」：照第一条实现，行为上会有两次注册与两次落盘（一次来自 AssetDatabase，一次来自管线），且第一次注册发生在 Produce 执行期间——正好是 spec 禁止的「导入器调注册表」。
- 建议改法：
  1. `design.md:36` 删掉 AssetDatabase 那条，只保留「直接 new 资产填数据交迭代器」；AssetDatabase 的用法限定在测试侧读回（见主张-溯源-017）。
  2. 判据加一条行为判据，词面 grep 之外再钉：Produce 调用期间注册表条目数与落盘文件不变（可用 HasResource/文件修改时间或锁），或给导入器注入一个「只读」注册表句柄（若有）。
  3. `tasks.md` 2.1/2.2 的验收补一句「导入器文件里 MUST NOT 出现 AssetDatabase 标识符」，把间接路径也堵住。

## 七、边界

- 核了：AssetDatabase 三个方法里的注册表调用、管线自己的 Release/Register/SerializeAll、既有探针把 AssetDatabase 用在测试侧。
- 没核：没有跑任何 Produce（实现尚不存在）；没有检查 AssetDatabase 是否可能拿到注册表（构造器要 IResourceRegistry，Host 侧有 s_api/s_system，技术上拿得到——所以这条不是不可达的假设）。
