# 证据-溯源-012：RGB 补的 alpha 值与 OBJ 默认顶点色都没钉死

> 定位以逐字引文为准；行号是 2026-11-24 审查时实测值。

## 一、主张摘要

- 主张编号：主张-溯源-012
- 攻击面：无中生有（默认值只给意象不给数字，验收却要逐字节比对）
- 严重度：misleading（不钉死会让「写死期望」变成抄实现，但不至于实现不了）
- 工件：`design.md:28`、`design.md:32`、`tasks.md:10`、`spec.md:19`
- 一句话：alpha 补 255 还是 0、OBJ 默认色到底是 (1,1,1) 还是别的，工件没定；而验收写的是「逐字节一致」。

## 三、对照：仓库里同类默认值都写成了常量

`Scripting/Managed/Assets/Mesh.cs:31-33`（布局常量写死，可核）：

> public const uint VertexStride = 24;
> public const uint PositionOffset = 0;
> public const uint ColorOffset = 12;

`Scripting/Managed/ResourceImporterProbe.cs:34-35`（既有探针连两字节内容都写死）：

> internal static readonly byte[] BytesA = { 0xC5, 0x01 };
> internal static readonly byte[] BytesB = { 0xC5, 0x02 };

即：这个仓库的惯例是把期望值写成代码常量，而不是靠散文描述；本批两处默认值反而不符合该惯例。

## 五、结论与建议

- 影响一：RGB→RGBA 的 alpha 若取 0，整张图全透明；若取 255，不透明。两种都「长度合法」，落盘与 Parse 都会成功，测试若从实现取期望值就完全发现不了。
- 影响二：OBJ 默认色若取 (0,0,0)，网格在场景里是黑的；若取 (1,1,1)，是白的。工件用「如」描述，tasks 只说「默认色」。
- 建议改法（把数字钉进工件，判据更严）：
  1. `design.md:28` 改为「颜色类型 2 补 alpha=255（不透明）」；
  2. `design.md:32` 去掉「如」，改为「默认色 (1,1,1)，写进 tasks 1.2 的验收里作为写死期望」；
  3. `spec.md:19` 把「写死默认色」改成「写死默认色 (1,1,1)」，避免规范与 design 各说各话。
- 不构成 blocking 的理由：实现者可以自己选一个值并写进代码常量；但选择过程不该是隐式的，且验收期望不能由实现自证。
