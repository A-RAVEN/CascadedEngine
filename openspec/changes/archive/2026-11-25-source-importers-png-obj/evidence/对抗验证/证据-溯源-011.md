# 证据-溯源-011：灰度（颜色类型 0/4）既不在支持面、也不在拒绝面

> 定位以逐字引文为准；行号是 2026-11-24 审查时实测值。

## 一、主张摘要

- 主张编号：主张-溯源-011
- 攻击面：无中生有（把「不支持清单」当成完整清单，漏掉两种合法颜色类型）
- 严重度：blocking
- 工件：`design.md:28`、`spec.md:5`、`tasks.md:9`
- 一句话：合法颜色类型是 0/2/3/4/6；工件只支持 6/2、显式拒绝 3，0 与 4 没有任何规定。

## 二、工件原文

`design.md:28`（节选）：

> 解析 PNG 签名 + IHDR（宽/高/**位深 8/颜色类型 6 RGBA 或 2 RGB→补 alpha**）+ IDAT（…）。**只支持 8 位深非隔行**（Adam7 隔行/16 位/调色板明确抛 AssetFormatException 点名不支持）。

`spec.md:5`（节选）：

> …8 位 RGBA/RGB→RGBA8，不调 native stb、不动绑定面…**不支持的 PNG（16 位/隔行/调色板）MUST 抛 AssetFormatException 点名，MUST NOT 静默。**

`tasks.md:9`（1.1 节选）：

> 签名+IHDR（宽/高/位深 8/颜色类型 6 RGBA 或 2 RGB→补 alpha）+IDAT（…）；**16 位/隔行/调色板**抛 AssetFormatException 点名。

## 三、规范原文（RFC 2083）

第 857-860 行：

> Color type is a single-byte integer that describes the
> interpretation of the image data.  Color type codes represent
> sums of the following values: 1 (palette used), 2 (color used),
> and 4 (alpha channel used). Valid values are 0, 2, 3, 4, and 6.

第 862-882 行：

> Bit depth restrictions for each color type are imposed to
> simplify implementations and to prohibit combinations that do
> not compress well.  Decoders must support all legal
> combinations of bit depth and color type.  The allowed
> combinations are:
>
>    Color    Allowed    Interpretation
>    Type    Bit Depths
>
>    0       1,2,4,8,16  Each pixel is a grayscale sample.
>
>    2       8,16        Each pixel is an R,G,B triple.
>
>    3       1,2,4,8     Each pixel is a palette index;
>                        a PLTE chunk must appear.
>
>    4       8,16        Each pixel is a grayscale sample,
>                        followed by an alpha sample.
>
>    6       8,16        Each pixel is an R,G,B triple,
>                        followed by an alpha sample.

## 五、结论与建议

- 8 位、非隔行、颜色类型 0 的 PNG 是完全合法的文件（很多工具导出的灰度图就是它）。工件既没写「支持」（支持面只有 6/2），也没写「拒绝」（拒绝面只有 16 位/隔行/调色板）。实现者的自然写法是 `switch (colorType) { case 6: …; case 2: …; }`，0/4 直接落到 default 或崩在别处。
- 两种后果都坏：
  1. 静默：若把灰度样本当 R 写、G/B 留 0、A 留默认值，会产出一张「看起来是红色/黑色」的错图，像素长度仍然合法，落盘成功；
  2. 非点名：抛 `ArgumentException`/`IndexOutOfRange` 之类，不满足 spec 的「AssetFormatException 点名」。
- spec 的「MUST NOT 静默」按字面只覆盖括号里那三种，0/4 落空。
- 建议改法（二选一，都更严）：
  1. 支持面加上颜色类型 0（灰度复制到 RGB、alpha=255）与 4（灰度复制到 RGB、alpha 取样本值）；
  2. 保持不支持，但把拒绝清单补成「16 位 / Adam7 隔行 / 调色板（类型 3）/ 灰度（类型 0）/ 灰度+alpha（类型 4）」，并给每种一个红态用例。
- 顺带：`tasks.md:9` 与 `spec.md:5` 的清单不一致（前者多了「颜色类型 6/2」的支持面，后者只写「8 位 RGBA/RGB」），修的时候一起对齐。

## 六、边界

- 核了：RFC 2083 的颜色类型表与「必须支持所有合法组合」的句子；工件三处清单。
- 没核：没有实际解码一张 8 位灰度 PNG 来观察程序的真实反应（只读环境，不跑构建/测试）；上述后果是按工件文字推导的两条可能路径。
