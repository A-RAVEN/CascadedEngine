## 3. 模块 teardown 依赖审计

- [x] 3.1 逐模块 grep/读各模块 `Release()`/`Shutdown`/析构，核对是否 deref **更高注册 index** 的 peer。**结论：8 模块全部 SAFE**（Explore 子代理审计，覆盖 TimerSystem(0)/ThreadManager(1)/backend(2)/ShaderCompilerSlang(3)/WindowSystem(4)/IOManager_FS(5)/CAGeneralReourceSystem(6)/IMGUIContext(7)）。关键证据：①**唯独 backend(2) 引用更高 index peer**（ShaderCompilerSlang 3/WindowSystem 4，运行时经 `GetInstance<>` lazy 获取），但**其析构/Release()/~VulkanWindowHandle/CleanupSwapchain 均不 deref 它们**——`Release()` 只碰 backend 自有 vk 对象，`shaderCompiler`/`p_ResourceImporter` 是 Init 内局部变量（`RenderBackend_Vulkan.cpp:173-174`）不持久化，`m_ShaderImporter` 持**裸非拥有** compiler 且析构无 deref（`~ShaderImporter_Vulkan()=default`），`CleanupSwapchain→GetDevice()` deref 的是 backend **自身**（pApp=self）；②`~WindowImpl` 只 drop 裸 `WindowSystem*`/`GLFWwindow*` 成员值、无模块 deref；③**IMGUIContext(7) 逆序下先析构**，`~IMGUIContext` 销毁 `m_WindowHandles`（强引用）→ `~VulkanWindowHandle`→`CleanupSwapchain`→`GetDevice()`=pApp 时 **backend(2) 仍活、device 有效 → 0xDD UAF 消除**（正中要修点）。**建议（latent，非缺陷）**：backend 对更高 index peer 的引用是运行时 lazy——若未来 backend 析构/Release 开始调 ShaderCompiler/WindowSystem，会引入 UAF；已在 design Open Questions 标注。
- [x] 3.2 审计 `m_Modules`(DLL) 第二阶段的 `TryRelease` 是否依赖实例存活。**结论：零依赖，保持**。证据：`TryRelease` **无任何模块导出**（`CAModuleImplementation.cpp:16` 与 `.h:109` 均注释掉）→ `pTryShutDownFunc=nullptr`（`CAModuleManager.cpp:13` GetProcAddress 取不到）→ `CAModule::Shutdown` 仅 `FreeLibrary`（:36-50），从不 deref 实例；且二阶段在析构中固定位置运行（在实例循环之后），与正/逆序无关。另：tester 为 **static 构建**（`CA_STATIC_BUILD=1` 默认），模块经 `StaticInitModule` 注册 → `m_Modules` 为空 → `m_Modules.clear` 本就是 no-op。
