【阻断 1】产物文件名仍是短名，同短名共存会写同一路径（1.1/1.3 无法按现工件实现）
  证据：
    CodeGenMain.cpp L11924  const std::string cppPath = ... + shape.name + ".Bindings.cpp";
    CodeGenMain.cpp L11925  const std::string csPath  = ... + shape.name + ".Bindings.cs";
    CodeGenMain.cpp L12730  cpp += "#include \"" + entry.shortName + ".Bindings.cpp\"\n";
    build.py L1237  短名重复即失败（"绑定清单冲突：短名 %s 同时对应 %s 与 %s"）
    build.py L1287  shared_types 产物路径 out_dir / f"{short_name}.Bindings.cs"
    Scripting/Managed/Scripting.Managed.csproj L32  <CascadedBindingFile Include="$(CascadedBindingDir)\*.Bindings.cs" />
  推理：`ns1::Device` 与 `ns2::Device` 同一次构建 → 两次 --emit-binding 都写
        `Device.Bindings.cs/.cpp`，后写覆盖先写；registry 的 `#include "Device.Bindings.cpp"` 也会重复
        包含同一份、漏掉另一份。工件（proposal/design/spec/tasks）没有任何一条规定产物文件名规则，
        而 spec 的"跨命名空间同名接口同构建共存"场景要求两者各自成面、构建全绿。
  需要裁定：产物文件名/落盘目录用什么规则（例如按镜像命名空间分子目录，或文件名带限定名线形），
        以及随之要改的 build.py 期望前缀、csproj/CMake glob、CoreTests/tester 的 #include。

【阻断 2】C++ 文件作用域辅助标识符仍以短名为前缀，同短名共存会在同一翻译单元里重定义
  证据（out\build\x64-debug\codegen\bindings\IBindNativeShape.Bindings.cpp 实测）：
    typedef struct NativeCountC ...
    static ca_bind_fixture::NativeCount IBindNativeShape_fromC_NativeCount(...)
    static NativeCountC IBindNativeShape_toC_NativeCount(...)
    typedef struct IBindNativeShapeLayoutFieldData / IBindNativeShapeLayoutTypeData ...
    static const IBindNativeShape_layoutFields0[] / IBindNativeShape_layoutTypes[]
    static <ret> IBindNativeShape_thunk_<方法>(...)
    static const int32_t IBindNativeShape_ERROR_<码名> ...
    （另有 <短名>Handle、<短名>Bindings 等）
  并且 BindingRegistry.Bindings.cpp L12730 把全部接口产物 `#include` 进**同一个 TU**。
  推理：`ns1::Device`/`ns2::Device` 两份产物进同一 TU → 同名 typedef/static 函数/常量重定义（C2011/C2084）。
  工件 D1/D2 只规定命名空间与槽名，没有规定这些文件作用域辅助名的去碰撞规则。
  需要裁定：辅助名是否也改限定名线形（或把它们包进按限定名命名的 C++ namespace）。

【观察 3】其它已确认但可照现有工件执行的点

  - check_bindings.py 的 `CPP_SYMBOL_RE` / `ERROR_CONST_RE` / `THUNK_ANCHOR_RE` 按单下划线切接口名，

  - 审计表 ROW_RE 的字符类放不下 `::`（第四节），2.2 必须同步改正则。
