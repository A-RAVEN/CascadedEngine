## 逐条处置

| 裁决 | 来源 | 问题 | 处置 |
|---|---|---|---|
| B1 | 复核-0014 | `GPUBufferDescriptor` 的两个 `uint64_t` 字段生成 `ulong`，现有共享类型判据会同时报“未登记”和“禁用 ulong”。 | 修订 design 第七节与 tasks 4.2：登记该共享记录，允许两个定宽字段使用 `ulong`，继续拒绝公开方法中的原生句柄和未登记 `ulong`；增加删错字段与句柄混入的红态。 |
| B2 | 复核-0004、0017、0018 | 中心 84–86 依赖未固定的尺寸，320×240 下正确渲染也可能越界。 | 改用三个实色顶点，中心精确要求 `(255, 0, 0, 255)`；`bad-vertex` 改一个顶点为蓝色，仍证明插值来自 C# 数据。proposal、design、spec、tasks 与 tasks 6.2 已同步。 |
| B3 | 复核-0007、0013 | 五个可失败方法返回 `void`，无法观察“非零”和错误文本。 | 建图与提交方法改为 `int32_t` 状态，并增加对应对象的 `GetLastError()`；spec 与 tasks 同时检查非零状态、参数文本、实现未进入和成功清错。 |
| B4 | 复核-0005 | 探针依附全进程只调一次的 `OnEngineReady`，会被先前测试消耗。 | 改为独立的 `OnRenderProbe` 和独立调用标记，由 `TestCSharpTriangle` 在自己的 Tick 前设置并清理开关。 |
| M1 | 复核-0001 | 删除 `Present` 不影响离屏像素，原“删任一调用必红”抓不住。 | 新增真实 `GPUGraph` 呈现清单断言和 `skip-present` 负向模式，不只依赖像素。 |
| M2 | 复核-0003、0008、0012、0015 | “每图至多一个呈现目标”没有 Roadmap 或代码出处。 | 删除上限和错误归属；`Present` 仍只接受后台缓冲，示例只用一个窗口，不改变现有多目标语义。tasks 6.4 留下改前改后对照。 |
| M3 | 复核-0009 | 重复审计行不会使脚本或构建失败。 | tasks 1.1 与 spec 明确要求重复行非零，审计脚本按“头文件方法数与表内行数必须相等”检查，并加入重复行变异证据。 |
| M4 | 复核-0010 | 审计表写死 60 条/7 接口，新增方法后会自相矛盾。 | tasks 1.1 要求同步接口数和方法合计，审计脚本用头文件实算数字核对汇总；不符必须非零。 |
| M5 | 复核-0006 | 要求离屏目标与窗口同尺寸，但没有可核窗口尺寸的入口。 | `GetWindowTarget` 保存窗口描述快照，原生测试用它核对离屏目标宽、高和格式；不一致必须失败。 |
| P1 | 复核-0002 为 false-positive，复核-0011 为 verified | 两条对 `WaitIdle` 的结论冲突；原判据只依赖后端内部同步，无法证明 C# 调用了等待。 | 采用需要补判据的处置：记录 `WaitIdle` 调用次数，核对调用增加和待完成集合清理，并增加 `skip-wait`。不再仅用后端是否已有内部同步判断该调用是否可观察。 |
| P2 | 复核-0016 | 全量运行要求新像素测试通过，但未写探针开关由谁何时设置。 | 与 B4 同步处置：`TestCSharpTriangle` 在自己的 Tick 前设置并清理开关，独立入口不被先前一次性脚本调用影响；spec 新增全量运行场景。 |

## 复核结论

11 个裁决条目均已修订，没有“保留不改”的条目。修订没有通过删除测试、降低像素要求、放松审计或取消句柄检查来取得通过；呈现数量上限的删除是因为它没有用户、Roadmap 或代码依据，且现有 `GPUGraph` 本就支持多个呈现目标。
