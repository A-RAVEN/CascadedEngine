## Context

`IWindowSystem` 的 C++ 面有 16 个方法，当前只有 `NewWindow`、`GetWindowCount`、`GetMonitorCount`、`UpdateSystem`、`GetSystemNativeHandle` 进入 C# 函数表。其余 11 个方法被 `CA_BIND_SKIP` 排除：10 个 `castl::function<void(...)>` 回调和返回 `MonitorInfo` 的 `GetMonitor`。

生成器已经有两张投影矩阵、统一句柄表、错误通道、布局清单、C# 表面对象和 `IBindRow13` 回调拒绝夹具。窗口系统的 GLFW 回调在引擎主线程进入 `WindowSystem_Impl.cpp`，C# 的 `Host.Tick` 也在主线程执行。由此可以复用现有绑定设施，但不能再把回调写成固定函数指针，也不能把 `MonitorInfo` 当作只有一层标量字段的结构体。

## Goals / Non-Goals

**Goals:**

- 10 个 `Set*Callback` 与 `GetMonitor` 全部经同一次生成进入 C ABI 和 C# 表面，不再有这 11 条排除。
- 回调能收到真实参数与正确的窗口对象；替换、置空、释放和异常行为都有明确生命周期。
- `MonitorInfo` 的两个矩形与 DPI 逐字段穿过边界，嵌套布局可校验。
- 每个新增行为都有确定性测试和能构造红态的判据。

**Non-Goals:**

- 不做渲染后端 binding，不做带返回值的回调，不做任意线程的托管调度。
- 不支持含字符串、容器、指针或自定义所有权成员的嵌套记录。
- 不改 C++ 接口签名、不改 GLFW 事件实现、不放宽函数表版本检查。

## Decisions

### D1 回调注册号只在内部层，公开表面保持 `void Set*Callback`

生成器把每个回调 setter 投影为“安装回调并返回内部注册号”的 C ABI 入口，另为每个接口生成一个通用的注销伴生入口。注册号标识接口、方法和本次注册，注销时只清理仍与该注册号匹配的那一项；旧注册号不能误删后来替换的新回调。

C ABI 的回调形状是“真实签名的原生函数指针 + `void* user`”。`user` 只作为不透明令牌传给生成的托管桥，不允许原生代码解引用。注册号与既有资源句柄使用不同的命名和释放入口，禁止拿 `ReleaseHandle` 注销回调。

公开 C# 表面仍是 `void SetWindowFocusCallback(...)` 等同名方法，参数还原为类型匹配的 `Action<...>`，允许 `null`。注册号、函数指针、用户令牌和注销伴生全部留在 `internal` 层。

被否决：让公开 setter 返回注册对象。那会改变 C++ 声明的返回语义，也把生命周期管理推给每个脚本调用点。

### D2 替换、置空与释放都必须同时清理原生注册和托管保活

生成的托管注册表用 `GCHandle` 保活委托，原生注册表保存函数指针、用户令牌、当前注册号与活动状态。

- **替换**：先安装新回调并取得新注册号，再注销旧注册号。新安装失败时旧回调保持有效。
- **置空**：向原生实现传入空 `castl::function`，然后注销旧注册号并释放对应 `GCHandle`。
- **释放窗口系统表面对象**：逐项注销该对象仍持有的回调，再执行既有句柄释放；`Host` 重绑时先 `Dispose` 旧表面对象。另新增托管 `Host.Shutdown` 入口，`CSharpHost/private/CSharpHost.cpp` 在调用 `hostfxr_close` 前加载并调用它，关闭路径不得只把旧引用置空。
- **清理后**：后续原生事件不得再触发旧委托，注册表中不得保留对应保活项。

测试不能依赖垃圾回收时机猜“可能已经释放”，而要直接检查生成注册表的存活项，并触发事件证明旧委托不再执行。

### D3 回调里的 `IWindow*` 是回调期间有效的借用对象

原生桥把 `IWindow*` 映射为既有 `IWindow` 表面的借用对象，所有权仍属引擎。托管桥在进入用户委托前建立借用包装，返回后撤销包装并释放本次借用状态。

委托可以保存这个 `IWindow` 引用，但回调返回后再次调用其任何方法都必须得到明确的失效异常，不能解引用悬空原生指针。回调内读取窗口身份、尺寸或名称时，必须走真正的 `IWindow` 函数表，不能用空壳对象只转发数值参数。

被否决：只把窗口指针改成 `IntPtr` 暴露给脚本。这能绕过生命周期设计，却破坏现有“托管表面镜像 C++ 声明”的要求。

### D4 只允许主线程回调，重入注册变更必须显式失败

本 change 不引入跨线程队列。回调桥记录注册线程；若原生回调来自其他线程，不得直接进入托管委托，必须记录明确错误并停止该次调用。

回调执行期间修改同一个回调注册可能销毁正在执行的 `castl::function`。生成的桥必须用活动标记阻止这种重入变更，并返回可诊断错误；不得静默接受、清空或替换当前正在执行的回调。不同回调之间的普通调用不受这条限制。

被否决：在本 change 里加通用锁或后台队列。当前窗口系统与宿主都按主线程工作，凭空引入线程模型会扩大所有权的范围，不能解决真正的跨线程调度。

### D5 托管回调异常就地截获，在下一次主线程调用上报

托管桥调用用户委托时必须捕获全部托管异常，禁止异常穿过原生回调边界。异常文本保存在对应窗口系统的回调错误槽中；下一次 `UpdateSystem` 或回调注册调用完成后，公开表面抛出 `IWindowSystemException`，并保留可读错误信息。原生实现和进程不得因用户委托抛异常而崩溃。

回调专用错误标识必须在 `Tools/CodeGen/CodeGenMain.cpp` 的生成期错误表中新增命名项，并同步 `Tools/CodeGen/check_bindings.py` 的 `ERROR_CODE_TABLE` 与 `Tools/CodeGen/README.md` 的错误码说明。生成器和判据必须使用同一套名称与数值，测试断言异常类型、错误标识和原始异常文本，不在设计或测试中手抄一个新数值。

### D6 嵌套镜像只递归处理纯标量记录，并收紧非法成员拒绝

镜像发现从“每个直接成员必须是标量”扩为“成员可以是标量或另一个纯标量记录”。`FloatRect` 实际是 `cacore::Rect<float>`，带有 defaulted `operator<=>`；生成器必须允许这种不改变数据布局的默认比较运算符，其他自定义方法仍按非数据类型拒绝。遇到字符串、容器、指针、智能指针或自定义所有权成员时，必须修改当前“只跳过布局清单、仍以退出码 0 出产物”的行为，改为非零退出并点名完整成员路径。

`MonitorInfo` 因而展开为两个 `FloatRect` 与一个 DPI 标量。C ABI 使用两侧同源的布局镜像，C# 公开表面使用 `FloatRect` 与 `MonitorInfo` 记录类型，保留原始字段名与字段顺序。布局清单同时记录嵌套类型和字段偏移，不能只把全部字节当成匿名数组。

`GetMonitor` 的 thunk 先按字段把原生嵌套记录搬到镜像，再由 C# 按相同字段还原。除现有 C++ `static_assert` 外，还要生成可由托管启动过程读取的布局清单入口；`Host.Boot` 必须逐项比较两侧清单后再允许绑定，缺字段或偏移不符时拒绝启动并点名字段路径。所有大小与偏移都来自真实 `sizeof` / `offsetof`，不得假设嵌套记录紧凑，也不得把编译期断言冒充成托管启动自检。

### D7 夹具从拒绝用例改成正向行为用例，审计只移除已实现的备注

`IBindRow13::SetCallback` 改为正向回调夹具，覆盖参数顺序、替换、置空、注销和异常。嵌套记录夹具覆盖非零字段、布局偏移和按值返回。矩阵总行数不因这次实现自动增加；现有回调行从“拒绝”改成“生成并调用”，相关期望文本和 README 同步更新。

唯一审计表仍由 `check_bindable_audit.py` 定位。`GetMonitor` 行只有一处“本轮未实现”备注可删；10 个回调行没有这句备注，必须改写它们的“投影形状”和备注列：接受内部注册号、注销伴生与回调期间借用 `IWindow`，删除“首参改成窗口 id”和“回调签名里不许出现 `IWindow*`”的旧结论。所有行保持“可绑”，其他未实现形状不得顺带解封。`WindowSystem.h` 只移除这 11 条排除，注释中的方法总数与排除数同步改写。

### D8 测试分两层，避免依赖人工输入和真实显示器数值

- **CoreTests**：用 `IBindRow13` 和嵌套记录夹具验证生成签名、原生函数指针调用、注册号注销、重入保护与布局。CoreTests 不直接声称验证了托管委托或 `GCHandle`。每个关键缺陷都要先做红态，再恢复验证。
- **GPUBackendTester**：扩展 `FakeWindowSystem.h`，让它保存 10 类回调、提供公开确定性触发方法，并返回固定非零 `MonitorInfo`；不得让 `Main.cpp` 包含 `WindowSystem/private/WindowSystem_Impl.h` 或访问私有 GLFW 路径。新增 `TestCSharpWindowCallbacks` 覆盖 C# 委托参数、保活项清理、借用对象失效、异常与主线程限制；保留 `TestCSharpWindow` 的真实窗口系统 `GetMonitor` 两侧同刻对拍。固定非零夹具负责防止“真实环境全零也能通过”的假绿，文档中的 CoreTests 与 tester 数量都按实际清单核对。

真实窗口回调的验收必须检查窗口身份与标量参数，不能只数调用次数。显示器验收必须比较两个矩形和 DPI，不能只断言方法存在。

### D9 无效显示器编号在绑定层显式失败

现有 `WindowSystem::GetMonitor` 对越界编号使用 `castl::clamp`，会返回另一个真实显示器；唯一审计表却要求无效编号报错。生成的 `GetMonitor` thunk 在调用原生实现前 MUST 先用 `GetMonitorCount` 校验编号，负数或不小于当前数量的编号走统一错误通道，C# 表面抛出 `IWindowSystemException`。有效编号才允许搬运嵌套记录，不能把 clamp 后的合法结果当成无效编号的答案。

错误时返回的镜像零值只属于失败通路，公开 C# 不得把它当成成功结果。空显示器列表同样按无效编号处理，不新增静默降级。

## Risks / Trade-offs

- **替换回调时的旧注册误删新注册** → 注册号同时标识方法与代次，注销只作用于匹配项；用替换后连续触发事件的测试证明。
- **回调保存窗口引用导致悬垂** → 回调返回即撤销借用包装，保存后调用必须失败；单独写保存后调用的测试。
- **用户异常跨边界导致进程终止** → 托管桥全捕获，下一次主线程调用上报；测试抛异常后继续执行后续用例。
- **嵌套布局在不同配置下含填充** → 使用真实编译期的 `sizeof` / `offsetof` 清单，不用手算字段偏移。
- **真实显示器数据随环境变化** → 真实接口只做两侧同刻对拍，另用固定非零夹具证明字段没有丢失或错序。

## Migration Plan

1. 先把回调与嵌套记录夹具改成会失败的正向测试，保存当前拒绝/缺字段的红态证据。
2. 先实现原生回调投影，解除 1.2 的生成器拒绝；再实现嵌套镜像与 `GetMonitor`，然后完成托管回调生命周期。每一步都先跑对应测试，不能让“回调仍被拒”与“全量构建必须过”相邻冲突。
3. 移除 `IWindowSystem` 的 11 条排除，更新 `CSharpHost.cpp` 的函数表断言与关闭入口，接入新的回调测试和真实窗口测试，更新审计、README 和测试文档。
4. 最后跑完整构建、CoreTests、相关窗口测试与 `openspec validate --all`。任何一步失败都保留当前步骤，不回退已经通过的前置判据。

## Open Questions

本设计没有留给实现阶段自由决定的生命周期问题。若实际代码证明现有句柄表无法表达回调借用对象，必须先修订本设计与规范，不能悄悄改成公开裸指针。
