# 1.3 红态：越界读被拒绝并报告（改前）

时间: 2026-11-16 23:56:57（Asia/Hong_Kong）
代码状态: 接口层 `Read` 已返回 bool，但实现保留旧缺陷——越界分支是"静默接受"（`return true`），
          对应改前的 `return;`（调用方永远看不出被拒绝）。

## 判据（tasks.md 1.3 原文）
「真临时文件（16 字节）建批，顺序读完 16 字节后再 `Read(1, &b)`，返回值必须为 `false`——改前红
（返回 void 无从判），改后绿。」

## 判据的落地形态（比原文更严，覆盖"位置不推进"）
1. `Read(8)` 必须被接受；
2. `Read(16)`（当前位置 8 + 16 > 文件尺寸 16）必须返回 **false**；
3. 拒绝之后 `Read(8)` 必须**仍被接受**——这是"批内位置没被推进"的可观测判据；
4. `SubmitAndWait()` 之后头 8 字节 == 0..7、尾 8 字节 == 8..15（说明前两条读落在正确位置）。

## 命令（真实执行）
```
out\build\x64-debug\bin\GPUBackendTester.exe --backend vulkan --test TestIOErrorChannel --headless 1 --report test_output\io_error_channel_red_vulkan.json
```
（d3d12 同一条，读数逐字相同）

## 真实输出（test_output\TestIOErrorChannel.log 第 4 行，原文）
```
[I/O 错误通道 1.3] 越界读返回 false、批内位置不推进、已接受的读仍读得到正确字节：判据不成立 ⇒ 首读 8 字节被接受=1、越界读 16 字节被拒=0、拒绝后再读 8 字节仍被接受（位置未推进）=1、头 8 字节内容符合=1、尾 8 字节内容符合=1
```

## 判据为什么红
- 唯一为 0 的就是"越界读 16 字节被拒"：旧实现把越界读**静默接受**（改前 `return;`、红态实现
  `return true;`），调用方拿不到任何信号。
- 位置没推进（第 3 项为 1）与前后两段内容正确（第 4/5 项为 1）说明这条判据只抓"越界是否被报告"
  这一件事，不是被别的行为顺带带红。
