# 4.2 可行性结论：原生渲染进网页（D3D12 → WebView2 canvas）

> 结论一句话：**D3D12 共享纹理的"建/共享/第二消费者读回"在本机可行；但"共享纹理零拷贝进网页 canvas"在本批的
> WebView2 137→157 运行时上不可行（网页侧没有导入 DXGI 共享句柄的 API）**。因此本批实现走
> **CPU 读回**（运行读数 `path=cpu-readback`），与判定一致；零拷贝留后续，**Vulkan↔WebGPU 本批排除、仍未知**。

## 一、研究冻结快照（详见 `evidence/1.1-互操作研究.md`）

| 项 | 值 |
|---|---|
| 研究时间 | 2026-11-24T14:16:04+08:00 |
| WebView2 运行时版本 | **157.0.4341.60**（`CoreWebView2Environment.BrowserVersionString`；本文件下方的运行读数同一来源） |
| WebView2 托管包 | `Microsoft.Web.WebView2` 1.0.4370.26 |
| WebGPU 规范快照 | `gpuweb/gpuweb` `spec/index.bs` @ `d178d9145ab1652ec933e71a8c30e8f6470f00a3` |
| WebCodecs 规范快照 | `w3c/webcodecs` `index.src.html` @ `e3e611cc4f68610f8589ad9f70a2ef5f44f74a6b` |
| 规范零命中 | `DXGI` / `sharedHandle` / `sharedTexture` / `CreateSharedHandle` / `externalMemory` / `importSharedTexture` 在 WebGPU 规范各 **0 行**；WebCodecs 的 `DXGI` / `sharedHandle` / `CreateSharedHandle` 各 **0 行** |

关键逐字事实：
- WebGPU `GPUExternalTextureDescriptor.source` 的类型是 `(HTMLVideoElement or VideoFrame)` —— **不收裸共享句柄**。
- WebCodecs `VideoFrame` 的构造来源只有 `CanvasImageSource`（网页对象）或 `AllowSharedBufferSource`（CPU 字节）——
  **没有"平台共享句柄"重载**，所以"共享句柄 → VideoFrame"的桥在网页侧不存在。
- [GPUWeb #5167](https://github.com/gpuweb/gpuweb/issues/5167)（`importExternalTexture: Support importing
  platform-shared GPU textures (DXGI / IOSurface / dma-buf)`）状态 **closed / not_planned**；维护者答复：
  "this is on the native side of a browser engine … entirely outside the purview of the Web platform"。
- Electron 有一份引擎侧实现（[electron/electron#46811](https://github.com/electron/electron/pull/46811)，
  已关闭并拆成多个依赖 PR），但那是**浏览器引擎内部**改动，WebView2 嵌用方没有对应开关/接口。

## 二、实际 path 的运行读数（本批实现 = CPU 读回）

绿跑（D3D12 独立进程，`evidence/3.1-绿跑.json` = `status=pass, exit_code=0`）的读数行（`evidence/3.1-绿跑读数.txt`）：

```text
path=cpu-readback spikePath=cpu-readback spikeFrames=3 spikeMatched=3 spikeError=-
webview2Version=157.0.4341.60 spikePage=1 clients=2
```

三帧同帧对账标记（网页 canvas 回传 vs 原生读回，逐帧哈希不同）：

```text
[渲染原型 读数] spikeMatch frame=1 hash=7df2b6c5 canvas=256x256 path=cpu-readback webgpu=1
[渲染原型 读数] spikeMatch frame=2 hash=2dfb06c5 canvas=256x256 path=cpu-readback webgpu=1
[渲染原型 读数] spikeMatch frame=3 hash=90355dc5 canvas=256x256 path=cpu-readback webgpu=1
```

即：**网页 canvas 真的显示了原生 D3D12 渲染的像素**，但走的是
`共享纹理 → C++ Readback → C++→C#（EditorService WebSocket）→ 网页 putImageData` 这条 CPU 路径，每帧 262144 字节。

## 三、可行性判定（与 path 一致）

| 问题 | 判定 | 证据 |
|---|---|---|
| D3D12 共享堆纹理 + 共享句柄可建？ | **可行（本机实测）** | 原生侧正控通过：句柄非空 + `OpenSharedHandle` 第二消费者读回字节与本设备逐字节一致 + 多点/帧序号位匹配（`evidence/2.1-原生侧正控.txt`） |
| 共享纹理**零拷贝**进 WebView2 网页 canvas？ | **不可行（本批环境）** | 缺失 API：标准 WebGPU 无"导入 DXGI 共享句柄"入口（规范零命中）；`importExternalTexture` 只收 `HTMLVideoElement`/`VideoFrame`；`VideoFrame` 构造不收平台句柄；GPUWeb #5167 closed/not_planned；本机运行时 WebView2 **157.0.4341.60** 同样没有这类入口；Electron 的引擎内部实现不适用于 WebView2 嵌用方 |
| 本批实际走哪条路？ | **CPU 读回（path=cpu-readback）** | 见上运行读数；零拷贝是 Non-goal（proposal / design D3） |

**一致性强校验**：判定为"零拷贝不可行" ↔ 运行读数 `path=cpu-readback` —— 二者一致。若反过来声称"零拷贝可行"，
判据要求给出"该帧没有 Readback"的证据，而本批每帧都经过 C++ Readback（`spike-frame` 的 `pixels` 就是读回字节），
所以"可行"会与本批读数直接矛盾，必判红。

## 四、退路建议（喂后续 `editor-free-dock`）

1. **路线 B：透明叠层**（不需纹理互操作）：WebView2 透明背景叠在原生渲染之上，网页只报告 scene 面板矩形，原生按矩形
   设视口。代价：矩形同步、z-order/透明合成、拖动时的跟随；优点是复用现有原生渲染、无每帧 CPU 拷贝。
2. **CPU-GPU 桥（本批已证的最小版）**：CPU 读回 + 共享内存/字节通道。代价：每帧一次 GPU→CPU 拷贝
   （256×256×4 = 262144 字节/帧），高分辨率/高帧率不可行，只适合低频预览或测试正控。
3. **等引擎侧能力**：WebView2/Chromium 若提供"共享句柄 → `VideoFrame`/纹理"入口（GPUWeb #5167 那类提案被引擎实现），
   再回来做零拷贝；这不受本项目控制。
