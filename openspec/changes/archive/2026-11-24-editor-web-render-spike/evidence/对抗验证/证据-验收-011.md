# 证据：主张-验收-011

- 面：验收可失败性-③（2.1 原生离屏读回与 3.1 网页 canvas 是否两套独立判据）
- 严重度：misleading
- 主张：2.1 的「共享句柄产出可核」没有定义——松读法下它恒真（句柄非空是 API 默认行为），严读法下它需要一个工件没给的第二个消费者。

## 一句话结论

「可核」是这份工件里最常出现的两个坑之一（另一个是「结论可核」）。它把「判什么」留给了执行者，于是判据的松紧取决于谁去执行。

## 工件逐字引文（命令 + 真实输出）

命令 1（2.1 的验收原文）：

```text
Select-String -Path openspec\changes\editor-web-render-spike\tasks.md -Pattern "共享句柄产出可核" | ForEach-Object { "$($_.LineNumber): $($_.Line.Trim())" }
```

输出（tasks.md:14 逐字）：

```text
14: - [ ] 2.1 D3D12 离屏渲染到 DXGI 共享纹理：复用 D3D12RenderBackend 渲染确定性红三角（沿用现有探针像素惯例），渲染目标带共享句柄（D3D11_RESOURCE_MISC_SHARED / D3D12 shared handle）；画面尺寸/中心像素期望写死。验收：构建过；共享句柄产出可核；离屏读回中心 == (255,0,0,255)（原生侧正控）。
```

```text
cd openspec\changes\editor-web-render-spike; foreach($k in @('OpenSharedHandle','第二个消费者','另一设备','打开句柄','句柄非空')){ $n=(Select-String -Path *.md,specs\*\*.md -Pattern ([regex]::Escape($k)) -AllMatches | Measure-Object).Count; "$k = $n" }
```


命令 3（仓库里目前没有任何共享句柄代码，可核的对象本身还不存在）：

```text
Get-ChildItem -Recurse -File -Path D3D12RenderBackend -Include *.cpp,*.h | Select-String -Pattern "MISC_SHARED|CreateSharedHandle|OpenSharedHandle" | Measure-Object | Select-Object -ExpandProperty Count
```

```text
0
```

## 为什么这条判据现在不能失败

1. 「可核」没有判据。执行者甲的读法：句柄非 0、日志里能看到一个数字 → 合格。执行者乙的读法：必须能跨设备打开并读出像素 → 不合格。同一条验收，两种结论。
2. 松读法几乎没有信息量：只要创建资源时带上 `D3D11_RESOURCE_MISC_SHARED`，`CreateSharedHandle` 成功返回非空句柄就是 API 的既定行为；「拿到了句柄」与「共享可用」之间隔着「第二个消费者能不能打开、读到的是不是同一幅图」。
3. 严读法所需的第二个消费者在工件里 0 处提及（命令 2），而仓库里共享句柄代码也是 0 处（命令 3）——所以这条判据的严读法根本没有可执行的前提，只能退化成松读法。
4. 它与主张-验收-008 是同一处缺陷的两面：008 管「读回有没有绑在这张纹理上」，本条管「可核」这个词没有判据。修一处（三层判据）可同时解决。

## 加严建议（可直接落进工件）

1. 拆成三个具名判据，各自写死读数行字段与失败码：
   - ① 句柄非空且资源描述含 `SHARED` → `E_WEBSPIKE_NOSHARED`；
   - ② 第二个消费者 `OpenSharedHandle` 成功 → `E_WEBSPIKE_OPENSHARED`；
   - ③ 第二个消费者从同一资源读回中心 == `(255,0,0,255)` → `E_WEBSPIKE_SHARED_PIXEL`。
2. 红态：去掉 `MISC_SHARED` 后 ① 必须红，贴 `result.json` 的 `status`/`error` 原文。
3. 全工件搜一遍「可核」，每一处都换成「判什么值、什么失败码、红态怎么造」；本文件已单独主张的还有 4.2 的「结论可核」（主张-验收-012）。
