## 4. 影响

- 兜底的两端都在工件之外：读像素的一侧是 C++（C# 绑定面明确没有 Readback），持有 WebView2 与 host object 的一侧是 C#（全仓 WebView2 只在托管侧）。design 第 61 行把「host object vs WebSocket」写成 C# 侧的选型问题，但**两种选择都接不到 C++ tester 读回的字节**：host object 是 C# 对象，WebSocket 需要一个监听方，而 C++ tester 与 C# 之间没有任何现成通道。工件没有一条任务设计这个桥、没有端口/目录规则、没有失败判据。
- 即使共享纹理做出来，路径③也不是「保证可行」：它依赖一个未设计的跨语言字节通道。若实现者顺手加一条本机套接字监听，就落进主张-影响-011 的端口问题；若用临时文件，就落进主张-影响-010 的目录/清理问题。
- 若实现者为了省事把 Readback 加进可绑面，绑定产物必然变化，与 tasks 4.1 的「逐字节不变」冲突（主张-影响-008）。

## 5. 建议的能失败判据

1. tasks 2.3 点名字节通道：实现文件、监听方、临时目录或端口、清理责任，三选一写死。
2. 兜底要么改用普通纹理 + C++ 侧 `Readback`（不依赖共享纹理），要么在风险表承认两条路径同阻塞。
3. 验收：通道每次传输记录 `bytes=<n>`（应等于宽×高×4）与一条失败路径（通道断开时以点名错误码退出），失败路径必须能构造并落 evidence。
