# 证据：主张-验收-001

- 面：验收可失败性-①（3.1 网页 canvas 中心像素断言）
- 严重度：Blocking
- 主张：3.1 的断言读的是 canvas 位图，不是 WebView2 合成后看得见的画面；「数据到了但看不见」不在红态清单里，断言照旧绿。

## 一句话结论

本 spike 的核心命题是「原生渲染能显示进网页」。3.1 只证明「canvas 位图里有红像素」，没有证明「用户看得见这块红」。后者恰恰是「显示」二字的分量所在，而工件的红态清单里没有任何一条能把它变红。

## 为什么这条判据现在不能失败

1. 断言的两个动作都落在同一块 canvas 位图上：`putImageData` 把原生送来的红字节写进位图，`getImageData` 从同一块位图读出来。位图内容与「这块 canvas 有没有被合成到屏幕上」是两件事——按 Web 平台的行为，`display:none`、`opacity:0`、父容器未挂载都不清空位图（这是推理，本角色禁跑程序，**未在本机实测**）。
2. 因此「原生像素到了、但网页上看不见」这个反例下，断言很可能仍然绿。要证明它绿还是红，唯一办法是造这条红态跑一次——而工件的红态清单里没有它（命令 4 的 8 个关键字全为 0 命中）。
3. design.md:39 用「**或**」把 getImageData 断言与抓窗核对并列，实现方可以只做前者就宣称 3.1 过；而抓窗那一条（3.2）是人的核对，不进自动化判据。
4. 3.2 的抓窗证据本身也不判内容：仓库里的抓窗先例只检查 `stream.Length != 0`（命令 5），画面是不是红三角由主循环看图判断——这一条 3.2 已经写了，但它救不了 3.1。

## 加严建议（可直接落进工件）

1. 3.1 红态清单加「显示类」反例，用自检开关注入（开关形态照既有惯例：`Main.cpp:2396` 的 `CASCADED_CSHARP_CONSTCOLOR_SELFTEST` 是进程环境变量 + 未知值判 `E_CONSTCOLOR_MODE` 失败）。三种注入任选其一即可，建议全做：
   - `CASCADED_WEBSPIKE_SELFTEST=hide-canvas` → 页面脚本把 scene 面板设 `display:none`；
   - `CASCADED_WEBSPIKE_SELFTEST=zero-size` → canvas 宽高设 0；
   - `CASCADED_WEBSPIKE_SELFTEST=detach-panel` → 面板不挂到文档树。
   每种都必须以写死的失败码（建议 `E_WEBCANVAS_NOT_VISIBLE`）退出 1，evidence 存 result.json 的 `status`/`error` 原文，格式照归档先例 `2026-11-24-editor-asset-browser/evidence/4.1-首次运行红态.txt` 的「退出码 1 / status=fail / error=…」逐字贴法。
2. 回传行补几何与可见性读数：`canvas.width`、`canvas.height`、`getBoundingClientRect()` 的宽高、`document.visibilityState`。C++ 断言前两项 > 0、矩形宽高 > 0、状态为 `visible`，缺字段判 `E_WEBCANVAS_GEOMETRY`。这样「canvas 尺寸为 0」不必靠位图判，直接读数就红。
3. design.md:39 与 spec.md:5 的「或」改成「且」：getImageData 回传断言（自动化）与 CapturePreviewAsync 抓窗 + read_image 核对（3.2）两条都要过，任一条不过即判不通过。
