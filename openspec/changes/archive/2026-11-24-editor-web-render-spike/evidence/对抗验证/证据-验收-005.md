- 面：验收可失败性-②（1.1 互操作研究「不可行有具体阻塞证据」）
- 严重度：Blocking
- 主张：1.1 的「不可行」只要求写「缺失 API 名 / 版本」；这是无边界的否定命题，任何一句话都满足验收，且设计里已经先写好了这句否定结论。

## 一句话结论

## 为什么这条判据现在不能失败

1. 判据的全部内容是「evidence 里出现缺失 API 名 / 版本 / 文档 URL」。这三样都可以凭记忆写，且写完之后判据就满足了。
2. 「缺失」是全局否定：要判它假，得证明「某个 API 在某处存在」。没有冻结快照与检索词，读者无法知道核实的范围是哪个版本、哪份规范——范围不明，否定命题既不能证实也不能证伪。
3. design.md:29 已经替 1.1 把结论写好（「标准 WebGPU web API 无直接导入 DXGI 共享句柄的入口」），且这句话在 design 里没有任何引用。1.1 只要补一条 URL 就能交差，核实方向被结论锁死：任务从「查」变成了「找支持这句话的材料」。
4. 仓库的既有要求是「对抗者必须复查文档引用真实性」，那只管得了链接真不真，管不了「没查到的部分」。1.1 需要在工件层面补上这一层，否则 URL 只是装饰。

## 加严建议（可直接落进工件）

1. 「不可行」的验收改成三段必填、缺一即不合格：
   - 冻结快照：URL + 抓取日期 + HTTP 状态码 + 引用段落逐字摘录；
   - 检索词与零命中输出：在那份快照里检索 `DXGI shared handle`、`importSharedTexture`、`external texture import` 等词，贴出零命中或「全文未提及」的原文片段（命令 + 输出，不是结论）；
   - 版本：WebView2 运行时版本号与其获取命令（见主张-验收-006）。
2. 在 evidence 里显式回答一句：「design.md:29 的否定结论是本次核实的，还是本次沿用了未核实的旧判断」。沿用的必须标「待核实」，不许当结论。
3. 三个候选各写「结论 + 依据」，「complex 所以不试」不算结论（见主张-验收-007）。
