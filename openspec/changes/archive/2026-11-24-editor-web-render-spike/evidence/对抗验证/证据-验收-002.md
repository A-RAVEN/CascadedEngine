# 证据：主张-验收-002

- 面：验收可失败性-①（3.1 网页 canvas 中心像素断言）
- 严重度：Blocking
- 主张：「互操作断链 MUST 红」在工件里没有判红机制：没有超时、没有失败码、没有缺行即失败，「通道可核」也没有判据。断链时测试可以挂住或跳过断言。

## 一句话结论

3.1 写了两条 MUST 红的反例，但只给了「空白/黑」的期望像素，没给「拿不到像素」时的行为。断链恰恰就是拿不到像素，于是这条 MUST 在本该最需要它的时候没有出口。

## 为什么这条判据现在不能失败

1. 「断链」分两种走向。第一种：原生→网页的链路断了，但网页→原生的回传通道还活着，页面回传一个「还没收到帧」的标记。第二种：回传通道本身断了，C++ 什么也收不到。工件对第二种没有任何行为规定——既没说超时多久算红，也没说收不到就失败。
2. 没有超时的等待不会变红，只会挂住；而在测试框架里「挂住」既不是 pass 也不是 fail，通常被当成环境问题重跑，红态就此消失。归档批次的教训正好是这一类：`2026-11-24-editor-asset-browser/evidence/4.1-首次运行红态.txt` 里红态之所以可核，是因为有 `result.json` 的 `status=fail` 与 `error` 原文。
3. 「读不到就跳过断言」是这类测试最常见的假绿路径，而工件没有任何一条禁止它。仓库里反过来的惯例是「读数行没出现就 fail」（命令 4 的 `E_TRIANGLE_READINGS`）。
4. 1.2 的验收「像素回传通道可核」同理：没有命令、没有期望值、没有红态，无法判合格与否。它还是 3.1 的前置，前置不可核，3.1 的绿就悬空。

## 加严建议（可直接落进工件）

1. 回传行带帧序号：原生侧每帧写入 `frameId`，回传行回带 `frameId` 与网页侧收到时的 `frameId`；C++ 断言连续递增且最后一条 ≥ 2。这样「只来了第一帧就断」也能红。
2. 超时用写死值并给来源：取 `Main.cpp:4362` 的 `int timeoutMs = 6000`（既有探针惯例），超时判 `E_WEBCANVAS_TIMEOUT`、退出码 1；若要做成可配，写进配置项表并给默认值。
3. 缺回传行立即失败：写 `E_WEBCANVAS_NOLINE`，措辞照 `E_TRIANGLE_READINGS` 的「……没有出现在日志里」。
4. 1.2 的「像素回传通道可核」改成：页面回传固定四元组 `(1,2,3,4)`（与红色无关的值，避免和 3.1 的期望撞车），C++ 逐字节断言相等；红态 = 注释掉页面的发送分支后该断言必须红。这样通道本身先独立证一次，再谈像素。
