# 证据：主张-验收-006

- 面：验收可失败性-②（1.1 互操作研究「不可行有具体阻塞证据」）
- 严重度：misleading
- 主张：要求写 WebView2 版本，却没给获取命令、没要求版本与判定绑定——版本号是装饰，写什么都一样。

## 一句话结论

版本之所以要写，是因为「该版本是否暴露某能力」是本 spike 唯一意义上的自变量。1.1 只要求「含版本」，不要求「用哪条命令取的」和「这个版本上怎么确认」，于是版本号可随手填，判定也就与版本无关。

## 为什么这条判据现在不能失败

1. 判据是「evidence 里出现 WebView2 版本」。任何形如 `x.y.z.w` 的字符串都能满足；把版本写成 `131.0.2903.86` 还是 `999.0.0.0`，验收结果一样。
2. 判定与版本之间没有格式约束。工件允许出现「版本 A：不可行」这样的句子而不说明「在 A 上用什么方式确认了不可行」——版本只是句子的前缀。
3. 仓库里没有既有的版本读取路径（命令 3、4），所以执行者要么临时找命令、要么凭记忆写版本；两种情况都不留下可核痕迹。
4. design.md:50 担心「版本不足」，却没把版本钉死，于是这个风险只能靠事后读报告的人自己判断——而报告里的版本号本身不可核。

## 加严建议（可直接落进工件）

1. 钉一条命令，二选一写死：
   - `CoreWebView2Environment.GetAvailableCoreWebView2BrowserVersionString()` 的返回值打印到日志；
   - 或注册表 `HKLM\SOFTWARE\WOW6432Node\Microsoft\EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}` 的 `pv` 值。
   evidence 里贴命令原文与输出，不许只贴版本号。
2. 每个候选的判定写成固定格式：「在版本 <X> 上：<可行|有具体阻塞|未核实>，核实方式 = <命令/文档段落>」。X 必须与第 1 条的打卡行逐字一致。
3. 1.1 与 4.2 两处出现的版本号必须逐字相同；不同即判不合格（防止研究时一个版本、结论时另一个版本）。
