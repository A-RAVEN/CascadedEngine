## 为什么这条判据现在不能失败

1. 评判红态的人只能看到一份 txt。txt 里写「已构造红态：断言失败」，与真跑一次失败，在纸面上完全一样——因为工件没有要求贴出退出码、失败码、result.json 原文，也没有要求给复跑命令。
2. 红态不能复跑这一点更关键：工件里没有自检开关（命令 3 全 0 命中），要造红态只能改代码。改完代码跑一次、把日志截进 txt、再改回去——第三方无法复现，也无法确认那次失败是「判据在缺陷存在时变红」还是「代码本来就没编过」。
3. 这与文件自己写的口径（命令 1）直接冲突：开头要求命令与期望读数，3.1 的红态两项都缺。
4. 归档批次的红态是可核的：有开关、有退出码、有 status、有 error 原文（命令 4、5）。本工件退回到「一份自由格式的 txt」。

## 加严建议（可直接落进工件）

1. 3.1 红态改成三件套，逐项写死：
   - 注入开关：`CASCADED_WEBSPIKE_SELFTEST=<模式>`，未知模式判失败（照 `E_CONSTCOLOR_MODE` 的「未知的自检模式」写法）；
   - 复跑命令：完整命令行（含 `--backend d3d12` 与 `--test TestWebRenderSpike`），写进 tasks 条目本身；
   - 期望读数：退出码 1 + `status=fail` + 失败码 + `error` 原文。
2. evidence 文件名由通配 `3.1-*.txt` 改成具名（例如 `3.1-红态-断链.txt`、`3.1-红态-隐藏画布.txt`），一条红态一份；每份里逐字贴 `result.json` 的 `status` 与 `error`。
3. 红态必须能在不改代码的前提下复跑：若某条红态只能靠改代码造出来，就在工件里写明「此条不可复跑」并降级为辅助证据，不算通过 3.1。
