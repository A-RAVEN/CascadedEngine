# 证据：主张-验收-007

- 面：验收可失败性-②（1.1 互操作研究「不可行有具体阻塞证据」）
- 严重度：misleading
- 主张：design 预先给候选②写了「复杂，评估不强行」，这不是判定，但足以让 1.1 交差；三态不齐也没有后果。

## 一句话结论

1.1 的三条候选里，有一条在 design 里已经被允许「不试」。于是「每条候选都要有可行/不可行判定」这句话对候选②事实上不成立：写「复杂，未尝试」既不违反 design，也不触发任何失败判据。

输出（design.md:31 逐字）：

```text
cd openspec\changes\editor-web-render-spike; foreach($k in @('未核实','未尝试','三态')){ $n=(Select-String -Path *.md,specs\*\*.md -Pattern ([regex]::Escape($k)) -AllMatches | Measure-Object).Count; "$k = $n" }
```

命令 4（那唯一一处「未核实」的位置与原文）：

```text

```

输出（spec.md:23 逐字）：

```text
spec.md:23: - **WHEN** 零拷贝互操作不可行（或尚未核实）
```

它只是兜底正控的触发条件，不是「每条候选必须标注三态」的要求；1.1 的验收仍然只写「可行/不可行判定」。

## 为什么这条判据现在不能失败

1. 任务要求「每条候选给可行/不可行判定」，design 却对候选②写明「不强行」。当两者冲突时，执行者引用 design 一行就够，验收方没有判据可以说它不合格——因为「复杂度不做」没有被定义为失败。
2. 「未核实」是第三种真实存在的状态（既没证实可行，也没找到阻塞）。工件只在 spec.md:23 的兜底触发条件里提过一次「（或尚未核实）」，没有把它定为 1.1 逐候选的合法状态，也没有规定它的后果（命令 3、4）。于是执行者只能把它伪装成「不可行」，而「不可行」的验收又只要求一句缺失 API 名（见主张-验收-005）。
3. 这一条还直接影响 4.2：如果候选②没核，那么「零拷贝是否可行」的结论只覆盖候选①，4.2 却可以写成全局判定（见主张-验收-012）。

## 加严建议（可直接落进工件）

1. 1.1 每条候选落三态之一，措辞写死：
   - 实测可行 —— 附运行读数（命令 + 输出）；
   - 有具体阻塞 —— 附冻结快照 + 检索词与零命中输出 + 版本（见主张-验收-005）；
   - 未核实 —— 必须写明未核实的原因，以及它使 4.2 的哪一条判定悬空。
2. 把 design.md:31 的「复杂，spike 评估不强行」改成：「预算内不实现，但仍须给出 ① 或 ②，否则只能标 ③ 并在 4.2 列为未决」。
3. 1.1 的验收补一句：出现第 ③ 态时，4.2 不得据此判定该路径不可行；4.2 的结论里必须逐条列出「本次核实覆盖到哪条、哪条未核实」。
