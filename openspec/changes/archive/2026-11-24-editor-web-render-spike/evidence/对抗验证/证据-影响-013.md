## 3. 影响

- 路径①失败后由路径③静默接管，与路径①真正跑通，在 3.1 的验收读数上完全一致：两种情况都是「中心像素红 + 正控过」。
- 「实际跑通路径」只出现在 evidence 的文字要求里，没有机器可读字段，也没有「path 与 evidence 声明不符就判红」的断言。实现者把路径③跑通后，可以在 evidence 里写「路径①跑通」而不触发任何失败——这正是静默降级：**核心交付物（零拷贝可行与否的判定）没有能失败的判据**。
- 4.2 的「可行性结论」同样是 md 文档；4.1 的回归、3.1 的正控都不读它。
- 附带说明：性能本身在 design 第 51 行明示「性能非目标、明示非零拷贝」，不算静默降级；本条针对的是「哪条路径跑通」这个判定，而不是速度。

## 4. 建议的能失败判据

1. 定义机器可读字段：每次运行写 `path=zero-copy` 或 `path=cpu-readback`（宿主日志 + 读数文件双通道），3.1 断言该字段与 evidence 声明一致。
2. 加负控：强制路径①（例如 `CASCADED_WEBRENDER_SPIKE_PATH=zero-copy`）且互操作不可用时，必须以点名原因的失败退出（如 `E_SPIKE_ZEROCOPY`），不得自动落到路径③；该负控落 evidence 并能在 CI 复跑。
3. 4.2 的结论必须引用该字段的原始读数行（文件 + 行号），而不是只写结论句。
