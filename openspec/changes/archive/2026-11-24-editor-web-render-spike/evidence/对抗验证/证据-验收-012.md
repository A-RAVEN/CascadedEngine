# 证据：主张-验收-012

- 面：验收可失败性-④（4.2 可行性结论「可核」）
- 严重度：Blocking
- 主张：4.2 的「结论可核（运行读数或阻塞证据）」是松口径，且不要求判定与 2.3 的实际路径一致——CPU 读回实现 + 「零拷贝可行」判定可以同时过。

## 一句话结论

这是整个 spike 的结论任务，而它的验收等于「写一份带读数或带链接的报告」。两条腿都软，且没有一条把结论钉在「实际实现了什么」上。

## 为什么这条判据现在不能失败

1. 「可核」= 有一条腿满足即可。判「不可行」只要一份文档链接（1.1 已经不再要求别的，见主张-验收-005）；判「可行」只要一份运行读数，而这份读数可以是 3.1 的正控读数原样复制——它证明的是「画面到了网页」，不是「零拷贝」。
2. 4.2 没有要求判定与 2.3 的实现路径一致。2.3 允许走 CPU 读回兜底（design.md:34 明说兜底「一定能跑通」），而 4.2 的判定可以写「零拷贝可行」。两句都各自满足自己的验收，合起来是自相矛盾的结论。
3. 判「可行」需要的证据类型与判「不可行」完全不同（一个要没有 CPU 读回的证明，一个要否定命题的证据），工件对两者都只写了一句笼统的「给运行读数 / 给阻塞证据」。
4. 结论的落点是 TODO/008 未决问题 1，而那条问的是 Vulkan↔WebGPU（见主张-验收-013），于是判定即使写错平台，也能算「已更新」。

## 加严建议（可直接落进工件）

1. 判定必须与 2.3 路径一致：2.3 走 CPU 读回时，4.2 判「零拷贝可行」即红（`E_WEBSPIKE_VERDICT_MISMATCH`）。
2. 判「可行」必须附「该帧没有走 CPU 读回」的可核证据：实现里零拷贝路径上不存在 `Readback` 调用点，或日志里该帧没有 Readback 记录；只给 3.1 的正控读数不算。
3. 判「不可行」必须逐字复用 1.1 冻结的版本号与三段阻塞证据（快照 URL + 检索零命中 + 版本），并写明「本次核实覆盖候选①②③中的哪几条」。
4. evidence 里放一张对照表：`判定` ↔ `2.3 实际路径` ↔ `1.1 证据`，缺表即不合格。
