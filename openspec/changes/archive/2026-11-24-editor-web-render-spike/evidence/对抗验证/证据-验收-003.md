# 证据：主张-验收-003

- 面：验收可失败性-①（3.1 网页 canvas 中心像素断言）
- 严重度：Blocking
- 主张：期望是恒定纯红，且没有禁止网页本地画红，于是「页面自己画红」与「原生渲染进网页」不可区分，3.1 可以恒绿。

## 一句话结论

3.1 只盯一个常量像素值。任何来源的纯红都能满足它，包括页面自己在没收到任何原生帧时画的那一块。这个 spike 最容易被自己糊过去的地方正在这里：开发时可以顺手在页面上画个红块验证 canvas 能用，画完忘了删，3.1 从此永远绿。

## 为什么这条判据现在不能失败

1. 断言只有一个常量期望值，被测对象是「canvas 中心是不是纯红」。页面自己 `fillRect` 一块红，与原生送入红字节，在这条断言下完全等价。
2. 工件没有禁止页面本地绘制。反而 1.2 要求做「互操作胶水」，页面在收不到帧时画点什么是最自然的第一版实现；design.md:40 也只是**假设**它会空白或黑，没有把它写成约束。
3. 期望值恒定还有一个副作用：即便胶水页后来被改成「优先用原生帧、没有就画占位红」，测试也发现不了——因为两条来源产出同一个值。
4. 仓库对这类风险的既有处置是「两边各写一份夹具，不共享常量表」和「恒真/恒假实现也能过的判据不合格」（命令 4、5）。本工件两条都没有对应的安排。

## 加严建议（可直接落进工件）

1. 明文约束写进 1.2 与 3.1：页面在未收到原生帧时 MUST NOT 绘制任何像素，画布保持浏览器初始状态；占位色、占位图、示例红三角一律禁止提交。
2. 加「不启动原生渲染」的对照组红态：只起 WebView2 与页面、不起 D3D12 渲染，断言必须红（`E_WEBCANVAS_NO_FRAME`）。这条能直接杀掉「页面自己画红」的实现。
3. 中心点之外再加一个原生侧每帧变化的采样点：把帧序号对 256 取模写进左上角 1×1 采样点，C++ 逐帧断言该点跟随变化。恒定红过不了逐帧变化的点；这条同时给 002 的帧序号判据提供像素级证据。
4. 采样的算法与值都写在 C++ 侧，网页侧只负责搬运，不许网页知道「期望应该是什么」——照 `CSharpConstantColorProbe` 的双夹具惯例。
