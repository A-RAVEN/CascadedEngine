# 证据-影响-014：红态没有构造机制，「断链时 canvas 空白或黑」是没有被固定的前提

对应主张：`主张-影响-014.json`（严重度 blocking）。

## 4. 影响

- 没有开关，红态只能靠「临时改代码，跑一次，贴 txt，再改回来」构造：evidence 里的 txt 无法在 CI 复跑，下一次运行也不能重放。
- 更关键的是前提没有被固定：spec 说断链时 canvas「空白或黑」，但路径③下 canvas 的初始内容由网页胶水决定（透明黑、被清成黑、还是被预填成红色）。工件没有一条断言检查「未收到字节时 getImageData 的读数」，也没有禁止网页侧预填颜色；如果页面在 JS 里先填红再尝试 `putImageData`，断链时中心像素仍是红，3.1 会假绿。
- 因此「反例 MUST 红」在工件里既没有构造方式，也没有对「空白/黑」这一前提的断言。

## 5. 建议的能失败判据

1. tasks 2.3/3.1 写死红态开关（例如 `CASCADED_WEBRENDER_SPIKE_SELFTEST=skip-transfer` 与 `no-native-render`），只让「传输」或「原生渲染」单步失败。
2. 断言未收到字节时 canvas 的读数写死（例如 `getImageData` 返回 `(0,0,0,0)`），并禁止网页侧预填任何颜色（grep 页面源码里不得有 `fillStyle`/`fillRect` 的红色预填）。
3. 验收：开关生效时命令以点名错误码（如 `E_SPIKE_BLANK`）退出，并与绿态读数一起落 evidence；该命令必须能在同一环境重复跑出同样结果。
