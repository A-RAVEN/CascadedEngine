## 一、Non-goals 把零拷贝排除在本批之外

`proposal.md` 原文（逐字，第 36 行）：

> - **零拷贝性能优化**：spike 先证「能显示」，性能/零拷贝是后续；CPU 读回概念验证可作为兜底正控。

同文件第 34 行还把「Vulkan 共享纹理互操作」列为 Non-goals——共享纹理互操作整体被当作后续方向，本批只验「能显示」。

## 二、tasks 2.3 把它写成条件式实现任务

`tasks.md` 原文（逐字，第 16 行）：

> - [ ] 2.3 互操作实现（按 1.1 结论）：零拷贝可行则实现共享纹理→WebGPU canvas；不可行则 CPU 读回共享纹理→字节传网页→canvas.putImageData 兜底。网页 canvas MUST 显示原生渲染画面。验收：构建过；3.1 正控过；evidence 注明实际跑通路径（零拷贝/CPU 读回）。

`design.md` D3 同样写「核实可行则实现」（第 30 行）：

> - **路径①（零拷贝目标）**：Chromium/WebView2 实验性共享纹理互操作（若该版本暴露）。核实可行则实现；不可行则记具体阻塞（API 缺失/版本/文档 URL）。

## 三、范围随研究结论浮动

- 若 1.1 核实「可行」：2.3 要求实现共享纹理→WebGPU canvas，本批就包含 Non-goals 排除的工作。
- 若 1.1 核实「不可行」：2.3 走 CPU 兜底，Non-goals 不被越过。

开工前无法确定的边界不叫边界。四份工件里也没有第三处文字说「零拷贝实现属于本批」，只有 tasks 2.3/design D3 这两处实现指令。

## 五、结论与改法

`tasks.md` 2.3 的「可行则实现」与 proposal Non-goals 的「是后续」互斥；后者是范围声明，前者是任务指令，执行者只能二选一。

改法：保留 Non-goals 就删掉 2.3 的实现分支，只留「按 1.1 结论实现兜底 + 记录零拷贝可行性结论与后续入口」；要做零拷贝就改 proposal/spec（见主张-一致-001 的二选一）。本条与 001 同源，父 agent 合并处置。
