## 3. 影响

- 上下/左右翻转是绕画面中心做的：中心点是翻转轴的不动点，翻转后中心像素必然保持原值。缩放错配若以中心为锚，中心同样不变；部分传输只要覆盖中心附近，中心也仍红。
- 路径③是 CPU 逐字节拷贝→`putImageData`，最容易出的正是行序（D3D12 自下而上 vs canvas 自上而下）、尺寸错配与部分传输。中心一点判据对这些全部免疫。
- 工件把「网页 canvas MUST 显示原生渲染画面」的自动证明压缩成一个点，其余只能靠 3.2 的人工截图；截图不是可失败判据（同一张图人眼也可能看漏），也无法在 CI 里跑。
- 结果是「部分传输/翻转」这类正确性降级可以全绿通过，只在截图环节靠运气被发现。

## 4. 建议的能失败判据

1. 正控改成多点签名：背景色、中心、三角形三个顶点附近、一个角落哨兵，四个以上期望值写死（例如背景 `(0,0,255,255)`、中心 `(255,0,0,255)`，与 `TestCSharpScene` 先例一致）。
2. 断言传输字节数 == 宽 × 高 × 4，并断言 canvas 的 `width/height` 与原生画面尺寸一致。
3. 反向构造：在传输里翻转行序或只传一半字节，上述多点判据必须至少打红一个点（证明它不是恒绿）。
