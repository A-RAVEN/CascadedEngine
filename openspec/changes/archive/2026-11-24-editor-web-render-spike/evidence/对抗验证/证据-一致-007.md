## 一、spec 把两种判据并列成「或」

`spec.md` 要求 1 原文（逐字，第 5 行，节选）：

> 网页 canvas 中心像素 MUST 等于写死期望（沿用 (255,0,0,255) 精确匹配惯例），经网页 getImageData 回传 C++ 断言或 CapturePreviewAsync 抓窗 read_image 核对。

场景 1（逐字，第 10 行）：

> - **THEN** 网页 canvas 中心像素 MUST == (255,0,0,255)（getImageData 回传断言或抓窗 read_image 核对）；断链/未渲染时 MUST 红（空白/黑像素不符）

要求 3 与场景（逐字，第 33、38 行，节选）：

> spike MUST 有真实打开原型窗的截图 + 主循环 read_image 核对网页 canvas 显示原生渲染（编辑器类硬要求）。

> - **THEN** CapturePreviewAsync 抓窗 PNG MUST 经 read_image 核对 canvas 区显示原生画面；MUST NOT 置前/最小化/移动用户窗口；缺截图或画面不符 MUST 判不通过

## 二、design 与 tasks 沿用同一个「或」

`design.md` D4 原文（逐字，第 39 行）：

> - 网页侧 `canvas.getImageData` 读中心像素，经 host object/WebSocket 回传 C++ 断言 == (255,0,0,255)（或写死纯色期望）；**或** CapturePreviewAsync 抓 WebView2 PNG（不前置，AGENTS §2）+ 主循环 read_image 核对 canvas 区显示红三角。

`tasks.md` 3.2 原文（逐字，第 21 行，节选）：

> read_image 核对网页 canvas 区显示原生红三角。验收：截图存 evidence/3.2-截图.png + read_image 核对记录；抓不到/不符判不通过。

## 三、两个判据不等价

`read_image` 的输入是 PNG 图片，输出是「看到什么」；它无法读出像素四元组，也没有阈值/采样点定义。spec 要求 1 的 MUST 是「中心像素 == (255,0,0,255)」——只有 getImageData 路径能判定。把截图路径写成「或」，等于让精确数值 MUST 变成可选。

反过来，若执行者只做 getImageData，tasks 3.2 的截图 + read_image 记录也仍可被写成「看过了」，但 spec 要求 3 的视觉验收又要求真实截图；两条判据互相顶替时，没有任何一方能保证另一方被做。

## 五、结论与改法

数值 MUST 与目视核对被写成同一条判据的两个可选项，强度差一个量级；这是本 spike 唯一的正控，不能留这种口子。

改法：删「或」，拆两条都 MUST 的判据——数值（getImageData 四元组 == (255,0,0,255)，有反例）与视觉（截图 + read_image 只核对形状/位置/非空白）。spec 场景 1 只保留数值判据，视觉要求归要求 3。
