# 证据：主张-验收-008

- 面：验收可失败性-③（2.1 原生离屏读回与 3.1 网页 canvas 是否两套独立判据）
- 严重度：Blocking
- 主张：2.1 的「离屏读回中心 == (255,0,0,255)」没有钉在读回哪张纹理上；照仓库先例读一张独立离屏捕获纹理就能过，共享纹理有没有做出来不影响判据。

## 一句话结论

2.1 是本 spike 里唯一证明「原生侧真的渲染出了红」的判据。它现在只证明「某张离屏纹理的中心是红」，不证明「这张纹理带共享句柄、能被第二个消费者打开」。而本 spike 的核心恰恰是后者。

## 为什么这条判据现在不能失败

1. 2.1 只给了一个像素期望，没有给「读回的是哪张资源」的约束。开发者照仓库先例（命令 2、3）建一张普通离屏捕获纹理做读回、另建一张带共享句柄的纹理放着不读，2.1 依然全绿。
2. 这不是假设：仓库先例本身就把「窗口后台缓冲」和「离屏捕获纹理」分成两张资源，像素判据读的是后者（命令 2）。共享纹理在本仓库是全新能力（命令 4：0 处共享句柄代码），新能力和旧检测手段之间没有绑定关系。
3. 「共享句柄产出可核」这句在 2.1 里独立存在，但它没有判据（主张-验收-011），而且即便句柄非空，也不代表那张纹理就是被读回的那张。
4. 后果是连锁的：2.1 绿 → 3.1 的「原生侧正控」成立 → 但原生侧从没证明过共享纹理可用，spike 的核心命题（共享纹理进网页）就少了一整条证据链。

## 加严建议（可直接落进工件）

1. 2.1 改成三层判据、缺一即红：
   - ① 读数行打印共享纹理的共享句柄值、尺寸与资源描述（`MiscFlags` 含 `SHARED`）；句柄为 0 或描述不含 `SHARED` 判 `E_WEBSPIKE_NOSHARED`；
   - ② 读回的 `ImageHandle` 必须就是第 ① 层那张（同一个读数行字段，禁止另建「捕获纹理」）；
   - ③ 从共享句柄 `OpenSharedHandle` 到第二个消费者（另一设备、或 D3D11 侧）后读回中心，同样必须 == `(255,0,0,255)`。这一步才真正证明「共享」可用，也才是 3.1 应有的前提。
2. 红态：把 `MISC_SHARED` 去掉后第 ① 层必须失败（`E_WEBSPIKE_NOSHARED`），贴 `result.json` 原文。
3. tasks.md:14 的「构建过」删掉或换成具体产物判据（构建成功不算验收，AGENTS §2）。
