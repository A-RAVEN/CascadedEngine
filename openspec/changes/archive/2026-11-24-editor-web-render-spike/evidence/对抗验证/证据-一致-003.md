## 三、现有接口没有共享句柄能力，且都在绑定面

`GPUTexture.h` 描述符字段（逐字，第 9–18 行）：

> ```cpp
> 	struct GPUTextureDescriptor
> 	{
> 		ETextureFormat format;
> 		ETextureType textureType;
> 		//ETextureAccessTypeFlags accessType;
> 		uint32_t width;
> 		uint32_t height;
> 		uint32_t layers;
> 		uint32_t mipLevels;
> 		EMultiSampleCount samples;
> ```

没有共享标志，也没有取共享句柄的入口。`GPUTexture` 与 `CRenderBackend` 都是绑定面类：

```text
PS> Select-String -Path 'Interface\RenderInterface\header\GPUTexture.h','Interface\RenderInterface\header\CRenderBackend.h' -Pattern 'CA_BIND'
GPUTexture.h:2 // 绑定标注宏（CA_BIND）：这个头自己也进绑定面（2.2）。
GPUTexture.h:151 CA_BIND()
CRenderBackend.h:67 CA_BIND()
```

`CRenderBackend.h:108`（逐字）：

```cpp
		virtual castl::shared_ptr<GPUTexture> CreateGPUTexture(GPUTextureDescriptor const& inDescriptor, ETextureAccessTypeFlags accessType) = 0;
```

描述符已被按值镜像到托管面：`Scripting/Managed/NativeRenderSugar.cs:1373` 与 `:1453` 都是 `GPUTextureDescriptor descriptor = new GPUTextureDescriptor`。也就是说给它加「共享」字段会改变绑定产物。

## 六、结论与改法

这是「要求 A（渲染到共享纹理并产出可核句柄）+ 要求 B（绑定产物逐字节不变）+ 现状 C（接口无共享能力、且在绑定面）」三者拼不出一条执行路径的问题。工件没有写新 API 放哪、也没有提 CA_BIND_SKIP 旁路，执行者照 2.1 字面实现就得扩绑定面，然后 4.1 自己变红。

改法：在 design D2/tasks 2.1 写死落点（首选 CA_BIND_SKIP 的 C++ 专用取句柄入口，并给「基线对账 0/0/0 + 共享句柄读数」的验收；若必须改绑定面，则走换锚程序同步 spec 要求 3）。同时裁决 CPU 兜底时共享纹理/共享句柄是否仍是本批 MUST，避免留下无消费者的强制要求。
