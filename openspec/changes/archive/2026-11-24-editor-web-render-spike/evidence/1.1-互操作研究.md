**标准 Web API 里没有"把 DXGI 共享句柄变成 WebGPU 纹理"的入口**，不是"我们没找到"。

### 补充：`importExternalTexture` 只收两种网页对象（逐字引文）

WebGPU 规范 `spec/index.bs` 第 3131 行（IDL）：

```webidl
GPUExternalTexture importExternalTexture(GPUExternalTextureDescriptor descriptor);
```

同文件 `dictionary GPUExternalTextureDescriptor`：

```webidl
dictionary GPUExternalTextureDescriptor
         : GPUObjectDescriptorBase {
    required (HTMLVideoElement or VideoFrame) source;
    PredefinedColorSpace colorSpace = "srgb";
};
```

即：**`importExternalTexture` 的 source 只接受 `HTMLVideoElement` 或 `VideoFrame`，不接受裸共享句柄**。
WebCodecs 规范里 `VideoFrame` 的构造来源同样只有两类（`index.src.html`）：

```webidl
constructor(CanvasImageSource image, optional VideoFrameInit init = {});
constructor(AllowSharedBufferSource data, VideoFrameBufferInit init);
```

`CanvasImageSource` 是网页侧图像源（`HTMLCanvasElement` / `ImageBitmap` / `OffscreenCanvas` /
`HTMLVideoElement` / `VideoFrame` 等），`AllowSharedBufferSource` 是 CPU 字节；**两条都不接受原生句柄**。

### 出处：GPUWeb #5167（[链接](https://github.com/gpuweb/gpuweb/issues/5167)）

标题：`importExternalTexture: Support importing platform-shared GPU textures (DXGI / IOSurface / dma-buf)`；
状态 **closed / not_planned**（2025-04-21 提出，2026-11-24 查询时仍为关闭）。正文逐字：

> `importExternalTexture()` currently requires its source to be HTMLVideoElement or VideoFrame. There is no
> standard way to turn a platform‑shared GPU texture handle ... into either of those objects, so WebGPU
> developers must round‑trip through CPU memory.

维护者关闭理由（评论逐字）：

> Objects like `IOSurface` don't exist in the Web platform, and there's no way to refer to them, so this is on
> the native side of a browser engine. It's not a cross-Web-spec problem - the problem is entirely outside the
> purview of the Web platform.

即：这类互操作要由**浏览器引擎自己**（Electron 那一层、或 WebView2 那一层）开入口，网页侧没有标准入口。


实测输出：

```text

```

原型窗运行时还会把**同一个值**写进读数行：`Scripting/Managed/Editor/SpikeWindow.cs` 在环境创建完成时读
`CoreWebView2Environment.BrowserVersionString`，`EditorService.EmitReadings` 把它作为 `webview2Version=<版本>`
追加到 `[编辑器 读数]` 行。第三方可用
`GPUBackendTester.exe --test TestWebRenderSpike --backend d3d12` 复跑核对；这条读数由
`CASCADED_EDITOR_READINGS_FILE` 指向的文件给出（见 2.2 任务）。

WebView2 与 Edge 的关系有官方答复（[WebView2Feedback #1285](https://github.com/MicrosoftEdge/WebView2Feedback/issues/1285)）：

> We generally support what the Microsoft Edge Chromium platform supports. ... If you can find a command line
> arg that turns this on for Chromium, that same arg will likely work for WebView2.

也就是说 WebView2 的网页能力跟 Edge/Chromium 走；而 Chromium 侧的共享纹理导入在**引擎内部**
（[electron/electron#46811](https://github.com/electron/electron/pull/46811) `feat: import external shared
texture into VideoFrame`，closed 后拆成多个依赖 PR），**不是嵌用方（WebView2 宿主）能从网页侧调用的 API**。

## 四、三条候选路径的判定

### 路径① 零拷贝：D3D12 共享纹理直接进 WebGPU 纹理 —— **不可行（阻塞证据充分）**

阻塞项（逐条给具体缺口，不是口头断言）：

1. **缺失 API**：标准 WebGPU 没有"导入 DXGI 共享句柄"的方法（术语即 `importSharedTexture` 一类，规范
   零命中）；`importExternalTexture` 的 source 只收 `HTMLVideoElement` / `VideoFrame`（逐字 IDL 见第二节）。
2. **缺失桥接对象**：网页侧无法把原生句柄变成 `VideoFrame`——`VideoFrame` 的构造来源是 `CanvasImageSource`
   或 CPU 字节（逐字 IDL 见第二节），没有"平台句柄"重载。
3. **规范层已明确关闭该提案**：GPUWeb #5167 状态 `closed / not_planned`，维护者答复"这在网页平台范围之外，
   要由浏览器引擎自己开"（逐字引文见第二节）。
4. **本机运行时**：WebView2 **157.0.4341.60**（第三节）；即使 WebGPU 在该版本可用，可用的是
   `importExternalTexture` 那套（只收视频/VideoFrame），仍不覆盖共享句柄。此判定不依赖"WebGPU 有没有开"，
   而依赖"有没有这个 API"——零命中已经回答。

结论：本批**不实现零拷贝**（与 proposal Non-goals、design D3 一致）；后续若要做，必须等浏览器引擎
（WebView2/Chromium）提供"共享句柄 → VideoFrame/纹理"的入口，属引擎侧能力，不是本项目网页侧能补的。

### 路径② VideoFrame 桥 —— **不可行（作为零拷贝桥）**

- 若"桥"指在**引擎内部**把共享纹理包成 `VideoFrame`（Electron #46811 那条路），WebView2 嵌用方没有对应
  配置/接口可开，且需要改浏览器引擎本身 → 本批不可用。
- 若"桥"指在网页侧用 `new VideoFrame(canvas)` / `new VideoFrame(buffer)` 造帧，那是 **CPU 拷贝路径**
  （像素已经在 CPU 内存里），等价于路径③ 的显示方式，不构成零拷贝。
- 因此路径②判 **不可行**，并注明：不是"没试"，是"两条可能的解释都走不通"。

### 路径③ CPU 读回 —— **本批实现（path=cpu-readback）**

C++ 从共享纹理读回 RGBA 像素（`Readback` 绑定面 `CA_BIND_SKIP`，读像素只在 C++）→ C++→C#（EditorService
WebSocket 通道）→ 网页 `canvas.putImageData`。这条路**不依赖 WebGPU**，只依赖 canvas 2D，因此
WebView2 版本/WebGPU 开关都不构成风险（design Risks 第 2 条）。

## 五、退路建议（喂 4.2 / 后续 editor-free-dock）

- **路线 B 透明叠层**：原生渲染仍在原生 HWND/swapchain 上，网页用透明背景的 WebView2 叠在上层，dock 框架
  只做网页侧布局。代价：合成顺序与命中测试要按窗口层级处理，网页无法在 canvas 里"看到"原生像素。
- **CPU-GPU 桥（本批已证的最小版）**：CPU 读回 + 共享内存/字节通道。代价：每帧一次 GPU→CPU 拷贝
  （256×256×4 = 262144 字节/帧），高分辨率/高帧率下不可行，只适合 spike 与低频预览。
- 这两条都留给后续 `editor-free-dock` change 定（proposal Open Questions 3）。
