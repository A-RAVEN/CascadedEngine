# 5.5 Vulkan 可行性结论：Vulkan 共享图像 → WebView2 网页 canvas

> 结论一句话：**Vulkan 设备的 Win32 外部内存导出/导入在本机可用**（共享图像句柄非空、第二消费者导入成功、读回同一图像多点匹配）；
> 但**"共享图像零拷贝进网页 canvas"仍不可行**——网页侧没有导入 Vulkan 外部内存句柄的 API（与 D3D12 同一根因，且本批
> 引擎的 Vulkan 后端创建设备时未启用 `VK_KHR_external_memory_win32`，规范又禁止改后端公共代码）。
> 因此本批 Vulkan 实现走 **CPU 读回**（运行读数 `path=cpu-readback`），与判定一致；Vulkan↔WebGPU 的"零拷贝可行"不成立。

## 三、可行性判定（与 path 一致）

| 问题 | 判定 | 证据 |
|---|---|---|
| Vulkan 设备支持 Win32 外部内存？ | **支持（本机实测）** | `vulkaninfoSDK --summary`：`VK_KHR_external_memory` + `VK_KHR_external_memory_win32`；原型日志 `externalMemory=1 externalMemoryWin32=1` |
| Vulkan 共享图像可建、句柄可导出、第二消费者可导入并读回同一图像？ | **可行（本机实测）** | 原生侧正控：句柄非空 + `VkImportMemoryWin32HandleInfoKHR` 导入成独立 VkImage/VkDeviceMemory + 读回字节与本设备读回逐字节一致 + 多点/帧序号位匹配（`5.3-Vulkan绿跑测试日志.txt`） |
| Vulkan 共享图像**零拷贝**进 WebView2 网页 canvas？ | **不可行（本批环境）** | 网页侧无导入 Vulkan 外部内存句柄的 API：`VkExternalMemory` / `OPAQUE_WIN32` / `externalMemory` / `vkGetMemoryWin32HandleKHR` / `VK_KHR_external_memory` 在 WebGPU 规范 **0 命中**；`importExternalTexture` 只收 `HTMLVideoElement`/`VideoFrame`（1.1 逐字 IDL）；WebCodecs `VideoFrame` 构造不收平台句柄；GPUWeb #5167 closed/not_planned；本机 WebView2 **157.0.4341.60** 同样没有这类入口。另有引擎侧阻塞：`RenderBackend_Vulkan.cpp` 的设备创建未启用 `VK_KHR_external_memory_win32`，而规范要求 spike MUST NOT 改后端公共代码 |
| 本批实际走哪条路？ | **CPU 读回（path=cpu-readback）** | 见下：`vkCmdCopyImageToBuffer` → map → C++→C#（EditorService WebSocket）→ 网页 `putImageData` |

**一致性强校验**：判定"Vulkan 零拷贝不可行" ↔ 运行读数 `path=cpu-readback` —— 一致。若判"零拷贝可行"，必须给出
"该帧没有 Readback" 的证据；而本批每帧都经过 `vkCmdCopyImageToBuffer`（`spike-frame` 的 `pixels` 就是读回字节），
"可行"会与读数直接矛盾，必判红。

## 五、退路建议（与 4.2 同一组，Vulkan 侧追加两条前置条件）

1. **路线 B：透明叠层**——不需要任何外部内存互操作；Vulkan 后端照常渲染到窗口/离屏，WebView2 透明叠层。
2. **CPU-GPU 桥**——本批已验证 `vkCmdCopyImageToBuffer` → C++→C#→网页这条链路（256×256×4 = 262144 字节/帧），
   做多缓冲/共享内存可降拷贝开销，但不是零拷贝。
3. **真零拷贝的前提（两件缺一不可）**：① 引擎 Vulkan 后端在设备创建时启用 `VK_KHR_external_memory_win32`
   （本批为不改公共代码而没做）；② WebView2/Chromium 暴露引擎侧"外部内存 → WebGPU 纹理/VideoFrame"入口
   （GPUWeb #5167 那类提案被引擎实现）。当前两者都不成立。
